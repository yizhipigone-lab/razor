### Q1：回测交易有K线图展示吗？

**有。** 两个入口：

1. **选股信号表** — 每行"查看图表"按钮（`main.js:2879`）
2. **回测交易表** — 每行"图表"按钮（`main.js:3097`）

都调用同一个 `showChart()` 函数（`main.js:3184`），打开 K 线图弹窗（ECharts K 线 + 成交量 + MA5/MA10/MA20）。

**B 点标记已修复**：`main.js:3272-3289` 现在 `if (signalBuyDate)` 无条件画（不再要求 `isSignal &&`）。计划书 1.2 项标记 ✅ 已做——正确。

**小问题**：`main.js:3282` 的 fallback 链 `trade.close` 在回测交易对象中不存在（回测 trade 有 `entry_price`/`exit_price`/`pnl_pct`/`ret_pct`，无 `close`），可去掉避免误导。

### Q2：优化后 config 的 `optimizer.search_space` 还会对 AI 回测生效吗？

**会，且计划书没有改变这条链。**

代码链路：
```
config/app_setting.json → optimizer.search_space
  ↓ (settings.optimizer_search_space)
ai_optimizer.py:1032  search_space = settings.optimizer_search_space
  ↓
ai_optimizer.py:1044  _run_exploration(search_space, ...)
  ↓
ai_optimizer.py:1091  refined_space = search_space  (未启用 LLM 时)
  ↓
ai_optimizer.py:1095  _run_bayesian(refined_space, ...)
```

**计划书 §3 只改了**：objective 返回值（score→valid_score）、`_sort_key` 排序（score→valid_score）、样本切分方式。**没有动搜索空间的读取和使用**。

`config/app_setting.json` 中 `optimizer.search_space` 的 10 个参数（tp1_profit/tp2_profit/tp1_ratio/.../time_exit_days，每个含 min/max/step）**仍然是 AI 寻优的唯一参数搜索范围来源**（LLM 动态生成搜索空间的路径走另一条，但那是 `use_llm=true` 时才触发）。

**但计划书漏了一件事**：`_lhs_sample`（`:193`）和 Optuna trial（`:797-808`）都不读 `step` 字段——config 里的 `step` 是**死字段**（寻优-H1）。计划书 §3.3 把它放在"结构性增强（中期）"里，表示**现在不修**。这意味着即使修了过拟合口径，搜索空间中的 `step` 仍然不生效。

## 3. 我发现的计划书遗漏

### 3.1 §2.2.4 的 `_calmar_score` 输入兼容性

`_fast_simulate` 返回的 `pnl_pct` 目前是百分比值（`realized` 是百分比累加），`_calmar_score`（`:72-87`）计算 `np.mean(pnls)` 期望 pnls 是百分比列表。如果改为金额口径，需要同步：
- 改 `_calmar_score` 的输入格式（或保持 `_fast_simulate` 返回百分比兼容旧接口）
- 检查 `_summarize_result`（`:117-137`）中的 `avg_pnl` 计算——当前 `float(np.mean(pnls))` 期望百分比

**建议**：在 §2.2.4 或 §3.2 增加一行确认 `_fast_simulate` 的 pnl 格式与 `_calmar_score`/`_summarize_result` 之间的契约不变。

### 3.2 成本参数的"双源"问题

计划书 §2.2.6 要在 config 新增 `backtest.cost`。但 `execution.py:64/78` 的 `calc_buy_cost/calc_sell_revenue` 函数签名接受 `cfg: dict = None`，如果不传 cfg，它们从哪读成本率？目前可能从 `settings` 或硬编码读。**计划书应先确认现有 cost 来源**，再决定 config 新增段的结构。

### 3.3 78 公式批跑的 `_fast_simulate` 占比

计划书 §6 以 `_fast_simulate` 为最小起点——但 `_fast_simulate` 是 Python 策略的 1m 寻优路径，78 公式走 TDX 路径（`_run_trial_tdx`→`tdx_runner`）。如果 78 公式全部是 tdx 策略，那 `_fast_simulate` 单点改完后对 78 公式基线 diff 的影响是**零**——因为 78 公式不经过 `_fast_simulate`。真正的验证需要在**一条 Python 策略**上做。

**建议**：在 §6 的"一个策略"前面明确是"Python 策略（非 TDX）"，并用 Python 策略验证而非 78 公式。
