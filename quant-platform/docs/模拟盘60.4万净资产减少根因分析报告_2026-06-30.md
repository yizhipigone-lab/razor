# 模拟盘净资产减少 60.4 万 — 根因评估报告

> 生成时间：2026-06-30
> 问题描述：6月29日图表显示净资产比6月26日减少 60.4 万，但26日到29日之间没有任何买入/卖出交易记录

---

## 二、代码链路分析

追踪了完整调用链：

```
get_engine() → SimTraderEngine.__init__() → JsonSimStore 加载
    ↓
每日 cron: sell_phase() → check_stops() → execute_sell()
    ↓
    record() → total_equity() → save_equity_point()
    ↓
    JsonSimStore._save() — 全量写 state.json
```

## 三、发现的 5 个设计缺陷

### 🔴 缺陷 A（致命）— 原子写入缺失

**位置**：`app/sim_trader/store.py:243-245`

```python
def _save(self):
    with open(self._path, 'w', encoding='utf-8') as f:
        json.dump(self._data, f, ensure_ascii=False, indent=2, default=str)
```

**问题**：`json.dump()` 是渐进写入操作——逐行写，不是原子操作。整个系统的所有状态（持仓、交易、现金、净值曲线）都在同一个 JSON 文件里。如果进程在 `_save()` 执行期间被 kill（OOM、系统重启、手动 kill -9），文件会变成半截的损坏数据。

**被调用频率**：几乎每次状态变更——无阈值调用，每天被触发数十次，碰撞窗口非常大。

**参考**：项目中已有正确的原子写入实现 `app/backtest/exit_rules.py:344-349`，但 `JsonSimStore` 没有使用。

---

### 🔴 缺陷 B（致命）— sell_phase 保存顺序颠倒

**位置**：`app/sim_trader/engine.py:537-551`

```python
# 步骤 1：清理已平仓的（从内存 dict 中移除）
self.positions = {k: v for k, v in self.positions.items() if v.is_active}

# 步骤 2：逐个持久化（写同一个 JSON 文件 3 次）
if self._store:
    self._store.save_prev_day_snap(self._prev_day_snap)   # → _save() 第1次
    self._store.save_positions(self.positions)              # → _save() 第2次
    self._store.save_state(self.cash, ...)                  # → _save() 第3次
```

**问题**：先清理内存中的 positions，再分三次写同一个文件。每个 `_save()` 都是完整覆写 `self._data`。三步之间任意一个崩溃：

| 崩溃时机 | JSON 里的 positions | JSON 里的 cash | 后果 |
|----------|---------------------|----------------|------|
| `save_positions` 之后、`save_state` 之前 | ✅ 已清空 | ❌ 旧的（卖出前） | **就是现在的情况** |
| `save_prev_day_snap` 之后、`save_positions` 之前 | ❌ 含已死仓位 | ❌ 旧值 | 重启后出现"僵尸持仓" |

**说明**：即使没有真的发生卖出（check_stops 返回空），这里也是每天执行的分三次写入，每次都有可能。如果 6/26 当天 check_stops 真的触发了部分卖出，风险更高。

---

### 🟡 缺陷 C（严重）— Position 序列化不完整

**位置**：`app/sim_trader/store.py:285-292`

```python
def save_positions(self, positions):
    self._data['positions'] = {
        code: {
            'entry_date': str(p.entry_date),
            'entry_price': p.entry_price,
            'shares': p.shares,
            'cost': p.cost,
            'strategy_name': p.strategy_name,
            'entry_time': getattr(p, 'entry_time', '15:00'),
        }
        for code, p in positions.items()
    }
```

**丢失的关键字段**：

| 字段 | 含义 | 丢失后的默认值 | 影响 |
|------|------|:---:|------|
| `is_active` | 是否活跃 | `True` | 已死仓位"复活" |
| `peak_price` | 历史最高价 | `entry_price` | 移动止盈跟踪重置 |
| `remaining_shares` | 剩余股数 | `shares`（原始） | 部分止盈后仓位恢复 |
| `tp1_triggered` / `tp2_triggered` | 止盈档位状态 | `False` | 重复触发同一档 |

**对比**：DuckDB 版 `SimTraderStore.save_positions` 保存了全部 11 个字段，JSON 版只保存了 6 个。

---

### 🟡 缺陷 D（严重）— 启动补录静默固化错误数据

**位置**：`app/sim_trader/engine.py:202-269`

```python
def _fill_missing_snapshots(self):
    # ...
    for code, pos in self.positions.items():
        if not pos.is_active or pos.remaining_shares <= 0:
            continue
        # 逐日从 parquet 读收盘价
        total_mv += pos.remaining_shares * close_px

    equity = self.cash + total_mv  # 如果 positions 为空 → total_mv = 0
    self.equity_curve.append({...}) # 不可逆写入
    self._store.save_equity_point(d, equity, ...) # 持久化
```

**问题**：启动时自动运行。当 `self.positions` 已经是空的（缺陷 B 已丢失持仓），它会逐日追加 `equity = cash + 0` 的净值记录，不可逆。本次案例中恰好 6/27-6/28 是周末，这个函数没有介入。但原则上，如果丢失后的第一个非周末日它运行了，会把错误数据写进净值曲线。

---

### 🟢 缺陷 E（中等）— save_equity_point 非即时落盘

**位置**：`app/sim_trader/store.py:323-327`

```python
def save_equity_point(self, d, equity, cash, positions):
    pts = self._data.setdefault('equity_curve', [])
    pts.append(...)
    if len(pts) % 10 == 0:  # ← 每10次才真正写文件
        self._save()
```

虽然有 `record()` 末尾的 `save_state()` 兜底写文件，但如果 `save_state()` 也失败，最新的 1~9 个净值点会丢失。

## 四、最可能触发场景

### 场景 #1（概率最高）：_save() 写入过程中进程崩溃

```
6/26 14:54  — cron 正常执行
    ├─ sell_phase: check_stops → 可能触发卖出 → execute_sell → save_trade
    ├─ buy_phase: 买入新股票 → execute_buy → save_positions
    ├─ record(): save_equity_point → save_state → _save()
    └─ ✅ 此时 state.json 正确

6/26 14:54 ~ 6/29 14:52（72小时窗口，含周末）
    ├─ 某个时刻 _save() 被调用
    │   ├─ 可能是监控扫描、手动 API 调用、定时任务
    │   └─ 或者只是进程被系统回收
    ├─ _save() 写文件过程中...
    ├─ 💥 进程被 kill / 系统重启 / OOM
    └─ ❌ JSON 文件损坏或被截断

6/29 启动
    ├─ get_engine() → JsonSimStore() → json.load(损坏文件)
    ├─ 场景 A: json.load 成功但数据残缺
    │   └─ positions = {}（丢失）、cash = 2,993,729（保留旧值）
    └─ _fill_missing_snapshots → 周末跳过

6/29 14:52 cron
    ├─ check_stops → 无持仓可检查
    ├─ record() → equity = 2,993,729 + 0
    └─ ❌ 错误净值被写入，数据损失固化
```

### 场景 #2：sell_phase 的三步写入中崩溃

如果 6/26 当天确实触发了这 4 只的卖出：

```
sell_phase:
  ├─ check_stops → 返回4条卖出信号
  ├─ for each: execute_sell → save_trade → _save() ✅
  ├─ sell_phase 清理 positions
  ├─ save_prev_day_snap → _save() ✅
  ├─ save_positions(cleaned) → _save() ✅   ← positions 变空
  ├─ save_state(new_cash) → _save() ... 💥  ← 崩溃! cash 没更新
  └─ ❌ state.json: positions=空, cash=旧值
```

**但是这个场景有一个矛盾**：我们确实没有看到 6/26 之后的卖出交易记录。要么交易记录跟 cash 一起丢了（都在同一个 `_save()` 里），要么确实没有卖出发生。

## 六、修复方案建议（待讨论）

### P0：必须立即修复

1. **原子写入**（修缺陷 A）
   - `JsonSimStore._save()` 改为先写 `.tmp` 再 `os.replace()`
   - 参考项目已有的 `exit_rules.py:atomic_write_parquet`

2. **保存顺序修正**（修缺陷 B）
   - `sell_phase` 里先保存 cash/state，最后再清理 positions
   - `execute_sell` 内部不再单独调 `save_positions`，由 `sell_phase` 统一收尾

3. **完整序列化**（修缺陷 C）
   - `JsonSimStore.save_positions` 补全 `is_active`、`peak_price`、`remaining_shares`、`tp1_triggered`、`tp2_triggered`

### P1：应该尽快修复

4. **启动数据完整性校验**
   - `__init__` 加载完成后检查一致性
   - positions 非空 但 equity_curve 最近日期 > trade 最近日期 → 报警

5. **save_equity_point 即时落盘**（修缺陷 E）
   - 去掉 `% 10 == 0` 的延迟条件

### P2：可后续改进

6. **Mermaid 图表可视化**：添加数据流图和状态转换图到工程文档
7. **考虑用 DuckDB（SimTraderStore）替代 JSON 存储**：享有事务支持和更丰富的字段

## 七、数据恢复可行性

可以通过以下方式反推丢失的持仓信息：

1. 从 `state.json` 的 `trades` 列表反查：找出 `entry_date <= 6/26` 且 `exit_date > 6/26` 或 `exit_date` 为空的交易
2. 从 DuckDB `sim_trades` 表查（如果数据同步过）
3. 从 `data/parquet/daily/` 读取对应股票的 6/26 收盘价，计算当时的持仓市值

> ⚠️ 需先确认当前 state.json 中 trades 列表是否也丢失了部分记录，才能判断恢复的完整程度。
