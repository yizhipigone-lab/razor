## v4 仍存在的问题

### MEDIUM — 中优先级（建议修复）

#### M-V4-1 — `_load_trading_calendar` 仍是私有函数调用

**位置：** 计划书第 84-85 行（utils.py 中的 `calc_trading_days`）

```python
from app.api.sim_trader import _load_trading_calendar
cal = _load_trading_calendar() or set()
```

**问题：** v3 → v4 修复 C3（私有方法调用）时，把 `exit_monitor._calc_hold_days` 提取到了 `utils.py`，但函数内部仍调用 `app.api.sim_trader._load_trading_calendar`（下划线前缀的私有函数）。封装问题只是迁移了一层。

**风险：** `app/api/sim_trader.py` 内部如果重命名或修改这个函数，`utils.py` 会静默失败（被 `try/except` 兜底返回日历日数，但精度下降）。

**修复建议：** 把 `_load_trading_calendar` 也提取到 `app/live_trader/utils.py` 或独立的 `app/utils/trading_calendar.py`，两边都从公共入口调用。

---

#### M-V4-2 — 进度条"对应预算"仍无定义

**位置：** 计划书第 46 行

```
| 剩余 > 0 | `min(remaining / 对应预算 * 100, 95)`% | `var(--yellow)` |
```

**问题：** v3 审计就指出过这个问题，v4 仍未定义"对应预算"对每种规则是什么：
- HS：`|hard_stop|`（6%）？`|avg_cost|`（1800 元）？
- TR：`trail_dd`（2%）？`|peak_pnl|`（11.2%）？
- TF：`trigger_days`（12 天）？
- TP1：`trigger_value`（3%）？

实现时如果不清楚每个规则的 divisor，代码逻辑会随意发挥。

**修复建议：** 在进度条公式里为每种规则指定 divisor：
- HS: `|hard_stop|`（百分比小数）
- TR: `trail_dd`（百分比小数）
- TF: `time_force_days`（天数）
- TP1: 当前未触发档位的 `profit_pct`

## v4 决策质量点评

**做得对的事：**
1. **战略转向正确**：v3 试图"添加 BE 但不修代码"，制造了文档与代码的双重不一致。v4 直接承认 BE 是回测专属功能，实盘面板不展示。这才是 v3 应该一开始就做的决策。

3. **"不做的事"明确化**：第 303 行新增"BE（保本止损）不展示"，把所有 BE 相关决策都集中在这一处。
4. **删除比修复更有效**：与其纠结 BE 的优先级定义、消息措辞、数据来源，不如直接删除。这种"做减法"的思维方式值得肯定。

**还能改进的：**

2. **进度条公式仍不完整**：M-V4-2 是 v3 遗留问题，v4 没修。
