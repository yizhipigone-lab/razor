## 1. 架构链路

```
前端 📡通达信选股Tab (index.html:1529)
  │ runTqsdkScreen() → POST /api/tqsdk/screen
  ▼
API层 app/api/tqsdk.py
  │ start_screen() → run_in_thread(_run)
  │   ├─ _load_trading_calendar() (from sim_trader.py)
  │   ├─ 逐日循环 scan_dates
  │   │    └─ bridge.execute_screen(end_time=d_str)
  │   ├─ 补充股票名称/板块 (SQL拼接 ⚠️)
  │   └─ db.save_tqsdk_screen_history() 持久化
  ▼
桥接层 app/tqsdk/bridge.py (TdxBridge)
  │ _run_worker(task)
  │   ├─ tempfile 写 args.json
  │   ├─ subprocess.run(["python", WORKER_SCRIPT, ...])
  │   │    cwd=E:\NEW_TDX\PYPlugins\user  ← 硬编码路径
  │   │    timeout=600s * multiplier
  │   └─ 解析 stdout JSON 行
  ▼
Worker app/tqsdk/worker/tqsdk_bridge_worker.py
  │ tq.initialize() → 调真通达信
  │ tq.formula_process_mul_xg() 执行公式选股
  │ tq.get_market_data() 取价格
  └─ print(json.dumps(result))
```

**关键特征**: 这条路径**不翻译公式**，而是把公式名传给真通达信引擎执行，结果通过子进程JSON回传。比Python翻译路径可靠，但引入了subprocess开销和外部依赖。

## 3. CRITICAL 级发现

### T-01: SQL注入 — 股票代码字符串拼接

**文件**: [tqsdk.py:139-141](app/api/tqsdk.py#L139-L141), [tqsdk.py:317-319](app/api/tqsdk.py#L317-L319)
**风险**: SQL注入 + 数据泄露
**影响**: 虽然codes来自TDX返回，但若TDX被污染或stock_list_override由前端传入，可构造恶意code执行任意SQL

**问题定位**:
```python
# tqsdk.py:139-141
detail_df = db.conn.execute(
    "SELECT code, name, sector FROM stocks WHERE code IN ({})".format(
        ",".join(f"'{c.split('.')[0]}'" for c in matched)  # 直接拼接！
    )
).fetchdf()

# tqsdk.py:317-319 同样问题
"SELECT code, name FROM stocks WHERE code IN ({})".format(
    ",".join(f"'{c}'" for c in stock_list)
)
```

**攻击路径**: 前端 `stock_list_override = ["1' OR 1=1--"]` → SQL变成 `WHERE code IN ('1' OR 1=1--)` → 返回全表

**修复方案**:
```python
# 使用参数化查询
placeholders = ",".join(["?"] * len(matched))
codes_clean = [c.split('.')[0] for c in matched]
detail_df = db.conn.execute(
    f"SELECT code, name, sector FROM stocks WHERE code IN ({placeholders})",
    codes_clean
).fetchdf()
```

## 4. HIGH 级发现

### T-03: 区间选股逐日串行，性能灾难

**文件**: [tqsdk.py:103-121](app/api/tqsdk.py#L103-L121)
**风险**: 长区间选股耗时极长，用户体验崩溃
**影响**: 选1年区间 ≈ 250个交易日 × 单次subprocess开销(数秒~600s) = **可能数小时到41小时**

**问题定位**:
```python
for i, d in enumerate(scan_dates):  # 逐日串行
    result = bridge.execute_screen(end_time=d_str, ...)  # 每天一次subprocess
```

而 `bridge.execute_screen` 内部又是逐batch循环（BATCH_SIZE=50），全市场5000只股票 = 100个batch × 250天 = **25000次TDX调用**。

**修复方案**: 用 `execute_screen_range` 一次性区间扫描，而非逐日循环
```python
# 改用区间模式（worker的_do_range已支持）
result = bridge.execute_screen_range(
    end_time=end_str,
    start_time=start_str,
    kline_count=500,
    stock_list_override=stock_list_override,
    formula_name=formula_name,
)
# signals 已包含整个区间的信号，无需逐日循环
for code, d in result.get("signals", {}).items():
    dates = d.get("Date", [])
    var_name = next((k for k in d.keys() if k != "Date"), "ZP")
    zps = d.get(var_name, [])
    for dt, v in zip(dates, zps):
        if _is_signal_value(v) and code not in all_matched:
            all_matched[code] = str(dt)
            break
```

### T-04: 交易日历fallback bug

**文件**: [tqsdk.py:83-87](app/api/tqsdk.py#L83-L87)
**风险**: 日历加载失败时，节假日也被当交易日扫描，浪费资源 + 产生空信号

**问题定位**:
```python
if d in cal or d.weekday() < 5:  # ← OR 是bug
    scan_dates.append(d)
# ...
if not cal:
    scan_dates = [d for d in scan_dates if d.weekday() < 5]  # 这行才过滤
```

逻辑漏洞：
1. `cal` 加载成功时：`d in cal or d.weekday()<5` → 周末也会被加入（因为周末weekday>=5但不在cal，所以False；但工作日无论是否在cal都True）→ 实际上cal失效时工作日全过
2. `cal` 为空时：第一层把所有工作日加入，第二层再过滤一次（冗余但正确）
3. 真正的bug：当 `cal` 非空但某法定节假日（如国庆）是工作日时，`d in cal` 为False但 `d.weekday()<5` 为True → **节假日被当交易日扫描**

**修复方案**:
```python
# 严格用交易日历，日历不可用时报错而非降级
if not cal:
    sync_broadcast({"type": "tqsdk_screen_done", "status": "error",
                    "message": "交易日历加载失败，无法选股"})
    return
scan_dates = [d for d in date_range(sd, ed) if d in cal]
```

### T-05: `_to_tdx_codes` 漏北交所

**文件**: [worker.py:461-469](app/tqsdk/worker/tqsdk_bridge_worker.py#L461-L469)
**风险**: 北交所股票代码后缀错误，TDX无法识别 → 漏选股

**问题定位**:
```python
def _to_tdx_codes(codes):
    for c in codes:
        code_num = c.split(".")[0] if "." in c else c
        prefix = code_num[:1]
        suffix = ".SH" if prefix in ("6", "9") else ".SZ"  # ← 只分SH/SZ
        tdx_codes.append(f"{code_num}{suffix}")
```

北交所代码以 `8` 或 `4` 开头（如830789），这里被标成 `.SZ`，TDX引擎找不到 → 静默丢失。

**修复方案**:
```python
def _to_tdx_codes(codes):
    tdx_codes = []
    for c in codes:
        code_num = c.split(".")[0] if "." in c else c
        prefix = code_num[:1]
        if prefix in ("6", "9"):
            suffix = ".SH"
        elif prefix in ("8", "4"):
            suffix = ".BJ"  # 北交所
        else:
            suffix = ".SZ"
        tdx_codes.append(f"{code_num}{suffix}")
    return tdx_codes
```

### T-06: Worker自动部署到外部目录（模块加载副作用）

**文件**: [bridge.py:56](app/tqsdk/bridge.py#L56)
**风险**: import即写外部文件系统，测试/单元环境会被污染

**问题定位**:
```python
# bridge.py 模块级
_ensure_worker_deployed()  # import bridge 时立即执行 shutil.copy2
```

任何 `from app.tqsdk.bridge import TdxBridge` 都会触发把worker脚本复制到 `E:\NEW_TDX\PYPlugins\user`。在CI/测试环境（无此目录或无权限）会报警告。

**修复方案**: 改为显式调用
```python
class TdxBridge:
    def __init__(self):
        _ensure_worker_deployed()  # 实例化时部署，而非import时
```

### T-07: subprocess无资源限制

**文件**: [bridge.py:251-258](app/tqsdk/bridge.py#L251-L258)
**风险**: 恶意/异常公式导致worker进程吃满内存/CPU，拖垮服务器
**影响**: 只有timeout(600s)限制时间，无内存/CPU限制

**修复方案**:
```python
# Windows用job object限制内存，Linux用resource.setrlimit
import resource  # Linux
def _run_worker(self, task, timeout_multiplier=1):
    # ...
    result = subprocess.run(
        ["python", str(WORKER_SCRIPT), "--args-file", args_path],
        cwd=str(TDX_USER_DIR), env=env,
        capture_output=True, text=True, timeout=timeout,
        # Linux: preexec_fn=lambda: resource.setrlimit(resource.RLIMIT_AS, (2*1024**3, 2*1024**3))  # 2GB
    )
```
