## 2. 架构/业务独立观点

### 2.1 [架构核心] 三大 xtquant 路径 的整合方案

新发现 §1.1 已指出 v5.0 文档对现有 QMT 基础设施完全失忆。这里给出**我推荐的整合方案**(与 v5.0 不同):

```
Docker 容器 (Linux Python 3.11)
  api-server(:8888) FastAPI 主进程
  ├─ sim_trader/engine.py
  │   └─ if BROKER_ENABLED: get_gateway() → QMTGateway → HTTP
  └─ api/sim_trader.py (WebSocket 推送 sim_trader_update)
      ↕ HTTP (host.docker.internal:8001)

Windows 宿主机 (Python 3.13)
  live_trader 主进程 (:8001, NSSM 守护)
  ├─ qmt_wrapper  ← 单进程独占 xtquant 共享内存
  ├─ FastAPI 路由:
  │   ├─ /live/quotes  (行情代理,替代旧 qmt_proxy:8081)
  │   ├─ /live/orders  (下单/撤单)
  │   ├─ /live/positions (持仓/资产)
  │   └─ /live/admin   (killSwitch / dry-run)
  ├─ callback_handler (7 callbacks, db_executor 派发)
  ├─ 6 service (trade/orders/deals/positions/assets)
  ├─ ConnectionManager (熔断 + WaitingFreeWriter 强退)
  ├─ ClearanceLock (内存默认 + Redis 预留)
  ├─ RiskGate (8 闸门)
  ├─ KillSwitch (三重状态)
  ├─ ExitMonitor (复用 exit_rules)
  ├─ PnlEngine (buildSimpleCycles 移植)
  ├─ Reconciler (4 时点对账)
  └─ audit / notify / schemas / exceptions

  qmt_proxy_server.py 保留源码, NSSM 不启动
  app/trader/gateways/qmt.py proxy_url 改为:
    http://host.docker.internal:8001/live/quotes
  (Docker 端 sim_trader 的行情来源切换到 live_trader)

  XtMiniQmt.exe (D:\Program Files\XCXT\bin.x64)
  userdata_mini (D:\Program Files\XCXT\userdata_mini)
```

**关键改动**:
- **复用** app/trader/gateways/qmt.py 的接口(buy/sell/get_balance/get_position/get_realtime_quotes),只改其 proxy_url 指向
- **复用** sim_trader/engine.py:608 的 if BROKER_ENABLED: get_gateway() 模式,live_trader 端调 qmt_wrapper 而非 HTTP 代理
- **复用** sim_trader/intraday_monitor.py:200 的盘中 tick 驱动,只换 gateway.sell 为 qmt_wrapper.sell
- **复用** core/event_engine.py 的 EVENT_TICK,live_trader 也注册同一个事件源
- **只新建** live_trader 独有的:qmt_wrapper (xtquant 直连) / callback_handler / 6 service / ConnectionManager / ClearanceLock / RiskGate / KillSwitch / PnlEngine / Reconciler / store / audit

**这与 v5.0 文档的差异**:
- v5.0 设计 26 个新文件 / ~7400 行;本方案约 18-20 个新文件 / ~5000 行
- v5.0 的 services/ 6 个服务在已有 app/trader/gateways/qmt.py 已有部分,可抽取到 qmt_wrapper 内作为私有方法
- bridge.py 复用现成 app/tqsdk/bridge.py(已有 TDX subprocess 选股能力)

**自检补充**:QMTGateway 是 live_trader 在 Docker 端的前端代理,其 proxy_url 指向 live_trader:8001/live/quotes;QMTGateway 不直接连 xtquant(由 live_trader 独占)。这与 v5.0 §3.2 live_trader 单进程独占 xtquant 的表述自洽。

### 2.2 [业务] buildSimpleCycles 移植应 渐进式 而非 一次性

v5.0 §5.8 计划移植 MQ buildSimpleCycles 盈亏闭环。但 sim_trader/engine.py:385 的 total_equity 是用加仓后均价算法计算的(简化版),**这两套算法的差异**:

| 算法 | 数据 | 复杂度 | 准确性 |
|------|------|--------|--------|
| 现行 total_equity 简单加仓 | 只看最新一笔买入价 × 股数 + 浮盈/亏 | O(1) | 多次加仓后均价不准 |
| MQ buildSimpleCycles 完整闭环 | 按 orderType=23/24 逐笔配对,加权重算 | O(N) | 多次加仓后均价准 |

**我的建议**:**不要一次性替换**。建议:
1. **阶段 0-1**: 现有 total_equity 不动,新增 live_cycles 表存 buildSimpleCycles 输出
2. **阶段 2**: 跑 1 周对比两套数据差异,确认无 bug
3. **阶段 3**: 切换为 buildSimpleCycles 为准,旧表作历史参考

**v5.0 文档缺失**:完全没讨论迁移期如何保持两套数据兼容。

### 2.3 [业务] dry-run 模式应支持 快照恢复, 而非 独立表隔离

v5.0 §16.2 修复:dry-run 模式写入独立表 live_orders_dryrun / live_deals_dryrun (与 live_orders / live_deals 物理隔离, 绝不混写)

**问题**:独立表方案有 3 个副作用:
1. 跑 dry-run 没法回放如果当时是 live 会怎样——live_orders_dryrun 的 order_id 是 mock,无法调 QMT query
2. 切到 live 后,live_orders 表是空的(从未被写入),重启后无状态可恢复
3. 验收 dry-run 期间 live_orders 行数=0 只是简单计数器,无法验证决策链正确

**我的建议**:
- 改用**开关 + 标记**模式,而不是**独立表**:
  - live_orders 一张表,加 mode 字段(live / dry-run)
  - dry-run 模式:走完整 7 个 callback,callback 把 mode=dry-run 传给 DB writer
  - 验收: SELECT COUNT(*) FROM live_orders WHERE mode=live 在 dry-run 期间 = 0
- 优势:
  - 同一表 schema 同一代码路径,验证覆盖度更高
  - dry-run 期间如果有 bug 在 callback 路径,直接产出现
  - 切到 live 后全空是无害的(本来 NSSM 重启后也应该重新初始化)

### 2.4 [业务] RiskGate 闸门 7 连续拒绝 5 次 → kill switch 应有 原因分类

v5.0 §5.6 闸门 7:
> 连续 5 单被拒→kill switch

**问题**:
- 被拒原因可能是 (a) 风控拒绝 (b) 资金不足 (c) 涨停封板 (d) 重复代码 等

### 2.6 [业务] Reconciler 不应回写 live_positions,应新增 live_positions_audit 表

### 2.7 [工程] DuckDB 高频 callback 写入的 buffer 策略应分两层

v5.0 审计报告 HIGH-2 提出 DuckDB 单写者问题,我的扩展建议:

**两层 buffer**:
- **L1 in-process queue**:collections.deque(maxlen=2000),所有 callback 写入这个 queue(< 100μs)
- **L2 thread pool flusher**:ThreadPoolExecutor(max_workers=1),每 100ms 排空一次 queue 并 INSERT 到 DuckDB
- **优势**:
  - callback 函数体只 put_nowait + return(< 10μs)
  - 1 个写者写 DuckDB,完全规避锁竞争
  - 崩溃时 queue 内的数据可选择落盘(tmp file)或丢弃(有 audit 表可补)

**v5.0 文档应明确选择哪种策略**,而不是 db_executor 串行化 含糊带过。
