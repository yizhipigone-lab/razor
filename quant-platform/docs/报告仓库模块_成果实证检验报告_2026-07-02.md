## 三、实证新发现：文档未提及的 2 项风险

> 这两项不在三份文档的任何一张缺陷表里，是实证过程中现场复现出来的。

### 3.1 🟠 HIGH — agents 模块循环依赖，单独导入即崩

**复现**（venv313 真实环境）：

```
$ venv313/Scripts/python.exe -c "from app.api import agents"
  File "main.py", line 147, in <module>
    app.include_router(agents.router)
AttributeError: partially initialized module 'app.api.agents' has no attribute 'router'
(most likely due to a circular import)
```

**根因**：`agents.py:17` 写了 `from main import limiter`。当 agents 被单独首次导入时，触发 main.py 加载，main.py 执行到 `app.include_router(agents.router)`（line 147）时，agents 模块尚未完成初始化（`router` 还没挂上），于是崩溃。

**为什么正常启动不崩**：`python main.py` 路径下 main 先加载，到 line 81 `limiter` 已定义，line 147 才触发 agents 首次导入；此时 agents 里 `from main import limiter` 能拿到已部分初始化的 main（limiter 已就绪），故正常启动 OK（实测 `import main` 成功）。

**影响**：
- 任何针对 `agents` 模块的单元测试 / 独立 import 会直接失败，可测试性受损。
- 成果报告 5.1 表里没列"单独导入 agents"，所以严格说不算造假，但"模块导入验证全部 ✅"的口径掩盖了这一缺陷。
- 这是 P1-4 引入 slowapi 时的连带设计问题：为了复用全局 limiter 单例而 `from main import limiter`，制造了 main ↔ agents 的环。

**建议**：把 limiter 抽到一个无依赖的小模块（如 `core/limiter.py`），main 与 agents 都从它导入，打破环。

### 3.2 🟠 HIGH — slowapi 未登记到 requirements，新环境部署会缺失

**实证**：
- `requirements*.txt` / `pyproject.toml` 中 grep `slowapi` 均无结果。
- venv313 里已 `pip install`（实测可 import），但依赖未落盘到依赖清单。

**影响**：
- 当前开发机/生产机能跑（venv313 有装），但任何人重建虚拟环境、新机器部署、CI 流水线都会缺这个包，复现 3.1 之前的"启动即 ModuleNotFoundError"。
- 这正是本检验初稿误判的根源：我用全局 python（无 slowapi）测试，得到"崩溃"结论；切到 venv313（有 slowapi）才正常。环境差异本身就是部署不健壮的证据。

**建议**：把 `slowapi` 加入 `requirements.txt` 并锁定版本。

### 3.3 两项风险的关系

3.1 和 3.2 同源——都源自 P1-4 速率限制的落地方式。装了 slowapi 的环境下 3.2 隐而不发，但 3.1 的循环依赖仍在；缺 slowapi 的环境下 3.2 直接变成启动崩溃。两者都应在合并前修复。
