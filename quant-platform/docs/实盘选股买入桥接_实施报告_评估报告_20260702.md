### 漏洞 A: 同股重复信号 = 全部幂等 — ✅ 通过（有小瑕疵）

| 项目 | 详情 |

| 报告声称 | buy-signal 端点内部去重，保留第一条 |
| 代码实况 | [main.py:802-811](app/live_trader/main.py#L802-L811)，`seen_codes = set()` + `unique_signals = []` |

| **瑕疵** | 去重 key 用的是原始 `s.code`，而非 `format_code(s.code)`。如果同批信号中同股出现两种格式（如 `600000` 和 `600000.SH`），不会被去重。当前 Docker 端 `cron_jobs.py:569` 已统一 `format_code` 后发送，所以**单批次内不会触发**，但属于防御性缺陷 |

### 漏洞 C: Docker 不解析响应 = 状态错乱 — ✅ 通过（有边界缺陷）

| 项目 | 详情 |
|------|------|
| 报告声称 | 转发函数解析 resp.json() 的 accepted/rejected，按 code 标记状态 |
| 代码实况 | [cron_jobs.py:611-649](app/scheduler/cron_jobs.py#L611-L649) |
| 401 处理 | ✅ 显式处理 |
| JSON 解析失败 | ✅ 显式处理 |
| accepted/rejected 解析 | ✅ 正确标记 acked/rejected/unknown |
| **边界缺陷** | 非 200、非 401 的状态码（如 403/503/500）未显式处理。如果 FastAPI 返回 `{"detail": "QMT 未连接"}` 的 503 响应，代码会解析 JSON 成功但找不到 `accepted`/`rejected` 字段，所有信号标记为 `unknown`，最终被归类为 `all_rejected`。**运维人员无法区分"信号被风控拒绝"和"live_trader 服务不可用"** |

**建议**: 在 JSON 解析前加 `if resp.status_code != 200` 分支，记录 HTTP 状态码和响应体。

### 漏洞 E: 14:55 误拒 — ✅ 通过（但有时序设计矛盾）

| 项目 | 详情 |
|------|------|
| 报告声称 | 14:55-14:57 五档即成即撤，14:57-14:59 对手最优，14:59+ 拒收 |
| Windows 端 | ✅ 三档价格策略实现正确：[main.py:721-729](app/live_trader/main.py#L721-L729) |
| Windows 截止 | ✅ `buy_signal_cutoff = "14:59"` 后拒收 |
| Docker 端 | ⚠️ **≥14:55 直接存 pending 不发**: [cron_jobs.py:549](app/scheduler/cron_jobs.py#L549) |
| 价格类型常量 | ✅ 42(沪市五档)/47(深市五档)/44(对手方最优) 均正确 |

**设计矛盾**: Docker 端在 14:55 就停止转发，导致 Windows 端的 14:55-14:59 时间分段策略**在正常流程中永远不会触发**。只有通过其他路径（如手动调用 API）才可能到达这些分支。Windows 端的三档策略变成了"死代码"。

这不是 bug（双保险），但是一个**设计不一致**: 要么 Docker 端也应该放宽到 14:59 前继续转发（让 Windows 端的三档策略真正生效），要么干脆删掉 Windows 端的 14:55-14:59 分段逻辑（因为到不了）。

**建议**: 两种选择 — ① Docker 端也改为 14:59 截止，让 Windows 三档策略生效；② 保持现状但在文档中明确说明"Docker 14:55 截止是唯一有效闸门，Windows 三档策略仅作手动 API 的兜底"。

### 4.2 🟠 HIGH: time.sleep 阻塞事件循环 — Semaphore(3) 并发名存实亡

| 项目 | 详情 |
|------|------|
| 文件 | [clearance_lock.py:59-66](app/live_trader/clearance_lock.py#L59-L66) |
| 问题 | `acquire_with_wait` 使用 `time.sleep(0.5)` 循环等待，而调用链是 `_process_one_signal`(async) → `place_order_service`(sync) → `acquire_with_wait`(sync) |
| 影响 | 一旦锁冲突，整个 asyncio 事件循环被阻塞（0.5s/次，最长 5s），所有其他路由、WebSocket、心跳全部冻结。Semaphore(3) 的并发效果被 `time.sleep` 完全抵消 |
| 修复建议 | ① 将 `place_order_service` 调用包装在 `asyncio.to_thread()` 中；② 或将 `acquire_with_wait` 改为 async 版本用 `await asyncio.sleep()` |
