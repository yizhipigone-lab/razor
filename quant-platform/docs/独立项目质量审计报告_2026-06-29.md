## 5. 维度二：架构与模块化

### 5.1 评级：4/10

### 5.2 🔴 CRITICAL 问题

#### 5.2.1 风控参数三处真相源（数值不一致）

| 位置 | 字段 | 值 | 格式 |
|---|---|---|---|
| `config/app_setting.json:23` | `risk.hard_stop_loss_pct` | `-4.6` | 百分比（-4.6%） |
| `config/app_setting.json:146` | `backtest.hard_stop` | `-0.046` | 小数 |
| `app/sim_trader/config.py:17` | `HARD_STOP` | `-0.06` | 小数（-6%） |
| `config/app_setting.json:24-33` | `risk.take_profit_tiers` | 完整数组 | — |
| `config/app_setting.json:147-156` | `backtest.take_profit_tiers` | **完全相同但独立复制** | — |

**后果**：
- 改 `risk` 段的止损，`backtest` 段不会跟着变 → 前端面板改了风险参数，回测跑的仍是旧值
- `sim_trader/config.py` 的 -6% 与 config 的 -4.6% 是不同的止损线 → 模拟盘和回测的止损规则不一致
- `take_profit_tiers` 复制了两份完全相同的数组 → 违反 DRY 原则，一改漏改

**代码证据（`core/settings.py` 读取链）**：
```python
# settings.py:115-120 读取 priority 决定哪个源胜出
# 三处源的读取顺序不同导致跑批口径漂移
```

**修复建议**：
1. 删 `backtest.hard_stop` 和 `backtest.take_profit_tiers`，回测直接读 `risk.*`
2. `sim_trader/config.py` 改为从 `settings.get('risk')` 动态读取
3. `settings.py` 加一致性断言：风险参数只能有一处定义

#### 5.2.2 Engine.py 成本率旁路（执行层未统一）

`app/backtest/engine.py` 的 `_simulate_trade_v2` 和 `_simulate_trade_daily_fallback` 使用类内 `TRADE_COST_BUY/SELL` 常量计算成本，而不是调用 `execution.py` 中的 `calc_buy_cost/calc_sell_revenue`。

**代码证据**：
```python
# engine.py:24 — import 了但没在所有路径用
from app.backtest.execution import calc_buy_cost, calc_sell_revenue

# engine.py:657 — _simulate_trade_v2 仍用类内常量
cost_entry = entry_price * (1 + self.TRADE_COST_BUY / 100)  # ← 0.125%

# engine.py:881 — daily_fallback 同上
```

**影响**：
- engine 路径的成本率不从 config 读 → 改配置不生效
- 不经过 `calc_buy_cost` → 无法体现 `min_commission`（5元最低）
- `scripts/run_backtest.py`（统一 CLI）底层走 engine → 78 公式批量回测的真实成本口径不是配置里设置的值

> **注**：最新 commit `15df6c9` 已加 `_cost_rates()` 从 execution 派生，但仍有 fallback 到类常量的路径，且注释自承"比例口径无法体现 min_commission"。

#### 5.2.3 API 层与业务层循环依赖

```
app/api/sim_trader.py  ────imports───→  app/sim_trader/engine.py   (正常: API→业务)
app/sim_trader/engine.py ──lazy import─→ app/api/sim_trader         (反向: 业务→API)
app/sim_trader/intraday_monitor.py ──lazy─→ app/api/sim_trader      (反向: 业务→API)
```

**严重度**：🟠 HIGH — 模块加载顺序依赖 `lazy import` 这一脆弱的运行时约定，任何重构都可能触发循环 ImportError。

## 6. 维度三：安全与异常处理

### 6.1 评级：3/10

> **重要前提**：`PROJECT_RULES.md §6` 声明本项目为"个人本地单机使用，不对公网开放"，并豁免了部分网络攻击面。然而本报告从**业界最佳实践**角度仍将其列为风险项——因为"单机"不等于"以后永远不联网"，且部分问题即使在单机环境下也影响数据完整性。

### 6.2 🔴 CRITICAL 安全漏洞（5 项）

#### CVE-1：用户代码远程执行（RCE）

**位置**：`app/strategy_factory/engine.py:112`

```python
exec(code_content, local_vars)
```

**攻击面**：`POST /api/factory/save_physical_strategy` 接受用户提交的 Python 代码，直接 `exec()` 执行。

**排查**：
- `validate_strategy_code()` 函数**不存在于 strategy_factory/engine.py**
- `ast_sandbox.py`（`app/utils/ast_sandbox.py`）存在但**未在用户上传路径被调用**
- 任何能访问 `localhost:8888` 的人（局域网内任何设备）可以执行 `os.system('del /F /S /Q C:\\*')` 或更危险的命令

**严重度**：🔴 CRITICAL — RCE = 服务器沦陷

**修复方案**：
1. 用 `RestrictedPython` 或自定义 AST 白名单沙箱（已有 `ast_sandbox.py` 但没用上）
2. 禁止 `import`、`__builtins__`、`os`/`sys`/`subprocess`/`eval`/`exec`/`open`
3. 策略代码以模块文件落盘后 safety-check 再 import（而非直接 exec）

#### CVE-2：API 返回明文密钥

**位置**：`app/api/system.py:79-89`

```python
keys["tushare_key"] = v    # 明文
keys["deepseek_key"] = v   # 明文
# 同时也返回 masked 版本，但明文字段同样在 JSON 响应中
```

**攻击面**：`GET /api/settings/env-keys` 直接返回完整 API key

**严重度**：🔴 CRITICAL — 访问 API 的任何人都能拿到 Tushare/DeepSeek 密钥

**修复**：删明文字段，仅返回 masked 版本。

#### CVE-3：QMT Proxy 全网监听 + 无认证

**位置**：`qmt_proxy_server.py:486`

```python
uvicorn.run(app, host="0.0.0.0", port=8081)
```

**问题**：
- 绑定 `0.0.0.0`（全网监听），而非 `127.0.0.1`（仅本机）
- `/api/order` 端点**无任何 token/认证** → 任何人可向券商发起真实委托
- `ACCOUNT_ID` 硬编码 `1010303391`（真实账号）

**严重度**：🔴 CRITICAL — 实盘资金安全受到威胁

**修复**：改 `host="127.0.0.1"` + 加 token 鉴权。

#### CVE-4：CORS 全开 + allow_credentials

**位置**：`main.py:58-64`

```python
allow_origins=["*"],
allow_credentials=True,
```

**问题**：按 Fetch 标准，`allow_credentials=True` 与 `allow_origins=["*"]` 不可共存——Chrome 会拦截，但其他浏览器/工具可能不拦截。结合 `env-keys` 返回明文密钥，风险放大。

**严重度**：🔴 CRITICAL — 符合 OWASP Top 10 A01:2021

#### CVE-5：Tushare Token 已泄露到 Git 历史

**位置**：
- `_deprecated/test_tushare.py:7` — 硬编码真实 token
- `_deprecated/test_token_power.py:5` — 同上
- `.env` 文件已在 Git 历史中

**严重度**：🔴 CRITICAL — token 一旦被泄露，无法通过本地删除修复（需在 Tushare 控制台 rotate）

### 6.3 🟠 HIGH 问题

#### 6.3.1 静默吞异常（74 处，覆盖 26 文件）

这是全项目**最普遍的代码质量问题**。抽样列举最危险的几处：

### 6.5 PROJECT_RULES.md §6 豁免声明评估

`PROJECT_RULES.md §6` 明确声明了"安全维度审计豁免范围"（无鉴权/CORS/QMT Proxy/明文密钥等为"已知可接受风险"），本报告理解这一前提但仍独立记录上述安全问题——**因为"单机"不等于"永远安全"**：

1. `host="0.0.0.0"` 意味着服务对局域网开放——局域网内不一定只有操作者本人
2. `.env` 密钥一旦泄露到 Git 历史——删除本地文件无法消除风险
3. RCE（`exec`）即使在单机环境也是严重的安全实践缺陷——操作者本人也可能无意中粘贴恶意代码

**本报告的立场**：在报告正文中如实记录，在综合评分中将"已被 PROJECT_RULES 豁免"的项（CORS/无鉴权/无Rate Limiting）从安全评分中降权，但 RCE 和密钥泄露维持原评级。

## 8. 维度五：性能与数据流

### 8.1 评级：5/10

### 8.2 🔴 已修复：信号循环 O(N×M) 瓶颈（commit `ecd8c86`）

**原问题**：`engine.py:265,275` 在每条信号的循环内执行 `bars[bars["code"] == code]` 全表过滤。

```
5000股 × 2500信号 = 12.5M 行扫描 → 占 78 公式 6h+ 总耗时的 ~40%
```

**修复后**：循环外 `bars_grouped = dict(tuple(df.groupby("code")))` → 循环内 O(1) 查表。

**验证**：已查看 diff 确认修复正确实现。✅

### 8.3 🔴 已修复：DuckDB read_only 开关（commit `15df6c9`）

**原问题**：`duckdb_manager.py:99` 默认读写连接，导致"基线 diff 脚本与运行中服务争用 DB"

**修复后**：环境变量 `DUCKDB_READ_ONLY=1` 控制只读连接。✅

### 8.4 🟠 仍存：TDX 模式 trial 重复启动子进程

**位置**：`ai_optimizer.py:451-489` + `bridge.py:236-280`

每次 Optuna trial 调用 `run_tdx_backtest()` → subprocess + TdxBridge worker 重新计算**与参数无关的信号**。50 次 trial = 50 次完整 worker 调用。Python 模式已有 `_cached_signals` 缓存，TDX 模式缺失同样缓存。

**粗估影响**：TDX 模式单 trial 10s → 100s；50 trial 额外耗时 ~80 分钟。
