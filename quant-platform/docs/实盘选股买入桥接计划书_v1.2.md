## 2. 设计:Docker 选股 + HTTP 转发 + 实盘风控真下单

```
Docker(14:52)                          Windows(8001)
─────────────                          ─────────────
cron 14:52 → TdxBridge.execute_screen()
   → matched [code] (只有代码)
   → snapshot.get(close) 拿价
   → engine.execute_buy()(模拟盘照常)
   → LIVE_SIGNAL_MODE in [sim_and_live] 才转发
   → _forward_signals_to_live_trader():
        ├─【新】探活 GET /live/health(超时 1s)
        │  失败 → 持久化信号 + 告警 + 跳过本批次
        ├─ 构造 BuySignalRequest(含 code, price, source="TDX")
        ├─ POST /live/buy-signal
        │     Header: Authorization: Bearer <token>
        │     Body: { signals, strategy, source }
        └─【新】失败 → 重试 1 次(2s 内完成)
                                        → /live/buy-signal 端点
                                        → 鉴权(token 校验)
                                        → 逐个 signal:
                                           ├─ Windows 自己查 QMT 实时价(覆盖 Docker 价)
                                           ├─ 幂等键 MD5("buy_signal"|code|date)
                                           ├─ 同股冷却 20 天
                                           ├─ 闸门 10 在闸门 1 之前检查
                                           ├─ RiskGate 9 闸门 + 闸门 10
                                           ├─ ClearanceLock 排队 30s × 3 次
                                           ├─ _calc_buy_volume() 板块取整
                                           ├─ price_type=42/47(五档即成即撤)
                                           └─ qmt 真下单 → callback → 成交
```

**时序保证**(评审问题 7.5): 探活 1s + 重试 1 次 + Windows 处理 ≤ 5s = **总 ≤ 8s**,远小于尾盘 3 分钟窗口。超过 8s 立即放弃 + 告警,不再重试。

**暂停信号联动**(评审问题 7.7): Docker 端转发时检查 `engine.pause_until`,暂停期间直接跳过转发(实盘不感知模拟盘暂停状态,各自负责)。

## 3. 双重开关(评审问题 7.1 解决)

| 字段 | 位置 | 作用 | 默认 |
|------|------|------|------|
| `AUTO_BUY` (保留) | `sim_trader/config.py` | 控制模拟盘**是否执行模拟买入** | True |
| `LIVE_SIGNAL_MODE` (新增) | `app_setting.json` `live_trader.live_signal_mode` | 控制**是否转发到实盘** | `off` |

**组合语义**:
- `AUTO_BUY=False` + 任何 LIVE_SIGNAL_MODE → 模拟盘不买,实盘也没信号
- `AUTO_BUY=True` + `LIVE_SIGNAL_MODE=off` → 模拟盘买,实盘不转发
- `AUTO_BUY=True` + `LIVE_SIGNAL_MODE=sim_only` → 模拟盘买(等同 off,但显式声明)
- `AUTO_BUY=True` + `LIVE_SIGNAL_MODE=sim_and_live` → 模拟盘买 + 实盘真买

**前端/ API 兼容性**(评审 7.1 解决):
- 前端 set-auto-buy 控件照常工作(只控制 AUTO_BUY)
- 单独加一个"实盘信号转发"开关控件,写入 `LIVE_SIGNAL_MODE`
- `/api/settings/sim-switches` 端点增加 `live_signal_mode` 字段(向后兼容,旧客户端不传则保持原值)

## 10. v1.2.1 修订(二轮评审 8 条新问题)

> v1.2 整体可作为实施基础,但二轮评审挖出 4 条 P1 中等 + 4 条 P2 低风险问题。本节全部回应,正文已不重复改动(以本文 §10 为准)。

### 10.1 [P1] buy-signal 批量串行 + 清仓锁排队 = 尾盘窗口爆炸

**评审原文**:"5 只信号全部错过尾盘窗口。如果第 1 只信号被清仓锁阻塞 30s,第 5 只下完单就到 14:55:02 了"

**修复**(§2 流程图 + §5.2 端点):
- buy-signal 端点**内部并发**处理多个信号:`asyncio.gather` + `asyncio.Semaphore(3)`(并发度 3)
- **清仓锁冲突策略分场景**:
  - **buy-signal 批量(尾盘,时间紧)**:锁冲突只等 **5s**,不成立即跳过 + 写 audit + 告警"信号 X 跳过:清仓锁冲突"
  - **手动 /live/order 单笔(不急)**:保留 30s × 3 次排队
- **place_order_service** 接收 `lock_wait_sec` 参数,batch 模式传 5,manual 模式传 30
- **并发度 3 的依据**:QMT 共享内存同时 3 个订阅/下单不触发 WaitingFreeWriter(MQ 实证,>3 高频易出问题)
- **总时间保证**:5 只信号 × (5s 锁等 + 3s 下单) / 3 并发 = ~13s,远小于尾盘 3 分钟窗口

**实施代码示意**:
```python
async def buy_signal_endpoint(req):
    semaphore = asyncio.Semaphore(3)
    tasks = [_process_one_signal(s, semaphore, lock_wait_sec=5) for s in req.signals]
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return {"accepted": ..., "rejected": ..., "details": ...}

async def _process_one_signal(signal, semaphore, lock_wait_sec):
    async with semaphore:
        return await place_order_service(signal, lock_wait_sec=lock_wait_sec, source="TDX")
```

### 10.2 [P1] cooldown 数据源不一致

**评审原文**:"闸门 10 检查 live_positions.entry_date,但同股冷却应该看'最近卖出日'才能避免今天卖明天又买"

**修复**(§5.2 RiskGate 闸门 10):
- **数据源改为 live_deals**(最近 20 天的 sell 记录),不只查 entry_date
- 闸门 10 逻辑:查 `live_deals` 表,如果有同 code 的 `direction='sell' AND traded_at > today - 20day` → 拒
- 同时保留 `live_positions.volume=0` 但 `entry_date` 在 20 天内的检查(防止"已清仓但还该冷却")
- **实现位置**:`risk_gate.py` 新增 `_check_same_stock_cooldown(code)`,复用 `store.get_deals(code, limit=20)`

### 10.3 [P1] place_order_service 边界语义不清

**评审原文**:"手动 /live/order 和 buy-signal 调用同一个 service,但 buy-signal 走批量并发 + lock_wait=5,手动走串行 + lock_wait=30。service 需要区分场景"

**修复**(§5.1 service 设计):
- service 函数签名标准化:`place_order_service(intent, source="WEB", lock_wait_sec=30)`
- **source 参数决定价格/日志/审计标记**:
  - `source="WEB"`:手动端点调用,价格用客户端传的 price,terminal="WEB"
  - `source="TDX"`:buy-signal 端点调用,**先查 QMT 实时价覆盖** Docker 价格,terminal="TDX"
  - `source="SCHEDULER"`:ExitMonitor 调用,用于将来扩展
- **lock_wait_sec 由调用方传**:
  - 手动端点:`lock_wait_sec=30`(不急,等满)
  - buy-signal 端点:`lock_wait_sec=5`(尾盘,短等)
  - 未来 scheduler 可传 `lock_wait_sec=10`
- 拒绝"内部默认 30s"的隐式行为,所有调用方显式传

### 10.4 [P1] pending_signals.json 和 forwarded_today.json 状态不同步

**评审原文**:"Docker 端重试失败的信号存 pending_signals.json,但 buy-signal 已收到的可能在 forwarded_today.json。两个文件分别维护,可能出现:pending 已重试成功但 forwarded 没记录,或者 forwarded 记了但其实 buy-signal 没真收到"

**修复**(§5.4 持久化):
- **合并为一个状态机**,单一文件 `data/live_trader/signal_state.json`:
  ```json
  {
    "2026-07-03": {
      "signals": [
        {"code": "000001.SZ", "price": 10.27, "ts": "14:52:01",
         "status": "sent" | "acked" | "failed" | "skipped",
         "result": {"order_id": ..., "reject_reason": ...}}
      ],
      "last_heartbeat_at": "14:52:05"
    }
  }
  ```
- 状态转换:`pending → sent → acked`(收到 buy-signal 200 响应) → (执行结果 via GET /pending 拉取) → filled/rejected
- **失败状态保留**:`failed` 不删除,审计可查,当日 15:00 统一清理
- **Windows 端不需存储此文件**(只接 POST,响应里返回 accepted 列表);Docker 端单文件全状态

### 10.5 [P2] 闸门 10 只在 buy 方向生效

**评审原文**:"闸门 10 描述说'闸门 8 一样任意方向',但同股冷却是买入概念,卖出为什么也要拦?"

### 10.7 [P2] signal_state.json 并发写文件风险

- 读策略:每次读完整文件,捕获 JSONDecodeError 时回退到空状态(不阻塞主流程)

```python
_state_lock = threading.Lock()
def _atomic_write_json(path, data):
    with _state_lock:
        tmp = path + ".tmp"
        with open(tmp, "w", encoding="utf-8") as f:
            json.dump(data, f, ensure_ascii=False, default=str)
        os.replace(tmp, path)  # 原子替换
```

## 11. v1.2.2 修订(审计自检 6 条新漏洞)

> v1.2.1 整体可作为实施基础,但以审计架构师身份自检后挖出 3 P0 + 3 P1 漏洞,**不修会导致核心功能失效或资金损失**。本节全部回应,实施以本文 §11 为准。

### 11.1 [P0-A] 同股重复信号 = 全部幂等命中 = 一只都下不了单

**漏洞**:"5 只信号"可能包含重复 code(如 `["600000.SH", "600000.SH", "000001.SZ", "000001.SZ", "000001.SZ"]`),同股同日的幂等键相同 → 第 2 只起全部命中幂等 → 0 笔成交。

**修复**(§5.2 buy-signal 端点):
- **端点内部先去重**:`unique_signals = {s.code: s for s in req.signals}.values()`
- 去重时**保留第一条**(最早到达,价格最新)
- 单测:`test_buy_signal_dedup_keeps_first`(3 个 600000.SH → 只下 1 单)

### 11.2 [P0-B] code 格式不一致 = 同股冷却失效 = 资金风险

**漏洞**:QMT 报 `600000`,Docker 推 `600000.SH`,闸门 10 查 `live_deals WHERE code='600000'` 查不到 → 放行 → 违反 20 天冷却 → 重复买卖同一只。

**修复**(§5.2 RiskGate 闸门 10):
- **闸门 10 入口**统一 `from app.utils.xtquant_compat import format_code; code = format_code(input_code)`
- 同时**检查两端**:不仅查 `live_deals`,还查 `live_positions`,任何 code 格式变体都覆盖
- 实施时**所有 code 入库前**在 `store.upsert_*` 入口统一 `format_code()`(防止后续其他查询也有同样问题)
- 单测:`test_gate10_cooldown_normalizes_code`("600000" 卖出 → "600000.SH" 买入应被拒)

### 11.3 [P0-C] Docker 端不解析 Windows 响应 = 状态机错乱 = 重复下单

**漏洞**:Windows 端响应 `{accepted: [600000], rejected: []}`,但 Docker 端没解析就直接写 `status=sent`,无法区分"已 ack"还是"被实盘拒了",失败重试机制失效 = 重复下单。

**修复**(§5.4 Docker 状态机 + §5.3 转发逻辑):
- **转发函数必须解析响应**:
  ```python
  resp = requests.post(...).json()
  for sig in signals:
      if sig.code in resp["accepted"]:
          state["status"] = "acked"
      elif sig.code in resp["rejected"]:
          state["status"] = "rejected"
          state["reject_reason"] = resp["details"][...]["reason"]
  ```
- **响应里必须返回**每个信号的 accepted/rejected 状态(不在端点层只给汇总)
- 单测:`test_docker_parse_response`(mock Windows 返回,验证状态机正确更新)

### 11.4 [P1-D] place_order_service 不等 callback = 时序假设

**漏洞**:buy-signal 端点调用 service,service 内调 `qmt.order_stock_async()`。如果 service 同步等 callback 回报,**单只可能 5-10s**(订单提交 + 状态回报 + 成交回报),3 并发 × 10s = 30s,**接近 14:55 死线**。

**修复**(§5.1 service 设计):
- **service 不等 callback**:`order_stock_async` 返回 seq 后立即写 `live_orders` + 返回响应
- callback 由 `CallbackHandler` 异步处理(`_handle_order_update` / `_handle_trade`),写 `live_orders` 状态变更
- 端点响应 = "submitted" 而非 "filled"
- 验证:`test_service_no_callback_blocking`(用 mock qmt 测 5s 内必须返回)

### 11.5 [P1-E] 14:55 语义模糊 = 误拒 5 只信号

**漏洞**:v1.2.1 §10.8 说"14:55 后拒收",但 14:55 是常态时间点(5 只信号可能在 14:55:00-14:55:30 集中到达)。原 v5.4 设计 `no_new_order_after="14:55"` 意思是"只撤不挂限价单,但仍可挂市价单(42/47)",14:57 才是"强制市价"。如果 buy-signal 端点 14:55 拒收,会**误杀所有尾盘中段信号**。

**修复**(§2 流程图 + §10.8):
- **buy-signal 端点时点策略**:
  - 14:55-14:57:**仍接**,但强制用五档即成即撤(`price_type=42/47`),不限价
  - 14:57-14:59:**仍接**,但用 `MARKET_PEER_PRICE_FIRST`(44)对手最优价
  - **14:59 后**才拒收
- 时点参数化:`live_trader.buy_signal_cutoff`(默认 "14:59")
- 单测:`test_buy_signal_1455_to_1457_accepts_with_market_price`

### 11.6 [P1-F] service volume 参数契约不明确 = /live/order 与 buy-signal 互不兼容

**漏洞**:service 提取后,/live/order 调它传 `volume=100`(手动),buy-signal 调它传 `volume=0`(让 service 算)。如果 service 默认行为不一致,**手动端点行为突变**或**buy-signal 永远按 0 处理**。

**修复**(§5.1 service 签名):
- 明确:`place_order_service(intent, volume: int = 0)`,0 = service 内部 `_calc_buy_volume()`
- service 内部判断:
  ```python
  if intent.volume > 0:
      actual_volume = intent.volume  # 调用方已算好
  else:
      actual_volume = _calc_buy_volume(intent.code, intent.amount, intent.price)
  ```
- `intent.amount`(可选) = 期望买入金额(buy-signal 模式传),`intent.volume` > 0 = 直接股数
- /live/order 端点构造 intent 时设 `volume=user_input, amount=0`
- buy-signal 端点构造 intent 时设 `volume=0, amount=position_size`
- 单测:`test_service_volume_precedence`(传 volume=100 → 100;传 volume=0+amount=1000 → 算出来)
