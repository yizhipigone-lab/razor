影响分析：

第1项（dryrun残留清理重写）是安全关键代码——直接影响实盘启动时是否自动删除持仓。旧逻辑在 QMT 查询抖动时会误删真实持仓；新逻辑保守但会触发 Kill Switch 导致交易完全停止。这个变更必须在报告中明确说明。
第2项（Redis降级层）改变了整个应用的数据缓存行为——所有依赖 Redis 的功能（热度计算、信号发布等）在 Redis 不可用时会静默降级到进程内缓存，多 worker 间数据将不一致。
第3-5项是基础设施迁移，硬切换意味着任何还依赖旧端口/路径的环境会立刻出错。
审计结论: 报告对该 commit 的描述严重失实。23处注释纠正+4处默认值修复只占该 commit 变更的约 30%。剩余 70% 是未披露的功能性变更，包含两项安全关键改动。

三、🟠 HIGH 级别发现
HIGH-1: Redis 降级层存在语义不一致
问题	说明
hset TTL 硬编码 86400s	Redis 原生 HSET 无 TTL，内存缓存的 hset 固定 24h 过期。语义不对等
keys() 用 fnmatch 匹配	Redis KEYS 支持 */?/[]，fnmatch 支持范围更广（如 [a-z]），结果可能不一致
redis_client 从 eager 改 lazy	旧代码 redis_client = redis_manager.get_client()（import 时连接），新代码 redis_client = None。任何直接 from core.redis_manager import redis_client 后使用它的代码会 AttributeError
publish_signal 静默吞错	旧代码 log.error，新代码 log.debug——信号发布失败从"告警"降为"静默"，可能导致行情推送丢失不被察觉
HIGH-2: 实盘残留清理的安全模型反转未被充分评估
旧逻辑：发现残留 → 删除 → 通知
新逻辑：发现残留 → 不删除 → 激活 Kill Switch → 停止所有交易

这是正确的安全方向（防止误删真实持仓），但极端场景下：如果 QMT 连续 3 次返回空结果（xtquant 缓存问题），而本地有真实持仓，Kill Switch 会自动激活，交易系统完全停止。需要有：

Kill Switch 自动恢复机制（如 5 分钟后自动解除）
或者 QMT 查询重试次数可配置
或者管理员通知+手动恢复的工作流
HIGH-3: 端口/路径迁移是硬切换
data_sync.py 和 qmt_index_sync.py 从 qmt_proxy:8081/api/ 迁移到 live_trader:8001/live/，没有回退路径。如果 8001 端口上的 /live/sync/intra 或 /live/sync/index_daily 端点不存在或行为不同，同步请求会静默失败。
