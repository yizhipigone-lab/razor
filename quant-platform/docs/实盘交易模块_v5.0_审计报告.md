## 二、发现的问题（按严重度排列）

### [HIGH-1] sell_phase 时点与实际代码不一致

**文档声称**（开发书 §3.3、§7.3、研究基础 §6.3）：sim_trader 的卖出时间是 **14:52**

**实际代码**（[app/sim_trader/config.py:50](app/sim_trader/config.py#L50)）：

```python
SELL_TIME = "14:53"   # 止盈止损卖出时间
```

而 engine.py 第 4 行注释写的是 "14:52"，与 config 的 14:53 不一致。文档沿用了注释里的 14:52，但实际生效值是 config 里的 14:53。

**影响**：v5.0 §16.3 把实盘 sell_phase 提前到 **14:50**（留 10 分钟执行 ack 轮询），这个决策是合理的。但如果基线是 14:53 而不是 14:52，那窗口是 14:50→15:00 = 10 分钟，仍然够。所以影响不大，但**引用基线需要修正**。

**建议**：文档中所有 "14:52" 改为 "14:53"，或者在 §16.3 中注明"sim_trader 当前配置为 14:53"。

---

### [HIGH-2] DuckDB 作为高频回调写入存储的风险未讨论

**问题**：DuckDB 是**单写者模型**（single-writer, multiple-reader）。实盘环境下，xtquant 的 7 个 callback 可能在数秒内密集触发（例如一次批量成交产生多个 `on_stock_trade`），加上对账/监控等定时写入，会产生 DB 写锁竞争。

文档在 §6 和 §3.3 提到的 "独立 DB 文件避免与模拟盘写竞争" 是正确的，但这只是隔离了模拟盘的写入，没有解决实盘自身多 callback 并发写的问题。

**对比**：MQ 用 MySQL（支持行级锁+多写者），p9 用 DuckDB（OLAP 引擎，设计场景是低频追加写 + 高频分析读），两者写入模式不同。MQ 能用 `requests.post` 做 callback HTTP 推送 + x-server 统一写入 MySQL，但 p9 的单进程方案是所有 callback 直接写 DuckDB。

**建议**：
- 在文档 §6 中增加"写竞争与缓冲"段落，说明：7 个 callback 通过 `db_executor`（max_workers=4 的有界线程池）串行化后写入，确保同一时刻只有 1 个线程在写 DuckDB
- 或考虑在 callback 阶段只写内存 buffer（`collections.deque`），由一个定时 flusher（每秒/每 5 秒）批量写入

---

### [HIGH-3] 进程崩溃后的订单状态恢复逻辑描述不足

**文档 §12 "应急与运维"** 提到：
> "进程崩溃 → NSSM 自动拉起，启动时从 live_orders 恢复在途订单状态"

但没有说明**怎么恢复**。核心问题是：进程崩溃后（比如 `os._exit(1)`），已经通过 QMT 柜台挂出的在途订单可能在这段时间内已经成交/撤单/废单了。只读 `live_orders` 表会拿到**过时状态**。

**应该做的事**：
1. 重启后先调 `query_stock_orders(account, cancelable_only=False)` 从 QMT 获取最新订单状态
2. 用 QMT 返回的状态**覆盖** `live_orders` 中的终态字段
3. 对状态已变化的订单，补写 callback 逻辑（例如已成交的需要 INSERT `live_deals` + release 清仓锁）
4. 启动时输出一份"状态恢复报告"（audit 表记录：哪些订单状态变了）

**建议**：在文档 §5.2 或 §12 中新增"启动恢复流程"小节。

### [MED-2] Kill Switch + NSSM 重启的潜在死循环

**场景**：
1. QMT 断连 → `on_disconnected` 触发 kill switch → NSSM 重启进程
2. 重启后 `ConnectionManager` 尝试重连 QMT → QMT 仍然不可用 → 熔断器触发 → `os._exit(1)` → NSSM 再拉起
3. 指数退避上限 1800s 后会继续尝试，但 QMT 如果长期不可用（如券商维护），进程会反复拉起/退出

文档 §4.1 的指数退避和 §16.8 的启动互斥都只处理了资源池冲突（WaitingFreeWriter），没有处理"QMT 服务不可用"的持续重试。

**建议**：
- 增加**重连最大次数**（如 30 次 / 累计 2 小时后停止重试），超过后 NSSM 保持进程存活但 kill switch 持续激活
- 当 QMT 长时间不可用时，通过企业微信告知用户"需人工检查 QMT 是否启动"

## 四、架构设计的额外观察

### 4.1 值得肯定的决策

1. **单进程独占 xtquant**（§3.2）：这是正确且必要的。MQ 的分层架构（x-miniqmt 独立进程 → x-server HTTP 调用）对 p9 来说是多此一举，因为 p9 本身就是单语言 Python。减少一层 HTTP 调用 = 减少一个故障点。

2. **清仓锁设 Redis 接口预留**（§5.4）：当前单进程够用，但预留接口是明智的。MQ 的教训就是"注释说多进程改 Redis"但一直没动手。

3. **sell_phase 提前到 14:50 + 14:55 后只撤不挂**（§16.3）：这条修复很关键。14:57 后的收盘集合竞价是实盘特有的坑，很多量化系统在这里翻车。

4. **dry-run 与 live 物理隔离**（§16.2）：用独立表而不是同一个表的 mode 字段，避免了"dry-run 数据不小心被当成真实单"的灾难。

### 4.2 架构上可能的改进方向

1. **考虑引入"订单状态机"显式建模**：文档 §5.3 的 callback handler 做了状态转换校验（非法转换拒绝），但没有画一个完整的状态机图。建议在 §5.3 中加一个状态转换图，列出所有合法路径（50→56、50→57、50→51→53 等）。

2. **live_equity 表的 source=full/partial 机制**：文档 §6 提到复用 sim_trader 的"可信度保护"，但没有展开。当前 sim_trader 的 `equity_price_coverage` 已经实现了覆盖率检测，实盘应该继承这个机制。

## 自检：本报告的逻辑漏洞与迭代

我写完报告后，按规则 2 做了自检，发现了 3 个点：

### 1. 自检发现：DuckDB 串行写问题可能被夸大了

DuckDB 虽然对外暴露是"单写者"，但内部有 WAL（Write-Ahead Log）+ 多版本并发控制。实际上，多个线程短时间内对同一个 DuckDB 文件做 INSERT 是可以的（DuckDB 内部会排队）。问题更多在于**长时间持有的写事务会阻塞其他写入**，而不是"多线程写会直接失败"。

→ **本报告已调整**：从"DuckDB 不支持并发写"改为"需要讨论并发写策略"，严重度从 CRITICAL 调为 HIGH。

### 2. 自检发现：sell_phase 14:52 vs 14:53 需要再核实

我去核实了 [engine.py](app/sim_trader/engine.py) 里的 sell_phase 调用逻辑，发现 engine.py 的 sell_phase 只在 `main.py` 通过 APScheduler 调度，调度时间来自 `config.py` 的 `SELL_TIME = "14:53"`。engine.py 自己的方法注释是手写的 "14:52"，属于注释过期。所以**实际行为是 14:53**，这是确认的。

→ **结论不变**，HIGH-1 维持。

### 3. 自检发现：MQ 的 `trade_schemas.py:126` 声明未逐条核对

研究基础 §2.3 #10 说 `TradeResponseSchema` 缺少 session_id 字段，位置在 `trade_schemas.py:126`。我只验了 x-miniqmt 目录下有这个文件，没逐行检查该字段是否存在。

→ **本报告 LOW-1 已标注**，不影响主要结论。
