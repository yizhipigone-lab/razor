# 回测进度展示优化方案

> 日期：2026-07-12
> 状态：**方案文档，尚未实施**
> 关联：[TDX日线回测提速方案_2026-07-12.md](TDX日线回测提速方案_2026-07-12.md)（后端提速，与本方案互补：一个让回测"算得快"，一个让用户"看得见"）
> 触发：用户反馈"前端一直停在'正在启动回测'，看不到数据准备/选股/出结果的进度"

---

## 一、诊断结论（一句话）

**不是后端没推进度，是前端漏接了。** 后端 [backtest.py:780](../app/api/backtest.py#L780) 一直在推 `backtest_progress`（step/total/msg），但前端 `handleWS`（[main.js:2581](../static/js/main.js#L2581)）**没有 `backtest_progress` 分支**——全前端 grep 零命中。进度消息被静默丢弃，进度条永远停在 0%、文案永远"正在启动回测..."。

### 证据链（已亲自核实，非转述 agent）

1. **后端推送点**：[backtest.py:776-781](../app/api/backtest.py#L776-L781)
   ```python
   def _prog(step, total, msg):
       sync_broadcast({"type": "backtest_progress", "step": step, "total": total, "msg": msg, "context": "simple_bt"})
   ```

2. **前端 handleWS 分支清单**（[main.js:2584-2747](../static/js/main.js#L2584-L2747)）：
   `progress` / `screener_progress` / `scan_done` / `backtest_done` / `simple_bt_done` / `done` / `log` / `info` / `error` / `risk` / `strategy_test_result` / `strategy_saved` / `qmt_sync_done` / `sim_trader_*` / `risk_alert` / `tdx_translated` / `tqsdk_progress` / `tqsdk_screen_done` / `market_quotes` / `portfolio_snapshot`
   → **没有 `backtest_progress`**。

3. **前端进度 DOM 和函数都在，只是没人调**：
   - 进度条 [index.html:420-423](../static/index.html#L420-L423)：`#simple-bt-fill`（width%）+ `#simple-bt-msg`（文本）
   - 更新函数：`showProgress('simple-bt', text)`（[main.js:4797](../static/js/main.js#L4797)）、`updateProgressFill('simple-bt', step, total)`（[main.js:4805](../static/js/main.js#L4805)）
   - 启动时只调一次 `showProgress('simple-bt', '正在启动回测...')`（[main.js:4782](../static/js/main.js#L4782)），运行中再也不调

4. **附带死代码**：`simple_bt_done` 分支里 [main.js:2626-2627](../static/js/main.js#L2626-L2627) 调了 `showProgress(msg.msg)` / `updateProgressFill(msg.step, msg.total)`，但 `simple_bt_done` 的 payload（[backtest.py:843-852](../app/api/backtest.py#L843-L852)）根本不带这几个字段 → 读的是 undefined。像是误粘贴自一个 progress 处理器。

## 二、问题分两层

### 层 1：前端 bug（直接原因）
handleWS 缺 `backtest_progress` 分支 → 进度消息全丢。

### 层 2：后端静默段 + total 不一致（体验问题）
就算修了前端，后端在三个长阶段本身很少推 progress：

| 阶段 | 位置 | 耗时量级 | 推送现状 |
|---|---|---|---|
| 拉通达信全市场 K 线 | [tdx_runner.py:107](../app/backtest/tdx_runner.py#L107) `bridge.execute_screen_range` | 几十分钟 | **完全静默**（subprocess 内部） |
| 价格解析（含 parquet 补 low） | [tdx_runner.py:710-762](../app/backtest/tdx_runner.py#L710-L762) | 分钟级 | **完全静默**（在第一条 progress 之前） |
| 逐日回放主循环 | [tdx_runner.py:775-818](../app/backtest/tdx_runner.py#L775-L818) | **小时级（最长）** | 只在开头推一次 `(1,4)`，之后静默 |

另外 TDX 路径 total 不一致：首轮 `(0, 5)`（[tdx_runner.py:106](../app/backtest/tdx_runner.py#L106)），后面变 `(x, 4)`（[:764](../app/backtest/tdx_runner.py#L764)）→ 前端百分比会从 0% 跳 25% 再跳 75%。

## 三、三层方案总览

| 层 | 改什么 | 解决 | 工作量 |
|---|---|---|---|
| **L1** | 前端补 `backtest_progress` 分支 + 清死代码 | 层 1（前端 bug） | 小（~15 行 JS） |
| **L2** | 后端三个静默段补细粒度进度 + 统一 total | 层 2（后端静默） | 中（tdx_runner 多处加 progress_cb） |
| **L3** | 前端 UI 升级：分阶段面板 + 实时日志 + 心跳 | 体验质变 | 中（HTML/CSS/JS） |

**依赖**：L1 独立可上线；L2 依赖 L1（前端得先能接）；L3 依赖 L1+L2（要有连续进度数据才好做面板）。

## 五、L2：后端补细粒度进度（让长阶段"连续"）

### 设计要点：统一进度 schema（推荐）

为避免 total 在不同阶段含义混乱，**扩展 progress 推送，带阶段标识**：

```python
# 后端约定：每个 progress 推送带 phase
sync_broadcast({
    "type": "backtest_progress",
    "context": "simple_bt",
    "phase": "daily_replay",          # 新增：阶段 id
    "phase_label": "逐日回放",         # 新增：阶段中文名
    "step": 500, "total": 2383,
    "msg": "逐日回放 500/2383 天",
})
```

阶段 id 约定（4 阶段）：

| phase | phase_label | step 语义 | total 语义 |
|---|---|---|---|
| `data_fetch` | 数据准备 | 已处理股票数 或 0/1 | 股票总数 或 1 |
| `signal` | 信号生成 | 0/1 | 1（这步快，基本一档） |
| `price_parse` | 价格解析 | 已解析股票数 | 股票总数 |
| `daily_replay` | 逐日回放 | 已回放交易日 | 交易日总数 |
| `summarize` | 汇总出结果 | 0/1 | 1 |

> **简化方案**（不改 schema）：复用现有 step/total/msg，前端按 `msg` 文本正则判断阶段。改动小但脆弱。建议走扩展 schema。

### 改动 1：逐日回放按天推（最有价值，主循环）

**文件**：`app/backtest/tdx_runner.py`，`_run_daily_backtest` 主循环（[:775](../app/backtest/tdx_runner.py#L775) `for d_obj in td_list:`）

```python
_REPLAY_PROGRESS_EVERY = 50   # 每 50 天推一次，节流（避免刷爆 WebSocket）

for i, d_obj in enumerate(td_list):
    if stop_event and stop_event.is_set():
        return {"status": "stopped"}
    # 新增：节流推送逐日回放进度
    if progress_cb and (i % _REPLAY_PROGRESS_EVERY == 0 or i == len(td_list) - 1):
        progress_cb(i, len(td_list), f"逐日回放 {i}/{len(td_list)} 天", phase="daily_replay")
    # ... 原循环体 ...
```

> 注意：原 [:764](../app/backtest/tdx_runner.py#L764) `progress_cb(1, 4, "逐日回放 (N个交易日)...")` 改成 phase=daily_replay 的首条，total 改为 `len(td_list)`（不再用 4）。

### 改动 2：价格解析按股票推

**文件**：`app/backtest/tdx_runner.py`，价格解析循环（[:714-761](../app/backtest/tdx_runner.py#L714-L761) `for tdx_code, d in raw_prices.items():`）

```python

_codes = list(raw_prices.items())
for idx, (tdx_code, d) in enumerate(_codes):
    if progress_cb and idx % _PRICE_PROGRESS_EVERY == 0:
        progress_cb(idx, len(_codes), f"解析价格 {idx}/{len(_codes)}", phase="price_parse")
    # ... 原循环体 ...
```

### 改动 3：拉数据段心跳

`bridge.execute_screen_range` 内部是 subprocess（[bridge.py:216](../app/tqsdk/bridge.py#L216) `_run_worker`），不好插细粒度进度。**心跳方案**：在 backtest.py 的 `_run` 线程里起一个定时器，每 15 秒推一次"还活着"：

```python
# app/api/backtest.py 的 _run 函数里，调 run_tdx_backtest 之前
import threading as _th, time as _time
_last_heartbeat = {"stop": False}
def _heartbeat():
    while not _last_heartbeat["stop"]:
        sync_broadcast({"type": "backtest_heartbeat", "context": "simple_bt",
                        "msg": "数据获取中...", "ts": _time.time()})
        _th.Event().wait(15)   # sleep 15s，可中断
_hb = _th.Thread(target=_heartbeat, daemon=True); _hb.start()
try:
    result = run_tdx_backtest(...)   # 或 run_backtest
finally:
    _last_heartbeat["stop"] = True
```

### 改动 4：统一 total（修不一致）

把 TDX 路径所有 progress_cb 的 total 统一到上面 schema 的阶段语义，删掉 `(0,5)` 这种和后续 `(x,4)` 冲突的写法（[:106](../app/backtest/tdx_runner.py#L106)）。

### 节流策略（防刷爆）

WebSocket 广播 + 前端 DOM 更新都耗资源。长循环里**不能每次迭代都推**。经验值：
- 逐日回放：每 50 天一次（2383 天 → 约 48 次推送，每次间隔约 30 秒）
- 价格解析：每 500 只一次（5422 只 → 约 11 次）
- 心跳：每 15 秒一次

### 心跳与"卡死检测"

```js
// 前端每 5 秒检查一次最后消息时间
setInterval(() => {
  if (!btState.startTime) return;
  const silent = (Date.now() - btState.lastMsgTs) / 1000;
  const hb = document.getElementById('simple-bt-heartbeat');
  if (silent > 60) {
    hb.textContent = `⚠️ 已 ${Math.round(silent)} 秒无更新，可能卡住`;
    hb.style.color = '#e74c3c';
  } else {
    hb.textContent = `${Math.round(silent)} 秒前更新`;
    hb.style.color = '#7f8c8d';
  }
}, 5000);
```

后端心跳（L2 改动 3）配合：数据获取阶段每 15s 推一次 `backtest_heartbeat`，前端收到就刷新 `lastMsgTs`，彻底消除"卡死"错觉。

### 预估耗时算法

```
当前阶段已用 = now - phase_start_ts
当前阶段进度 = step / total
预估当前阶段总耗时 = 已用 / 进度
预估剩余 = 预估总耗时 - 已用
```

仅当 step/total > 0.05 时显示（避免早期抖动）。
