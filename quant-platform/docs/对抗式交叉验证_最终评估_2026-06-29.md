### 争议 1：engine.py 到底有没有走 execution.py 统一执行层

报告 A 说自己"全路径接入成本"。报告 B 说 engine.py 还在用硬编码常量，没真走 execution.py。

**我查了代码。B 说的对。**

- `engine.py:331-332`：`TRADE_COST_BUY=0.125`，`TRADE_COST_SELL=0.175` — 类内硬编码常量，确实还在
- `engine.py:24`：`from app.backtest.execution import calc_buy_cost, calc_sell_revenue` — import 了，但不说明用了
- `engine.py:657`：`cost_entry = entry_price * (1 + self.TRADE_COST_BUY / 100)` — 用的是类内常量，不是 calc_buy_cost
- `engine.py:881`：同样，daily_fallback 也是用类内常量

**定论**：报告 A 说"全路径接入成本"不算错——确实扣了成本。但 B 说"没有走 execution.py 统一执行层"也是对的——用的是自己类里的常量，成本率跟 config 里的 cost 段不是同一套值。execution.py 里 config 化的成本率（万2.5 佣金）和 engine.py 里的硬编码常量（0.125% 买入成本=万10 滑点+万2.5 佣金）是两个不同的东西。

**这是一个口径差异，不是 bug。** 但要承认：整改之后 engine.py 的成本率还是在类常量里，不在 config 的 `backtest.cost` 里。如果以后改配置文件里的成本率，engine.py 不会跟着变。

### 争议 2：_fast_simulate 的"已统一为小数"是不是过度宣称

报告 A 说 P0-1 已经把 `_fast_simulate` 统一到小数口径。报告 B 说 `realized` 内部还是混用百分比和小数。

**我查了代码。两边各对了一半。**

`ai_optimizer.py` 的 `_fast_simulate` 里：
- L658：`realized += tp_pct * 100 * actual` — tp_pct 是小数（0.03），乘 100 反推回百分比格式的 realized
- L674：`realized += curr_stop * remaining` — curr_stop 是百分比值（-7），直接加
- L685/693：`realized += close_pnl * remaining` — close_pnl 是百分比，直接加

**定论**：报告 A 说的"tp_pct 已统一为小数"是对的——tp_pct 这个变量本身确实改成了小数。但 B 说的也对——`realized`（最终 pnl 累加值）的内部计算还是混用两种单位（小数转百分比 + 原生百分比）。这更像是"输入变量统一了，但中间计算没有完全统一"。

**严重程度**：中等。不是 bug——结果算出来是对的。但维护性差——下一个人看不懂为什么有的地方乘 100 有的不乘。
