### plan 有一个**隐性但重要的细节**没在文档里写明 ⚠️

我重新走查成本计算链时发现一个 plan 没明示的微妙点:

- `simple_runner.py` 的 sell 在**部分卖出时,不递减 `p.cost` 和 `p.shares`**(只有 tdx_runner 递减 `pos.cost`)
- 但这**自洽**:因为 simple_runner 的 `_cb = p.cost * (ss/p.shares)`,分母 `p.shares` 全程不变(只在 full close 时归零)
- 全平后 Σ`_cb = p.cost * (p.shares / p.shares) = p.cost`,守恒成立
- 计划说"部分卖出必传 cost_basis",没说为什么不递减 — 应当补一句解释,免得施工者读到 simple_runner 觉得"少了一行递减"是 bug

**风险等级**:低(数学自洽),但**施工者会困惑**,影响他们对照验代码的信心。

### 计划里**没明说但应当预警**的两件事 ⚠️

1. **ai_optimizer 寻优结构会移位** — 计划提到"pnl_pct = Trade.ret,改净后自动变净"是符合统一目标,但**没说这是 AI 选策略优化器的寻优目标函数语义变更**,在保持样本内历史数据下重新优化会得到一组**不同**的最优参数。如果用户的优化器历史快照/已部署策略是按毛口径筛出来的,改后"最优"不再是同一个。**应在执行前与用户确认**:是否要保留旧 optimizer 快照、可回滚参数?

## 三、整个"验证 → 设计"流程的方法学自审

### ✅ 做对的
- 4 个只读 agent 并行验证 6 张卡 — 效率高、范围不重叠
- 派 Plan agent 设计实施方案 — 把改造细节和验证手段留痕
- 用户决策点明确(4 个 AskUserQuestion)— 不静默脑补、不自由发挥
- 验证报告用 PASS/FAIL/PARTIAL + file:line — 结论可追溯
- 个人亲自重读 9 处关键证据(3+6)— 防 agent 假阳性

### ⚠️ 流程本身的弱点

1. **agent 没做对抗式验证** — 4 个 agent 各自出结论,没有"第二个 agent 反向挑刺"。靠我手动抽查补这个环节,效率低。下次应当在 protocol 里加一步 "adversarial verify":每个 PASS 主张过另一个 agent 独立挑刺。
2. **"我亲自交叉验证"是被动加的,不是先列入计划** — 我抓到 CARD 2 FAIL 是在 agent 报告后才回过头自己读代码核对。**应在每次 agent 报告回来时立刻抽 20% 标的**重读,而不是等出现 FAIL/边界争议才补。这是流程改进点。
3. **没跑过 baseline pytest** — 我一直说"现有测试不破",但没真跑过。如果 baseline 是绿的,动工后第一次 red 就好排查;baseline 本身就有红,动工就被淹了。
4. **没建"完整改动行号 + 改前/改后"对照表** — 计划给了改动点的 file:line,但**没给改前/改后的完整代码块**(只给了伪代码片段)。施工时要一行行回去看。**应当做成一份 diff 文件** 让实施者直接在 diff 旁批注。
5. **过程性 artifacts 散落在多文件** — 验证报告 md 在 docs/,计划在另一个目录的 plans/,agent 输出在 Temp。**做事中确实没问题,但做完后归档应当集中**(比如 `docs/审计报告/` 下面子目录分 validate / plan / review)。

### ❌ 必须改的

无。所有产出都能开工,只是要带上 ⚠️ 标记的 3 个补强项。
