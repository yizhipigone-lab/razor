## 一、最终结论（一句话）

> **根因不是"资金减少"，而是"数据被替换"。** 在 6/26 收盘后、6/29 开盘前的某个时点，有人运行了一次性灌数脚本 **`scripts/populate_sim_quantqq.py`**，它把 TDX 全市场公式回测的结果**整盘覆盖**写进了真实模拟盘的 `output/sim_trader/state.json`。TDX 回测数据本身就是虚高的（首日净值就 214 万，而真实初始资金只有 100 万），于是 6/22~6/26 的净值全部虚高 ~2.5 倍。6/29 系统重启后加载了这份被替换的状态（现金 299 万、持仓清空），当天 cron 正常跑完写下真实净值 299 万，于是和虚高的 6/26（360 万）之间形成了 **60.4 万的"视觉断崖"**。**没有任何真实资金减少，4 只持仓也从未真实存在过。**

## 三、关键证据链（我亲自验证的，按证明力排序）

### 证据 1 ⭐ 决定性：数据结构的"键名指纹"

`_fill_missing_snapshots`（engine.py:259-262）和实盘 `record()`（engine.py:579）写 equity_curve 时，用的键是 **`'positions'`**：
```python
self.equity_curve.append({'date':..., 'equity':..., 'cash':..., 'positions': self.position_count})
```
而 state.json 里 6/22~6/26 这批虚高记录，用的键全是 **`'pos'`**：
```json
{"date": "2026-06-26", "equity": 3597707.64, "cash": 2993728.64, "pos": 4}
```
用 `'pos'` 键的写入路径只有两处：`store.save_equity_point`（落盘）和 **`populate_*` 脚本（166 行）**。
**这从数据结构层面直接排除了 `_fill_missing_snapshots`**——它要是真写过，键名会是 `'positions'`。

### 证据 2 ⭐ 决定性：补录函数的日志标记，11 天全 0

`_fill_missing_snapshots` 每补一天必打 `log.info("[快照补录] ... 启动时自动补齐")`（engine.py:266）。
```
grep -c "快照补录" logs/2026-06-*.log  →  全部 0
```
**该函数从头到尾一次都没跑过。原审计报告的根因不成立。**

### 证据 3 ⭐ 决定性：找到真凶脚本 `populate_sim_quantqq.py`

核校报告点名的 `populate_sim_trader.py`，其默认输出是 `output/sim_trader/{strategy}_state.json`（即 `QUANTQQ_state.json`），**不会**直接覆盖 `state.json`——除非手工指定 `--output`。这是核校报告逻辑链的薄弱环节。

我在 `scripts/__pycache__/` 里发现了一个**只剩编译产物、源码已被删**的兄弟脚本 `populate_sim_quantqq.cpython-313.pyc`（编译时间 **6/27 19:29:53**）。反编译它的常量字符串：
```
'\n[2/3] 转换格式并写入 state.json ...'
'将 run_tdx_backtest 结果写入 JsonSimStore (state.json)'
'output' / 'sim_trader' / 'state.json'
```
**它把 TDX 回测结果直写 `state.json`，路径是写死的。** 这才是真正的覆盖者。时间线也吻合：6/27 19:29 编译运行 → 6/27 日志暴涨到 10MB（含 2147 行 `TdxSimLogger` + DuckDB/Parquet 回测痕迹）。

### 证据 4：备份文件锁死了时间窗口

`output_backup_pre_p0/sim_trader/state.json`（mtime **6/29 00:03**，早于 6/29 开盘 cron）里：
- equity_curve 已是 114 条、首条就是 `equity=2,139,705 / pos=17`（TDX 指纹）
- 末条停在 `6/26 equity=3,597,707`，**还没有 6/29 的真实记录**
- trades 与当前文件**完全一致**（1297 笔），ec 前 114 条**完全一致**

**结论**：覆盖发生在 6/29 第一次 cron 之前（6/27~6/28 之间），与脚本编译时间 6/27 19:29 完全对得上。6/29、6/30 的真实记录是事后 cron 追加上去的。

### 证据 5：TDX 数据"自带虚高"，不是任何 bug 算出来的

- 真实初始资金（config）：`INITIAL_CAPITAL = 1_000_000`，单票上限 `POSITION_SIZE = 50_000`
- state.json 首日（1/5）：`equity=2,139,705`，**首日就 2.14 倍**，且 17 只持仓 × 5 万上限 = 85 万，根本兜不住 214 万
- 全部 1297 笔 trade 的 `entry_time` 都是 `09:30`、`exit_time` 都是 `15:00`（回测整点特征，真实盘中卖出不可能如此整齐）
- `prev_day_snap` 里塞了**全市场数千只股票**的昨日快照（真实模拟盘只会有持仓票）

这些都是 TDX 全市场回测的指纹，与真实 cron 引擎（日志显示真实净值在 60~135 万区间）是两套完全不同的数据。

### 证据 6：60.4 万差额 + 164 万 cash 跳变，一次性解释清楚

- 6/26 真实尾盘（日志）：`equity=1,486,078 / cash=1,350,782 / 持仓3`
- 6/26 被覆盖后（state.json）：`equity=3,597,707 / cash=2,993,728 / pos=4`
- 6/29 真实 cron：`equity=2,993,729 / cash=2,993,729 / 持仓0`
- **"60.4 万断崖" = 3,597,707（虚高 6/26）− 2,993,729（真实 6/29）= 60.4 万**
- **"164 万 cash 跳变" = 2,993,728（TDX 终值现金）− 1,350,782（真实 6/26 现金）= 164 万**

两个谜题的答案是同一个：**TDX 回测的终值现金恰好是 299 万，覆盖了真实的 135 万。** 不是手工改、不是利息、不是补录。

### 附带发现（新 bug，两份报告都没提）

6/29、6/30 的 equity_curve 各有**两条重复记录**——一条 `'positions'` 键、一条 `'pos'` 键：
```json
{"date":"2026-06-29", ..., "positions": 0}   ← record() 内存对象直接被整盘写回
{"date":"2026-06-29", ..., "pos": 0}          ← save_equity_point 正常落盘
```
说明存在**两条混用的写盘路径**（engine.py:200 `load_equity_curve()` 把磁盘 list 读进内存，record() 又把内存 append 回去整盘 dump），会造成同日双记录。属独立的数据一致性 bug，需一并修。

## 四、根因定位（分主次）

| 层级 | 根因 | 性质 |
|---|---|---|
| **直接根因** | `populate_sim_quantqq.py` 把 TDX 回测结果**直写 `state.json`**，整盘覆盖了真实模拟盘状态 | 操作 + 设计缺陷 |
| **设计根因 1** | 灌数脚本的输出路径与真实运行态 `state.json` **共用同一文件/目录**，无任何隔离、无确认、无备份 | 架构缺陷 |
| **设计根因 2** | `JsonSimStore._save()` 非原子写 + 无写入来源标记（`record`/`fill`/`import` 不分），坏数据静默固化、无法追溯 | 健壮性缺陷 |
| **放大因素** | TDX 回测数据本身虚高 2.5x（无视 5 万建仓上限），一旦混入真实盘极具迷惑性 | 数据语义不一致 |

**这不是"资金减少"事件，是"测试数据污染生产状态"事件。** 钱一分没少，是账本被人换成了另一本。

## 五、修复计划书

### P0 — 立即止血（今天做，防再次污染 + 纠正展示）

**P0-1 物理隔离灌数脚本，杜绝再次覆盖**
- 删除 / 封存只剩 pyc 的 `populate_sim_quantqq.py`（已无源码，是定时炸弹）
- `populate_sim_trader.py` 增加**硬护栏**：当 `--output` 解析后等于真实运行态 `state.json` 时**直接报错退出**，并要求显式 `--force-overwrite-live` 才放行
- 灌数默认输出目录改到独立的 `output/sim_trader/imports/`，与运行态目录物理分离

**P0-2 恢复真实 state.json（数据修复）**
- 现状：`state.json` 是 TDX 回测数据，真实 6/26 收盘态散落在日志里
- 方案：用日志真实快照重建真实状态作为新起点（不是补 4 只持仓——那 4 只是 TDX 虚构的）：
  - 真实锚点 = 6/26 14:54 `cash=1,350,782 / 持仓3只`
  - 3 只真实持仓代码需从 6/26 日志的买入/未平仓记录反查（**仅用日志，不用 state.json 的 trade**）
- ⚠️ **决策点**：是否接受"以 6/26 真实尾盘为新基线、丢弃被污染的 1~6 月历史曲线"——这需要你拍板（见末尾提问）

**P0-3 加载期一致性校验（防下次坏数据静默生效）**
- `get_engine()` 加载 state.json 后立即自检：
  - `state.cash` 是否 ≈ 最近 equity_curve 的 cash（偏差 >5% 告警）
  - `equity ≈ cash + Σ持仓市值`（偏差 >5% 告警）
  - 首日 equity 是否 ≈ `INITIAL_CAPITAL`（>1.2x 直接拒绝加载并告警，可挡住 TDX 数据）

## 六、给你的大白话总结

把模拟盘的账本想成一个 Excel 文件。

6/26 收盘时，这个账本是真实的：手头现金 135 万，还拿着 3 只股票。

6/27 晚上，有人跑了一个"测试灌数"脚本——这个脚本本来是拿历史数据做模拟演练用的，演练结果是一份**虚构的、放大了 2.5 倍的假账本**（假装从 100 万本金滚到了 360 万）。坏就坏在，这个脚本**直接把真账本文件覆盖掉了**，把假账本存成了正式账本。

6/29 系统重启，读到的就是这本假账。当天正常运行后，系统老老实实记下"现在实际只有 299 万"。于是屏幕上就出现了：昨天（假账）360 万 → 今天（真账）299 万，**看起来"凭空蒸发 60 万"**。

**真相**：钱一分没动过，4 只"消失的持仓"也从来不存在。是账本被人用测试数据覆盖了，不是资金出了事。

**最该做的不是去"找回那 60 万"**（它本就不存在），而是：① 把测试脚本和正式账本彻底隔离，别再误覆盖；② 用 6/26 的真实日志把账本重建回真实状态；③ 加一道开机自检，下次坏账本进来时系统自己能拦住。
