# 专项诊断：真实cron净值虚高问题会不会再发生

**日期**: 2026-07-01
**问题**: 用户问——真实cron净值虚高问题，后续是否还会发生？
**结论**: **分情况。正常14:52 cron不会；盘前/盘后手动触发或行情通道全挂时仍会。是结构性缺陷，需修但优先级中。**

---

## 一、根因坐实（不是猜测，有日志证据）

### 缺陷代码
`engine.py` `total_equity()`：
```python
def total_equity(self, snapshot: dict) -> float:
    pv = sum(
        p.remaining_shares * snapshot.get(p.code, {}).get('close', p.entry_price)
        #                                                        ^^^^^^^^^^^^^^^^
        #                          snapshot缺该股价格时, fallback买入价(而非当前市价)
        for p in self.active_positions()
    )
    return self.cash + pv
```

### 日志实证（5/27 净值序列自相矛盾）
5/27 当天 record 被调用 **6 次**，净值剧烈横跳：
```
08:31  权益=1,196,312  持仓17
08:47  权益=1,210,462  持仓25
08:56:18 权益=1,224,742 持仓26
08:56:57 权益=1,000,000 持仓21  ← 39秒内暴跌23万, 净值≈纯本金
09:08  权益=1,341,522  持仓21
16:39  权益=1,372,550  持仓29
```

**08:56:57 那条=100万的真相**：日志显示前一刻是"手动-QUANTQQ"策略在盘前批量买入（现金打到1095元，持仓21只）。买完立即 record，但**盘前无实时行情，snapshot为空** → 每只持仓 fallback 到 entry_price → 持仓市值≈买入成本 → 净值≈初始100万（因为刚花光现金买入，成本≈现金减少额）。

即：**净值虚高/跳变 = snapshot缺失时按买入价而非市价估值 + 盘前手动触发record**。

## 二、后续会不会再发生——分情况

### ✅ 情况A：正常 14:52 定时cron —— 不会
- 14:52 时 QMT 注入全市场行情（5/28实测注入5208只、6/26注入5206只）
- snapshot 覆盖完整，持仓股都有当前市价，不走 fallback
- 净值正确

### ❌ 情况B：盘前/盘后手动触发 —— 会
- 有人在盘前（如8-9点）手动点"选股买入"或触发record
- 此时 QMT/腾讯行情未开盘或返回异常 → snapshot空/不全 → fallback买入价 → 净值错
- 5/27 的乱象就是这么来的（策略名"手动-QUANTQQ"）

### ❌ 情况C：行情三通道全挂 —— 会
- QMT失败→腾讯失败→回退get_daily_snapshot(读parquet当日)
- 若当日parquet还没数据（盘中未收盘），snapshot空 → fallback

## 三、对本次迁移基线的影响：✅ 无影响

- **回放基线用的是 parquet 历史真实收盘价**，snapshot每天覆盖5200+只，从不fallback
- 迁移后基线净值曲线最大单日跳变仅 +4.6%，无100万异常跌落，数据自洽
- **明天正常14:52 cron接管后，只要行情正常注入，不会虚高**

## 四、残留风险与建议修复

### 现状防护缺口
| 机制 | 覆盖 | 缺口 |
|---|---|---|
| P0-4加载校验 | 启动时查首条>110%本金 | 不管运行中每日record的跳变 |
| total_equity | 无 | snapshot缺失静默fallback买入价 |
| #8修复(record开头) | 更新current_price防归零 | 但total_equity没用current_price, 用的snapshot |

### 建议修复（未在本次范围，供决策）
1. **total_equity 加防护**：snapshot缺某持仓股价格时，优先用 `pos.current_price`（上次已知市价），再不行才用entry_price，**并告警**"净值可能不准"
2. **record 加卫兵**：若 snapshot 覆盖率 < 持仓数（说明行情不全），**拒绝写净值点或标记该点不可信**（加 `source='partial'`）
3. **禁止盘前触发record**：手动买入后不立即record，或record前校验是否交易时段+行情就绪
4. **运行期跳变告警**：单日净值跳变>15%时告警（可复用P0-4的思路，扩展到运行期）

### 优先级
**中**。因为：
- 正常自动cron不受影响（主路径安全）
- 只在"手动盘前操作"或"行情全挂"边缘场景触发
- 但既然发现了，建议纳入下一轮修复（约1-2小时工作量）

## 五、大白话

**这个"净值虚高"是另一个独立的老bug**，跟之前的数据污染不是一回事。

**原理**：系统算总资产时，如果拿不到某只股票的"当前价"，就偷懒用"当初买入价"顶替。正常下午2:52自动跑的时候，行情是全的，不会出问题。但如果**有人大清早手动去点买入**，那会儿股市还没开盘、拿不到实时价，系统就用买入价估值，算出来的净值就是错的（会显示成刚好等于本金那种假数字）。

**明天会不会再犯**：
- 只要是**系统自己定时跑**（下午2:52）——**不会**，行情是全的
- 如果**有人手动盘前操作**——**还会**

**对我们刚弄好的账本有没有影响**：**没有**。回放基线用的是历史真实收盘价，干干净净。

**建议**：这个bug优先级中等，不紧急（主流程安全），但既然挖出来了，建议下次顺手修掉——让系统在"拿不到实时价"时会报警，而不是偷偷用买入价糊弄。
