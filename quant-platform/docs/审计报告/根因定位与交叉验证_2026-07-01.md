## 一、最终根因定位(一句话)

> **state.json 中 6/22 ~ 6/26 的 equity_curve 记录,全部由历史"补录/重算"逻辑写入,数值是当时真实 self.cash 的约 2.5 倍(虚高)。6/29 启动后,真实状态(self.cash=2,993,729 / positions={})与 6/26 那条虚高记录形成 60.4 万的"视觉差",但并非资金真的减少。**

换句话说:
- ❌ 不是"4 只持仓被清空,卖出的现金没到账"
- ❌ 不是"sell_phase 在 14:52 跑一半被强杀"
- ✅ 而是 **6/22~6/26 的 equity_curve 记录本身就是错误的(虚高)**,6/29 的 equity_curve 才是真实的

- 但 6/24 已被跳过,6/24 的 equity_curve 是**之前某次启动时**写入的,且写入了错误数字

### 证据 4:_fill_missing_snapshots 的虚高来源

**engine.py:202-269 的逻辑**:

```python
def _fill_missing_snapshots(self):
    last_date = date.fromisoformat(self.equity_curve[-1]['date'])
    d = last_date + timedelta(days=1)
    while d <= yesterday:
        # 跳过周末 + 非交易日
        for code, pos in self.positions.items():
            close_px = pos.entry_price  # ← 默认 entry_price
            # 读 parquet 收盘价
            total_mv += pos.remaining_shares * close_px
        equity = self.cash + total_mv
        self.equity_curve.append({...})
```

**潜在问题**:
1. 用 `self.cash` 计算 equity — 如果 self.cash 已经是 sell+buy 之后的状态(对)
2. 用 `self.positions` 计算持仓市值 — **但 self.positions 可能不包含冷启动加载时的最新数据**
3. parquet 中如果某日数据缺失,**fallback 到 `pos.entry_price`**——不是真实收盘价,会高估或低估

但实测发现的问题更严重:6/22~6/26 的 equity/cash 全部虚高 ~2.5x,而不是简单偏低或偏高。**这意味着写入时 self.cash 本身就是 ~2.5x 的错值**——可能是:
- 某次冷启动时,self.cash 是用 `state.cash`(错的)+ 重复累加得到的
- 或者 save_state 时 cash 被错误地乘以了某个系数
- 或者 _fill_missing_snapshots 在迭代历史日时,**用了累加的 self.cash(包含已补录的 equity 增量)**

### 证据 5:6/29 cash=2,993,729 是怎么来的(差额 164 万)

- 6/26 尾盘日志 cash=1,350,782
- 6/29 启动时 self.cash=2,993,729
- 差额 = **1,642,947 元**(约 164 万)

但 6/27~6/28 是周末,trade 列表没有新交易。**164 万从哪来?**

可能性:
1. **6/27~6/28 期间有手工修改 state.json**(把 cash 改了 164 万)
2. **6/28 19:19 日志之后(周一前夜),有定时任务执行了"分红/利息"调整**
3. **6/29 早上 7:21 启动时,`_fill_missing_snapshots` 跑了 6/27~6/28(周末)被跳过,但 6/27 或 6/28 是交易日?——查日志确认**
4. **state.json 之前被人为编辑过**(高级报告也提到了"系统重启/手工操作"的可能)

**最可能**:6/27 6:59 的 `[TDX模拟盘] 14:52 开始执行` 是一条干扰——这是另一个独立的 TDX 模拟盘,不是同一个 SimEngine。但 6/27 6:59 之后,**TDX 模拟盘加载时初始状态显示 "现金 1,000,000, 持仓 0"**——这说明 TDX 模拟盘与 SimEngine 是两套独立数据。

但 6/29 启动时 self.cash=2,993,729 是从 state.json state.cash 加载的,说明这个数字确实是某次写入的。

## 四、高级报告 5 个缺陷的逐一核验

### 缺陷 A:`_save()` 无原子写入(致命)

**位置**: `app/sim_trader/store.py:243-245`

**核验**: ✅ 确实是真问题。`json.dump()` 渐进入写,中途进程被杀会损坏文件。

**对本案的影响**: ❌ 不是本案根因。证据:
- 6/26 14:54 cron 跑成功了(日志明确)
- state.json mtime = 2026-06-30 14:54:13,文件没损坏
- 6/29 启动成功加载,无 ERROR

### 缺陷 B:sell_phase 保存顺序颠倒(致命)

**位置**: `app/sim_trader/engine.py:537-551`

**核验**: ✅ 代码确实如此(已 Read 验证),但 ❌ 不是本案根因。证据:
- 6/26 14:54 sell_phase + buy_phase + record 都跑成功了
- 6/26 11 笔 trade 全部落库
- 6/26 equity_curve 写入的数字是虚高,不是 sell_phase 中断造成的

### 缺陷 C:Position 序列化不完整(严重)

**位置**: `app/sim_trader/store.py:285-292`

**核验**: ✅ 是真问题。is_active/peak_price/remaining_shares/tp1_triggered/tp2_triggered 都没保存。

**对本案的影响**: ⚠️ 间接影响。冷启动时 is_active 默认 True,可能让"已死仓位"复活。但本案 6/29 启动后 positions 是空的(0 只),说明没复活。

### 缺陷 D:启动补录静默固化错误数据(严重) ⭐ **最接近根因**

**位置**: `app/sim_trader/engine.py:202-269`

**核验**: ✅ **高度疑似本案根因**。证据:
- 6/22~6/26 的 equity_curve 全部虚高 ~2.5x,与日志真实值不符
- 这几天都没有 14:52 cron 的 `[模拟盘] 完成` 日志,说明 equity_curve 不是当天 record() 写入的
- 只有 `_fill_missing_snapshots` 会在冷启动时回填历史 equity_curve
- 但补录逻辑中,`equity = self.cash + total_mv`——如果 self.cash 是错的,equity 就是错的

**疑点**:
- 6/24 已被 cron 跳过("已执行过今日任务"),但 state.json 6/24 equity_curve 仍在
- 这说明 6/24 那条 equity_curve 是**更早之前的某次启动时**用错数据写入的

### 缺陷 E:save_equity_point 非即时落盘(中等)

**位置**: `app/sim_trader/store.py:323-327`

**核验**: ✅ 是真问题。`if len(pts) % 10 == 0: self._save()` 会丢失最近 1-9 个净值点。

**对本案的影响**: ⚠️ 间接。但 record() 末尾还有 `save_state()` 兜底,所以丢失窗口有限。

## 六、根因推论(综合 3 份报告 + 我的交叉验证)

### 主因:`_fill_missing_snapshots` 在某次冷启动时用错数据回填了 6/22~6/26 的 equity_curve

**事件序列重建**:
1. **某次冷启动(可能 6/22 之前)**:`_fill_missing_snapshots` 跑,从最后已知 equity_curve 日回填到昨天
2. 当时 `self.cash` 是某个**错的中间状态**(可能是初始资金 × 2.5、或者从旧 state.json 加载了错误 cash)
3. 补录逻辑写出 6/22~6/26 的 equity_curve,数字 = 错 cash + 持仓市值
4. 之后每天 14:52 cron 跑,新的 record() **没有覆盖**旧 equity_curve(record 只覆盖当天的最后一条,但补录的"6/22"等日期不再被覆盖——因为 last_date 是 last_equity_curve_date)
5. 6/26 cron 跑的时候,record() 应该覆盖 6/26 那条——但 6/26 14:54 的 record() 算出的 equity=1,486,078,与补录的 equity_curve 6/26 条目(3,597,708)冲突
6. **关键**:`record()` 中 `if self.equity_curve[-1].date == today: self.equity_curve[-1] = entry` 只覆盖**最后一条**
7. 如果补录的 6/22~6/26 不是连续追加的(中间漏了日),record() 不会覆盖;或者 record() 在补录之前已经写入了 equity_curve

### 次因:save_state / save_equity_point 写入路径混乱

证据:
- 6/27~6/28 期间 cron 没真正跑(周末),但 state.json 里 state.cash 变成 2,993,729
- 这意味着有其他代码路径(可能是 IntradayMonitor 监控器的 stop 检查、API 调用)在写 state.json
- 这些路径没经过 record(),直接 save_state 写入

### 第 3 个可能:6/27~6/29 期间有人手工修改 state.json

- 6/26 尾盘真实 cash=1,350,782
- 6/29 真实 cash=2,993,729
- 差额 164 万,周末无 cron 跑,这 164 万是手工添加?或者 IntradayMonitor 异常?

## 七、修复建议(优先级排序)

### P0:立即止血(防止再次发生)

1. **回滚或修正 state.json 中 6/22~6/26 的 equity_curve 记录**
   - 方案 A:删除这几条记录,让 _fill_missing_snapshots 在下次启动时用真实 cash 重新补
   - 方案 B:用日志真实值手动修正:
     - 6/24 → equity=1,423,665 / cash=655,907 / pos=16
     - 6/25 → equity=1,427,142 / cash=1,052,173 / pos=8
     - 6/26 → equity=1,486,078 / cash=1,350,782 / pos=3(尾盘)

2. **加一致性校验**:每次 record() 后,检查 `equity == cash + sum(positions market_value)`,误差 >5% 报警

3. **加 _fill_missing_snapshots 的现金变化阈值**:
   - 补录前后 self.cash 变化超过 10% 时,拒绝补录并报警

### P1:结构修复

1. **修缺陷 A**:`_save()` 改 `tempfile + os.replace()` 原子写
2. **修缺陷 B**:sell_phase 改为先保存 cash,最后清理 positions
3. **修缺陷 C**:save_positions 补全 is_active / peak_price / remaining_shares / tp1_triggered / tp2_triggered
4. **修缺陷 E**:save_equity_point 去掉 `% 10 == 0` 的延迟落盘

### P2:长期改进

1. 引入 DuckDB 替代 JsonSimStore,享事务
2. 给所有 cron 入口加幂等保护(`_daily_ran_date`)
3. 给 equity_curve 加 `record_source` 字段(`record` / `fill_missing` / `manual`),便于追溯
