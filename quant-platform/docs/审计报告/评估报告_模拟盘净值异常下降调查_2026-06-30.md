## 五、独立第三方判断:当前 bug 的最大嫌疑点

**嫌疑: `_fill_missing_snapshots` (engine.py:202-269)**

### 代码路径

```python
def _fill_missing_snapshots(self):
    if not self.equity_curve:
        return
    last_date = date.fromisoformat(self.equity_curve[-1]['date'])
    yesterday = date.today() - timedelta(days=1)
    d = last_date + timedelta(days=1)
    while d <= yesterday:
        # 跳过周末
        if d.weekday() >= 5:
            d += timedelta(days=1)
            continue
        # ... 查 parquet 收盘价 ...
        for code, pos in self.positions.items():
            close_px = pos.entry_price  # ← 默认 entry_price
            if daily_dir and f.exists():
                row = df[df['date'] == d]
                if not row.empty:
                    close_px = float(row.iloc[0]['close'])
            total_mv += pos.remaining_shares * close_px
        equity = self.cash + total_mv
        self.equity_curve.append({...})  # ← 写入"补录"快照
```

### 风险点

1. **用 self.cash 计算** —— 如果 self.cash 是"补录日"的状态(非 6/26 收盘后的状态),数字会错
2. **用 self.positions 计算** —— 如果 6/27 冷启动时 positions 是空的(因为 6/26 没存),total_mv = 0,equity = self.cash,这反而是 6/29 看到的 299 万 → 但 6/26 那条记录是哪来的?
3. **补录 vs 真实 record() 的写冲突** —— 如果补录路径与 record() 路径都用 `self.equity_curve.append()`,且都 `save_equity_point`,会互相覆盖

### 假设的事件序列(基于实测数据重建)

| 时刻 | 事件 | 状态 |
|---|---|---|
| 6/26 14:52 | cron 触发 sell_phase | 卖 6 买 2 |
| 6/26 14:54:23 | cron 完成,日志打"持仓3 净值148万" | ✅ 内存与日志一致 |
| 6/26 14:54:23+ | record() 调用,写入 equity_curve | **写入什么数字?** |
| 6/26 14:54:24 | `save_equity_point(today, eq, ...)` | 落盘 |
| 6/26 收盘→6/27 | state.json 保存 | **保存的应该是 148 万,但实际是 359 万** |
| 6/27 00:31 | 冷启动,加载 state.json | 加载到 6/26 = 359 万 |
| 6/29 14:52 | cron 触发 | 加载 self.cash=2,993,728, self.positions={} |
| 6/29 14:54 | 净值 = cash + 0 = 299 万 | ✅ 与 state.json 一致 |

**所以 6/26 那条 359 万 equity_curve 是怎么来的?** —— 这就是真正需要查的。

### 三种可能的写入路径(我无法 100% 排除任何一个)

**路径 A: 6/26 14:54 record() 时,equity 计算用了错的 self.cash**
- record() 调 `total_equity(snapshot)`,公式 `cash + sum(positions market_value)`
- 如果此时 self.cash 已经是 sell+buy 之后(299 万),持仓 3 只市值 60 万 → 359 万
- **但日志说 14:54:23 这一刻 cash 是 135 万 持仓 3 只,不是 299 万 持仓 4 只**
- 所以 record() 一定是在 **另一时刻**被调用的,不是 14:54:23

**路径 B: 6/27~6/29 之间,某个 cron 任务用错的 state 重新触发了 record()**
- 例如 6/27 冷启动后,`_fill_missing_snapshots` 补录了 6/26
- 但补录用 self.cash(应该是 299 万)+ self.positions(可能是空的,导致 total_mv=0)
- 这样 equity = 299 万,不是 359 万 → 也不对

**路径 C: 6/26 当天有第二次 cron/手动触发,被中断后状态错乱**
- 6/26 14:54:23 第一次跑完,日志说 cash=135 万
- 之后又触发了一次(比如 15:30 收盘热度终版),这次 sell_phase 又卖了一些,positions 变化
- 但 state.json 最终持久化时,保留了"中间某一刻"的状态(359 万)而不是最终状态
- **这能解释 cash=299 万(对应 11 笔交易全部落库后的状态)+ 持仓 4 只(对应某一刻)**
- 但需要"15:30 模拟盘又触发"的证据 → **日志中没找到**(我搜了 6/26 15:00 之后,没有 sim_trader 日志)

**最可能的路径(我的判断)**: A 或 C 之一,但**缺少 6/26 14:54:23 到 6/27 00:31 之间的 state.json 写入日志**,无法 100% 确认。

## 六、修复建议(独立建议,与原报告不同)

### ❌ 不要做的事(原报告建议)

1. **不要"补 4 只持仓的 trade 记录"** —— "4 只"是基于错误数字推的,补了会让 state.json 更错
2. **不要急着改 sell_phase** —— 它不是当前 bug 源头(6/26 cron 跑成功了)
3. **不要先迁 DuckDB** —— 那是长期工程,不是止血措施

### ✅ 立即可做(我的建议)

1. **删除 state.json 里 6/26 那条 equity_curve 记录**
   - 当前:`{'date': '2026-06-26', 'equity': 3597707.64, 'cash': 2993728.64, 'pos': 4}`
   - 替换:基于 6/26 14:54:23 日志重建,真实值应是 `equity=1486078 cash=1350782 pos=3`
2. **添加诊断日志**:
   - `record()` 入口打印 `self.cash`、`self.position_count`、`len(self.positions)`
   - `_fill_missing_snapshots` 入口打印 `self.cash`、`len(self.positions)`、补录日期
   - `save_equity_point` 入口打印完整入参
3. **加一致性校验**:
   - 每次 record() 后,检查 `equity == cash + sum(positions market_value)`,误差 >1% 报警
   - 每次 save 前,检查 `last_equity_curve.cash ≈ self.cash`,差异 >10% 报警

### ✅ 中期改进

1. 给 equity_curve 加 `record_source` 字段(`'record'` / `'fill_missing'` / `'manual'`),便于追溯
2. 给 state.json 加写入时间戳,出问题时能定位"哪个时刻写入了错的数字"
3. 给关键操作加单元测试:`sell_phase` 中断、`record()` 重复调用、`_fill_missing_snapshots` 在不同 self.cash 下的输出
