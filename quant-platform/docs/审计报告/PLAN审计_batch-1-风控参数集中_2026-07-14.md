## 三、🏛️ 架构分析师发现

### 🔴 C1（CRITICAL，阻塞交付）：dataclass 传给期望 dict 的 build_context → 核心交易全崩

**现象**：plan 把 `engine.py` / `intraday_monitor.py` / `exit_monitor.py` 三处的 `sim_params`/`params` 从 **dict** 改成 `load_risk_params()` 返回的 **frozen dataclass**（plan 第 127、140、152 行）。但下游规则引擎用 dict API 访问。

**证据**：
- `app/backtest/exit_rules.py:399` `tp_tiers = params.get("take_profit_tiers", [])`
- `app/backtest/exit_rules.py:420` `hard_stop=params.get("hard_stop", -0.06)`
- `app/backtest/exit_rules.py:422-430` 全部是 `params.get(...)`
- `app/sim_trader/engine.py:513` `build_context(pos, bar, hold_days, sim_params, use_high_for_tp=True)`
- `app/sim_trader/intraday_monitor.py:149` 同样传 dict
- `app/live_trader/exit_monitor.py:172` `build_context(pos_obj, bar, hold_days, params)`

**故障场景**：按 plan 执行后，`params` 变成 `RiskParams` frozen dataclass。dataclass **没有 `.get()` 方法**。模拟盘每日 `check_stops`、盘中监控 `_check_position`、实盘退出扫描，任一持仓触发检查时立即抛 `AttributeError: 'RiskParams' object has no attribute 'get'`。

**后果**：止盈止损判定全部失效 → 要么不卖（亏损无限放大），要么监控进程崩。这是资金安全级故障。

**根因**：plan 作者写"sim_params 是 dataclass，字段直接用 .hard_stop 等"（plan 第 128 行），**显然没读 build_context 源码**就下了结论。plan 通篇没提要改 build_context，也没提 dataclass 不能用 `.get()`。

---

### 🟠 H1（HIGH）：违背项目铁律"config.py 唯一真相源"，方向反了

**证据**：
- `CLAUDE.md` 项目规则、`app/config/schema.py:3` 注释明确写"按用户铁律:config.py 唯一真相源"
- memory `feedback_config_flow`：改参数必追踪 config.py → 前端 → 引擎完整链路
- plan 第 28 行目标：**"settings 优先读 → config.py 兜底"** —— 把 `app_setting.json`（settings）置于 `config.py` 之上

**冲突**：plan 的方向与项目既定铁律**直接相反**。后果是：在系统设置页（写 settings）改了参数 → 生效；但直接改 `config.py` 源码常量 → **不生效**（被 settings 优先覆盖）。这恰恰是项目历史上"假默认值"摩擦的翻版（见 memory `project_known_risks`）。

**现状反证 plan 的论据偏颇**：plan 第 19 行称"`load_risk_params()` 读 config.py、`_cfg()` 读 settings，数据源顺序不一致"。但实读 `app/sim_trader/config.py:19-21`：
```python
HARD_STOP = settings.get("backtest", "hard_stop", default=-0.06)  # config.py 自己也读 settings！
```
config.py 的常量**本身就来自 settings**（backtest 段）。真正的不一致是 **risk 段 vs backtest 段两段并存**（`core/settings.py:41-82` 的 `_check_risk_consistency` 专门告警这个漂移），不是"config.py vs settings"。plan 诊断对了"有漂移"，但归因到"config.py vs settings"不准确，且开的药方（settings 压过 config.py）违背铁律。

### 🟠 H2（HIGH）：take_profit_tiers fallback 返回模块级 list 引用未拷贝 → 污染全局常量（现状有保护，plan 倒退）

**证据**：
- 现状 `app/config/schema.py:54`：`take_profit_tiers=list(sc.TAKE_PROFIT_TIERS)` —— **做了拷贝**
- plan 的 `_g()`（plan 第 63-69 行）：`return getattr(_sc, key.upper(), default)` —— 返回 `config.TAKE_PROFIT_TIERS` 的**原始引用**，无拷贝

**故障场景**：当 `risk` 段缺 `take_profit_tiers` 键时，`_g` 返回 config.py 模块级 list 引用，塞进 frozen RiskParams。下游任何对 `params.take_profit_tiers.append/modify` 的操作（如 `mark_tier_triggered`、止盈档处理）会**污染 config.py 的 TAKE_PROFIT_TIERS 全局常量**，影响所有后续调用方。现状 schema 用 `list()` 拷贝规避了这点，plan 把保护去掉了。

## 四、⚙️ 功能分析师发现

### 🟠 C2（HIGH）：fallback 名字对不上 config.py 常量 + 假默认取代了"缺键报错"铁律

plan 第 64 行 `_g` 注释声称"读 settings → config.py 兜底"。但实测 plan 的 `_g(key)` 用 `getattr(_sc, key.upper(), default)` 去 config.py 取，而 `key` 与 config.py 常量名**大面积对不上**，fallback 根本读不到 config.py，只返回 plan 写死的 default：

| plan `_g(key, default)` | `key.upper()` 去 getattr | config.py 实际常量 | 命中？ |
|---|---|---|---|
| `("hard_stop_loss_pct", -6.0)` | HARD_STOP_LOSS_PCT | HARD_STOP | ❌ |
| `("trailing_stop_activate_pct", 5.0)` | TRAILING_STOP_ACTIVATE_PCT | TRAIL_ACTIVATE | ❌ |
| `("trailing_stop_drawdown_pct", 2.0)` | TRAILING_STOP_DRAWDOWN_PCT | TRAIL_DD | ❌ |
| `("time_exit_min_profit_pct", 3.0)` | TIME_EXIT_MIN_PROFIT_PCT | TIME_EXIT_PROFIT | ❌ |
| `("time_exit_force_days", 12)` | TIME_EXIT_FORCE_DAYS | TIME_FORCE_DAYS | ❌ |
| `("use_atr_stop", False)` | USE_ATR_STOP | USE_ATR_TRAIL | ❌ |
| `("atr_stop_multiplier", 1.0)` | ATR_STOP_MULTIPLIER | ATR_TRAIL_MULTIPLIER | ❌ |
| `("time_exit_days", 7)` | TIME_EXIT_DAYS | TIME_EXIT_DAYS | ✓ |
| `("first_day_exit_min_profit", 0.0)` | FIRST_DAY_EXIT_MIN_PROFIT | FIRST_DAY_EXIT_MIN_PROFIT | ✓ |
| `("take_profit_tiers", ...)` | TAKE_PROFIT_TIERS | TAKE_PROFIT_TIERS | ✓（见 H2） |

**两个真实问题：**

1. **假默认值偏离真值约 30%**：risk 段缺某百分比键时，fallback 返回 plan 写死的 default（`hard_stop → -6.0/100 = -0.06`），而非 config.py 真值（`HARD_STOP = -0.046`）。同理 `trail_activate → 0.05`（真值 0.039）、`trail_dd → 0.02`（真值 0.017）。止损线比真实配置宽松约 30%，亏损放大。正踩中项目反复强调的"假默认值"雷区（memory `project_known_risks`、`feedback_config_flow`、schema.py:42 注释）。

2. **违背 schema.py"缺键即报错"铁律（plan 引入的回归）**：现状 `app/config/schema.py:38-43` 对缺 config 常量直接 `raise RuntimeError`（注释明写"按用户铁律,缺键应直接报错,不允许假默认"）。plan 的 `_g` 改成 default 假默认——把 schema 下游从"缺键硬报错保护"降级为"缺键静默用错值"。原本配错会立刻崩让你发现，plan 后静默用 -0.06 你都不知道。

> **勘误**：本审计初稿曾误判为"百分比除两次错 100 倍"。复核发现：fallback 因 key 名对不上 config 常量，返回的是 default 而非 config 小数，**不发生双除法**；真实问题是"假默认偏离 + 取代缺键报错"。现有 `engine._cfg`（engine.py:493-498）有同样的 key 名失配 + 假默认（pre-existing），plan 把它推广到 schema 全下游（settings 8 个 @property、AI 优化器基线、simulate_one_trade）。

## 七、🤔 我额外想到的隐患

1. **DeprecationWarning 会变成运行时噪音**：plan 给 `schema.load_risk_params()` 加 DeprecationWarning，但 `core/settings.py:142-224` 的 8 个 @property 每次访问都调它。模拟盘/实盘每分钟轮询 → 每分钟刷 8 条 DeprecationWarning 到日志，淹没真问题。plan 鼓励"用新函数"却没改 settings.py 的 @property，"统一"没贯彻到底。

2. **frozen dataclass + 可变 list 字段 = 伪不可变**：plan 第 48 行 `frozen=True` 但 `take_profit_tiers: list` 可变。配合 H2（未拷贝），"不可变"承诺形同虚设。tests 想 mock 还得用 `dataclasses.replace`，plan 注释"tests 可直接 mock"过于乐观。

3. **reload 时序**：`apply_bt_to_system` 先改 config.py 模块变量（492-512）、再 `settings.reload()`（516）、再写 risk 段（518-530）、再 save。plan 后运行时只读 risk 段，config.py 模块变量的写入（492-512）对运行时**完全失效**——成了死代码。plan 没指出这点，留着会误导后人以为 config.py 写入生效。

4. **回测与实盘口径进一步分裂**：plan 后，运行时交易读 risk 段，回测默认值（default_bt_config）读 backtest 段快照。同一参数两个口径，若 risk 段和 backtest 段漂移（_check_risk_consistency 已证明会），**回测验证的策略参数 ≠ 实盘执行的参数**。这是量化系统最危险的分裂。

5. **无回滚预案**：plan 第 192-198 行"执行顺序"只讲怎么改，没讲改崩了怎么回滚。涉及 5 文件、核心交易路径，应有"改前 git tag / 分支、逐文件可独立 revert"的预案。违背 development-quality 规则 3 的"回滚预案"。

## 九、🔧 建议修复项（按优先级，供改 plan 用）

> 审计只给建议不擅自动手。以下是让 plan 可交付的必改项。

1. **【必修·C1】** dataclass 要么加 `.get()` 兼容方法（`def get(self,k,d=None): return getattr(self,k,d)`），要么三个调用方仍构造 dict 传给 build_context。**最稳妥**：`load_risk_params()` 同时提供 `as_dict()`，调用方 `sim_params = load_risk_params().as_dict()` 传给 build_context，dataclass 留给新代码用。
