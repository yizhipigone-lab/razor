## 静态扫描结果（grep 实跑）

### ✅ 无硬编码 secret
- 0 命中（grep 整个 app/ core/ 无 API key/password/token 字面量）
- `buy_signal_token` 配置值（来自 app_setting.json，非硬编）

### ✅ 无 SQL 注入
- 所有查询都参数化（`execute("... WHERE x=?", [v])`）
- 唯一字符串拼接：[sync_min5.py:217](app/data_manager/sync_min5.py#L217) f-string 拼 `time_col` + `sample_path` 给 `read_parquet()`——不是 SQL 注入向量（DuckDB read_parquet 不接受用户参数化），是**路径拼接**，MEDIUM 风险

### ✅ exec() 受保护（[engine.py:177](app/strategy_factory/engine.py#L177)）
- `safe_builtins` 白名单（abs/min/max/.../print，**不含** `os/exec/eval/open/__import__`）
- `__builtins__` 替换为 `safe_builtins`（关键防线）
- 3 次 AST 沙箱预检（[engine.py:103,138](app/strategy_factory/engine.py#L103) + [agents/strategy_coder.py:55](app/agents/strategy_coder.py#L55)）—— 双重保护

### ⚠️ API 层 16+ 处 `except Exception` 吞错（[backtest.py:569,795,943](app/api/backtest.py#L569) 等）
- **评价**：可接受（API 边界兜底返回 error 给前端）+ 风险（吞掉细节难调试）
- **建议**：统一错误处理（中间件）+ 结构化错误日志

### ⚠️ print() 滥用 13 处
- 集中在 `app/live_trader/main.py`（应该用 `log.info` / `log.warning`）
- 风格问题 LOW

## 🏛️ 架构分析师发现（architect agent 完整返）

### 1. 分层架构：混合架构（模块化单体+调度驱动），非真正事件驱动

- **EventEngine 是"假事件驱动"**（[core/event_engine.py:66-107](core/event_engine.py#L66)）—— 实际是**调用线程内同步分发器**。全仓库 `grep` 无 `emit/put/start` 调用，只有监控器注册监听。这是**命名误导**——后人看了以为有事件总线，其实是同步回调
- API/业务/数据层边界弱：路由直接操作 DuckDB（[api/market.py:55-65](app/api/market.py#L55)、[api/watchlist.py:25-29](app/api/watchlist.py#L25)），实盘路由直接用 `store._conn`（[live_trader/main.py:461-511](app/live_trader/main.py#L461)）
- 多个"上帝模块"：
  - **`database/duckdb_manager.py` 1410 行**（之前未发现，**比 live_trader/main.py 还大**）—— 全平台持久化根
  - `app/live_trader/main.py` 1350 行（实盘组合根 + 路由 + adapter）
  - `app/api/backtest.py` 966 行（任务+配置+历史管理混合）

### 🔴 HIGH — 依赖方向倒置与循环依赖

- `core.settings` **反向导入** `app.sim_trader.config`（[core/settings.py:40-81](core/settings.py#L40)），后者又导入 `core.settings` —— **违反分层方向**（core 不应依赖 app）
- 模拟盘引擎、实盘离场模块反向依赖 API 层交易日历（[exit_monitor.py:196-213](app/live_trader/exit_monitor.py#L196)）
- **影响**：未来重构 core 可能意外破坏 app 模块；模块边界名义清晰实则混乱

### 🔴 HIGH — 数据一致性：成交与持仓不在同一事务边界

**architect 强调的最大架构风险**：
> "最大架构风险是交易事实、订单状态与持仓投影缺少统一事务和幂等边界。QMT、live_deals、live_positions 在正常运行期间可能分叉，而现有对账主要负责检测和触发 kill switch，不负责形成强一致状态。"

具体证据：
- 回调先写 `live_deals`（[callback_handler.py:309-328](app/live_trader/callback_handler.py#L309)）
- 卖出投影"trade_id 已存在"即 return（幂等）
- **买入投影缺少同等的重复回报幂等边界**（[store.py:291-381](app/live_trader/store.py#L291)）—— 重复买入回报会**导致重复持仓**
- **store._write_to_db 捕获异常不向上传播**（[store.py:230-245](app/live_trader/store.py#L230)）—— 上层返回"成功"而 DB 写入失败，**资金计算错误风险**

### 🔴 HIGH — AI 优化状态变量无锁

- `_task_state/_stop_flag` 由 API 线程和后台线程共同读写（[ai_optimizer.py:35-66](app/backtest/ai_optimizer.py#L35)）—— **数据竞争** + 可能崩溃或错误停止
- 模拟盘 `_engine_lock` 只保护初始化和重置，**不保护**调度/手动执行/监控对同一引擎的并发操作

### ⚠️ MEDIUM — LiveScheduler 在事件循环中同步阻塞

- `_tick` 在 asyncio event loop 中**直接同步调用 QMT 和 DuckDB**（[scheduler.py:155-245](app/live_trader/scheduler.py#L155)）—— QMT 慢响应会**阻塞整个 8001 进程的 event loop**，WebSocket 推送全卡住

### ⚠️ MEDIUM — Store._conn 被多模块绕过

- `LiveTraderStore` 用 `_db_lock` 串行化（[store.py:32-47](app/live_trader/store.py#L32)），但 **API/审计/对账/pnl_engine 都直接访问 `store._conn`** 绕过锁（[reconciler.py:188-225](app/live_trader/reconciler.py#L188)、[pnl_engine.py:133-151](app/live_trader/pnl_engine.py#L133)）—— 锁形同虚设

### ⚠️ MEDIUM — 配置 5 个真相源

- 来源：`.env` 环境变量 + `app_setting.json` + `output/backtest_config.json` + 模块常量 + 运行时内存状态
- 风控三源漂移：`app.config.schema` 宣称 `sim_trader/config.py` 为唯一源，但模拟盘 import 时读 `backtest` 配置（[sim_trader/config.py:17-35](app/sim_trader/config.py#L17)），退出优先读 `risk` 段（[exit_monitor.py:215-235](app/live_trader/exit_monitor.py#L215)）
- 热更新分裂：cron/data 触发调度重载 / 模拟盘改 module-level 常量 / 实盘 frozen config 只迁少量字段到 RuntimeState

### ⚠️ MEDIUM — mode/kill switch 状态重复 + 矛盾

- `mode` 同时存在 frozen config 和 `RuntimeState`（[main.py:158-176](app/live_trader/main.py#L158)），后者可覆盖前者，但残留清理仍读 `config.mode`
- kill switch "只能人工解除" vs "调度器/启动自动解除" 两种状态转换语义**矛盾**（[main.py:358-372](app/live_trader/main.py#L358)）

### ⚠️ MEDIUM — 错误处理不规范

- 无统一异常信封：HTTP 200 + 空数组 / `{status:error}`（[api/watchlist.py:39-42](app/api/watchlist.py#L39)）—— 客户端难区分"无数据"和"出错"
- 大量静默降级 `except Exception: pass`（[core/settings.py:78-81](core/settings.py#L78)、[server/market/quotes.py:87-101](server/market/quotes.py#L87)）—— 业务错误被压缩成"无数据"

### 🔴 HIGH — `/api/trade` 是"假可用"（用户可能踩坑）

- `/api/trade` 路由走 `QMTGateway.buy/sell`（[api/trade.py:19-67](app/api/trade.py#L19)），但 `QMTGateway.buy/sell` 固定返回失败（[trader/gateways/qmt.py:40-48](app/trader/gateways/qmt.py#L40)）
- **真实下单在另一个 `/live/order` 边界**（8001 端口 live_trader）
- 风险：用户/开发者以为 `/api/trade` 能下单，实际不行——**隐藏陷阱**

### 🟡 LOW — 可观测性弱

- 日志**双轨**（Loguru + stdlib logging，格式不统一，sync_logger 与主 logger 分离）
- WebSocket 广播消息无统一 schema（各模块直接构造 dict）
- **无 metrics / 无 trace ID**（无 Prometheus/OpenTelemetry）
- `/health` 只返进程存活，**不校验 DuckDB/QMT/调度任务/回调积压** —— 监控盲区

### 🟡 LOW — 状态恢复语义不统一

- 启动会恢复在途订单 + 接管 QMT 持仓
- 但 append-only `deals.wal` 只有写入逻辑、**未发现回放入口**
- 清仓锁、调度执行标记、任务状态仍是**纯内存状态**（进程重启会丢）

### 🟡 LOW — 前后端"大泥球"

- 11 个 tab + 6 个 JS 文件（非 module 异构）
- 已通过 commit 6e232d5 + a847ec2 等改善，但整体仍是"大泥球"前端
- 维护性 LOW 风险（不像后端那么严重）

### ✅ 探索阶段已确认的好设计

1. **exec 沙箱**：`strategy_factory` 用 `ast_sandbox` + `safe_builtins` 双重保护（已 grep 确认）
2. **行情 4 源降级**：`quote_source.py` 统一封装
3. **风控三源自检**：`core/settings.py:39 _check_risk_consistency()`
4. **优雅关闭**：`/shutdown` + `stop.bat` 双杀兜底
5. **DUCKDB_READ_ONLY 开关**支持只读模式
