## 0. 核心原则(不可妥协)

1. **资金安全 > 自动化 > 性能**:宁可漏买漏卖,绝不误下单
2. **隔离优于复用**:账户/进程/DB/配置四独立,实盘与模拟盘物理隔离
3. **复用优于重写**:策略/风控/信号复用(`exit_rules`/`execution`/`bridge`),只替换成交流水
4. **可回放**:每笔实盘单 5 分钟内可回放"为什么下/为什么没下/为什么成交/为什么没成交"
5. **可一键停**:任何时刻 5 秒内切断真实下单(保留监控)
6. **多重保险**:kill switch + 风控 8 闸 + 清仓锁 + 熔断器 + dry-run + 对账,六重防线
7. **大白话不忽悠**:所有阈值、所有拒绝路径都可解释
8. **fail-fast**:风控参数缺失/QMT 断连/资源池耗尽,宁可停机不可带病运行

## 1. 背景与目标

### 1.1 业务背景

p9 量化平台已具备完整能力栈:回测、模拟盘、AI 优化、通达信桥接选股、数据同步。**缺的最后一块**:把模拟盘验证过的策略,真实下单到券商柜台。

| 目标 | 度量 |
|------|------|

### 3.2 与现有 `qmt_proxy_server.py` 的关系(单进程独占,避免资源池冲突)

**关键约束**:`xtquant` 通过共享内存与 `XtMiniQmt.exe` 通信,**资源池有限**。多个 Python 进程同时连接同一个 XtMiniQmt.exe,高频调用会触发 `WaitingFreeWriter`(MQ 实证,唯一恢复方式是重启)。因此 **v5.0 必须单进程独占 xtquant 连接**。

**决策**:`live_trader` 进程**接管** `qmt_proxy_server.py` 的全部职责(行情 + 下单 + 资金 + 持仓 + callback),`qmt_proxy_server.py` **标记 deprecated**(代码保留,不再启动)。

- **live_trader 进程内** `qmt_wrapper` 独占 xtquant 连接(行情 + 下单 + callback 回报)
- **Docker 端** `qmt_gateway` 改调 `live_trader:8001` 的行情端点(`/live/quotes`),不再调 `qmt_proxy:8081`
- **`qmt_proxy_server.py`** 保留源码(规则3 向后兼容),但 NSSM 不再启动;其 `send_order` 逻辑作为 `qmt_wrapper` 的参考蓝本
- **过渡期**(阶段0-1):`qmt_proxy_server.py` 仍可独立启动做行情验证,但**禁止与 live_trader 同时连接 xtquant**(启动脚本互斥检查)

**为什么不合并成一个文件**:`qmt_proxy_server.py` 是历史代码(486 行,无熔断/回调/风控),直接改它风险高(规则3)。`live_trader` 是全新模块,从设计上就包含熔断/回调/风控,演进路径更清晰。两者职责在 v5.0 由 live_trader 完整接管。

#### 3.2.1 与现有 QMTGateway(`app/trader/gateways/qmt.py`)的关系(v5.3 关键澄清)

> v5.0 原稿遗漏了 p9 已有的网关层,经 codex 评审指出后补齐(详见 §18.1)。p9 **已有一套完整 QMT 网关基础设施**:`app/trader/gateways/qmt.py`(QMTGateway 类,buy/sell/get_balance/get_position/get_realtime_quotes/get_stock_list/get_index_members)+ `core/gateway.py`(工厂,按 `active_gateway` 路由)+ `sim_trader/config.py:66` `BROKER_ENABLED` 开关 + `engine.py:608`/`intraday_monitor.py:200` 的 `if BROKER_ENABLED: get_gateway().sell()` 真实下单路径(开关当前关闭)。

**决策:QMTGateway 沿用,不废弃;但行情与下单职责分离。**

| 职责 | 路径 | 说明 |
|------|------|------|
| **行情查询** | QMTGateway 沿用,`proxy_url` 改指 `live_trader:8001/live/quotes` | Docker 端 sim_trader/前端的行情来源,从旧 `qmt_proxy:8081` 切到 live_trader。QMTGateway 不直连 xtquant,只是 live_trader 的 HTTP 前端 |
| **真实下单** | **只走 live_trader 的 qmt_wrapper**(直连 xtquant) | sim_trader 的 `BROKER_ENABLED` **永久保持 False**,模拟盘永远不下真单,只模拟扣减。真单唯一入口是 live_trader |
| **cancel_order** | live_trader 的 qmt_wrapper 实现;QMTGateway 的 stub(`qmt.py:114`)不补,因为 sim_trader 不需要撤真单 | 避免在 QMTGateway 重复实现 |

**边界红线(防三条 xtquant 路径)**:
- ❌ 禁止:QMTGateway 直连 xtquant(它只是 HTTP 前端)
- ❌ 禁止:sim_trader 的 `BROKER_ENABLED` 置 True(模拟盘永远模拟)
- ✅ 唯一 xtquant 直连者:live_trader 进程的 qmt_wrapper
- ✅ QMTGateway 的 4 层 XtAccount 兼容代码(`qmt_proxy_server.py:87-113`)抽到 `app/utils/xtquant_compat.py`,三处(proxy 历史代码/qmt_wrapper/QMTGateway)共用,不重复实现(详见 §18.8)

**这样 sim_trader 已验证的 `if BROKER_ENABLED: get_gateway()` 代码路径完整保留**(规则3 不破坏现有),只是开关永远关着;live_trader 复用同一套 `exit_rules` + `execution` + `intraday_monitor` 的 tick 驱动逻辑(复用度 ~92%,详见 §18.7),只把"模拟扣减"换成"qmt_wrapper 真实下单 + 清仓锁"。

### 3.3 与 sim_trader 并行

- 模拟盘继续走 Docker 端 `sim_trader`(模拟成交,`BROKER_ENABLED` 永久 False)
- 实盘走 Windows 端 `live_trader`(真实下单)
- 两套独立 DB(`quant.duckdb` vs `live_trader.duckdb`)、独立表前缀(`sim_*` vs `live_*`)
- **存储介质差异**(v5.3 补):sim_trader 用 JSON(`output/sim_trader/state.json`,CLAUDE.md 唯一真相源),live_trader 用 DuckDB(`data/live_trader/live_trader.duckdb`)。两套体系各自校验,互不干涉

#### 3.3.1 已有持仓接管策略(v5.4 POC 发现,用户决策)

> POC 验证发现账户 180056133 已有持仓:2 只 ETF(159226.SZ 486700份、159290.SZ 229200份,合计市值 ¥964,724),可用现金仅 ¥117。用户决策:**ETF 保留不动,既不买也不卖;策略只管新增股票**。

**持仓分类接管**:
| 持仓类型 | `managed` 字段 | 行为 |
|----------|---------------|------|
| **保留持仓**(如 ETF 159226/159290) | `false` | exit_rules 不触发、不买卖、不参与风控计算、不参与对账偏差判定(单独标记) |
| **策略持仓**(新增股票) | `true` | 完全受 exit_rules + RiskGate + 清仓锁管理 |

**启动时持仓接管流程**:
1. `query_stock_positions` 拉全部持仓
2. 对照 `live_positions` 已有记录(首次启动为空)
3. 配置文件 `live_trader.preserved_codes` 列出保留代码(如 `["159226.SZ","159290.SZ"]`)
4. 保留代码 → `managed=false` 写入 live_positions;其余 → `managed=true`
5. 后续 POC 验证脚本拉到的持仓,自动按配置分类

**风控口径**(对应闸门 3/4):
- 闸门 3(单只集中度):只算 `managed=true` 的单只持仓
- 闸门 4(总仓位):只算 `managed=true` 的总持仓
- **保留持仓(ETF)市值不计入风控分母**
- `LIVE_CAPITAL`:只管新增股票部分(用户决策),设为策略可用现金规模(需用户准备现金,见 §3.3.2)

**对账口径**(§5.9 Reconciler):
- 保留持仓参与"QMT vs live_positions"比对(确保不被意外买卖),但偏差不触发 kill switch(只告警)
- 策略持仓偏差按正常阈值判定

#### 3.3.2 资金现状提醒(待用户处理)

## 4. 部署架构

### 4.1 NSSM 守护(新增)

`live_trader` 主进程注册为 Windows 服务,进程崩溃自动拉起:

```bat
nssm install QuantLiveTrader "<venv313>\python.exe" -m uvicorn app.live_trader.main:app --host 127.0.0.1 --port 8001
nssm set QuantLiveTrader AppDirectory <p9_root>
nssm set QuantLiveTrader AppEnvironmentExtra "PYTHONUNBUFFERED=1" "QMT_USERDATA_PATH=D:\Program Files\XCXT\userdata_mini" "QMT_ACCOUNT_ID=<account>" "TZ=Asia/Shanghai"
nssm set QuantLiveTrader AppRotateFiles 1
nssm set QuantLiveTrader AppRotateBytes 10485760
nssm set QuantLiveTrader Start SERVICE_AUTO_START
```

**指数退避**(防 WaitingFreeWriter 死循环拉起磁盘满):进程内记录连续退出次数,退避序列 30s→60s→120s→240s→480s→960s→1800s,10 次后停止并告警(人工介入)。

### 5.1 qmt_wrapper(xtquant 适配层)

**职责**:封装所有 xtquant 调用,隔离 SDK 升级风险。

**关键设计**:
- **子线程实例化**:`XtQuantTrader` 在 daemon 子线程创建,避免劫持 uvicorn 主 asyncio loop
- **3 秒超时**:所有同步调用(`order_stock`/`cancel_order_stock`/`query_*`)经 `ThreadPoolExecutor` + `Future.result(timeout=3)`,超时抛 `QmtTimeoutError`
- **4 层 XtAccount 兼容**:`from xtquant.xttype import XtAccount` → `from xtquant.xttrader import XtAccount` → `getattr(xtquant,'XtAccount')` → MockXtAccount 兜底
- **subscribe 兼容**:try 整数 ID,except 降级 StockAccount 对象
- **getattr 取值**:所有 XtOrder/XtTrade/XtPosition 字段用 `getattr(obj,'field',default)`
- **代码格式化**:`_format_code`(6→.SH,0/3→.SZ,8/4/920→.BJ)

### 5.2 ConnectionManager(连接 + 熔断 + 强退)

照搬 MQ `connection_manager.py` 设计并加强:

- **两层连接**:`xtdata.connect()`(行情基础)+ `XtQuantTrader`(交易)
- **callback 在 start 前注册**(硬约束)
- **熔断器**:连续 3 次失败→30s 拒绝→half-open 试恢复;成功重置
- **WaitingFreeWriter 强退**:`os._exit(1)` + 指数退避(记录到 `data/live_trader/restart_counter.json`,NSSM 拉起时读取决定是否继续退避)
- **on_disconnected 触发 kill switch**(非仅日志)
- **单连接架构**:不暴露 session_id 接口(从根上避免 MQ 的 `get_qmt_trader_by_session_id` bug)

### 5.3 Callback Handler(max_workers=1 硬约束)

**核心约束**:xtquant callback executor 是 `max_workers=1`(串行),callback 方法体**只做**:
1. `getattr(obj,'field',default)` 数据提取(< 100μs)
2. 派发到独立 `db_executor`(有界,`max_workers=4`)做 DB 写入
3. `try/except + log.error`,异常绝不逃出

**7 个回调**:

| 回调 | 处理 | DB 写入(派发) | 通知 |
|------|------|----------------|------|
| `on_disconnected` | 激活 kill switch | audit(qmt_disconnected) | 企业微信告警 |
| `on_account_status` | 异常状态→kill switch | audit | 告警 |
| `on_stock_order` | 状态转换校验 + 终态检查 | UPDATE live_orders | WebSocket(56/57 抑制) |
| `on_stock_trade` | 成交记录 + 盈亏重算 | INSERT live_deals + UPDATE order | WebSocket + 企业微信 |
| `on_order_error` | 废单处理 | UPDATE live_orders(status=57) + audit | WebSocket |
| `on_cancel_error` | 撤单失败 | audit | 告警 |
| `on_order_stock_async_response` | 维护 order_id→seq 映射(带 LRU 上限 10000) | audit | — |

**幂等 + 状态转换校验**:UPDATE 前先 SELECT,终态 `{53,54,56,57}` 后不再处理;非法转换(如 57→50)拒绝并 audit。

### 5.4 ClearanceLock(清仓锁)

照搬 MQ `clearance-lock-service.ts` + Redis 接口预留:

- **Key**:`(env, account, code)` 三元组
- **实现**:内存 `dict` + `threading.Lock` + 双索引(主 Map + order_id→key 反查)
- **TTL**:300s 兜底(覆盖 5 个 60s 轮询周期)
- **acquire**:撤单/挂新单/强平 5 类动作前
- **release**:成交回调 / 错误回调 / 异常路径,`release_by_order_id` 幂等
- **离场规则检查**:evaluate 阶段 `is_locked(code)` 跳过
- **接口**:`IClearanceLock` 抽象,内存实现 + Redis 实现预留(`SET NX EX 300`)

### 5.5 KillSwitch(一键停)

- **4 触发**:Web 按钮 / API POST / `touch .kill_switch` 文件 / 自动(QMT 断连、连续 5 单被拒、日亏 3%)
- **三重状态**:`live_killswitch` 表(DB)+ `.kill_switch` 文件 + 内存标志,任一触发即生效
- **效果**:所有 sell_phase/buy_phase/intraday_monitor 静默退出,不下任何新单(已挂单保留,可手动撤)
- **解除**:必须人工 Web 确认,系统不自动解除

### 5.6 RiskGate(8 闸门事前风控)

**事前检查**(不是事后),任意一闸失败即拒绝本次下单 + audit:

| # | 闸门 | buy | sell | 阈值(默认,按 LIVE_CAPITAL 比例) | 来源 |
|---|------|-----|------|------|------|
| 1 | 单笔金额 | ✅ | ✅ | ≤ `max_single_trade_pct`(默认 20%,实际受 `trading.max_buy_amount=1万` 即 10% 取严)× 资金 | 新建 live_trader/config.py |
| 2 | 现金保留 | ✅ | ❌ | 买入后现金 ≥ `cash_reserve_pct`(默认 10%) | 新建 |
| 3 | 单只集中度(含在途) | ✅ | ❌ | 单只(实际持仓 **+ 在途买入预扣**) ≤ `max_position_pct`(默认 30%) | 新建 |
| 4 | 总仓位(含在途) | ✅ | ❌ | 总持仓(实际 **+ 在途买入预扣**) ≤ `max_total_position_pct`(默认 90%) | 新建 |
| 5a | 日亏损软熔断 | ✅(禁) | ❌(允许止损) | 日亏 ≥ `daily_loss_halt_pct`(默认 3%)禁 buy;**QMT 缺价时 fail-safe 禁买**(H1) | 新建 |
| 5b | 单笔最大亏损 | ✅(禁该只) | ❌ | 单只浮亏 ≥ `max_single_loss_pct`(默认 5%)禁该只再买 | 新建(v5.3) |
| 6 | 启动自检 | ✅ | ✅ | QMT 连接 + 风控参数非零 + DB 可写 | 新建 |
| 7 | 连续拒绝(分类+时间窗) | ✅ | ✅ | **5 分钟内**连续 5 单 risk/broker 拒绝→kill switch;market/code 只记 audit;dry-run 整体不计 | 新建 |
| 8 | kill switch | ✅ | ✅ | 激活时全拒 | 新建 |
| **9** | **T+1 可卖校验** | ❌ | ✅ | 卖出量 ≤ `can_use_volume`(QMT 返回,已剔除当日买入冻结);`today > entry_date` | 复用 execution.py:50 |

**关键**:
- 闸门 2/3/4 只对 buy,sell 不查(止损卖出不应被"现金不足/集中度超限"误拒)
- **闸门 3/4 含在途买入预扣**(C1 修复):A 股异步撮合,下单到成交回调有几秒延迟,连续下多笔时若只看实际持仓会超买。下单成功(seq>0)即在 `live_positions.pending_buy_volume` 冻结名义敞口,闸门用 `实际持仓 + 在途预扣` 计算,成交回调后释放预扣换实际持仓。**买入侧也走 ClearanceLock**(同一 code 有在途买单时后续买单串行、重算额度)
- **闸门 5a fail-safe**(H1):QMT 行情缺失时浮亏算不准,不能因"算不出亏损"放行,必须保守禁买
- **闸门 7 时间窗**(H4):早盘 9:30 柜台未完全 ready 时 broker 类拒绝是瞬态,5 分钟窗口 + 分类避免误杀一整天
- **闸门 9 T+1**(H6):卖出必须校验 `can_use_volume`,当日买入冻结不可卖

### 5.7 ExitMonitor(离场监控,复用 8 规则)

**双驱动**:
- **定时驱动**:默认 60s 扫描持仓(APScheduler),可前端配置
- **tick 驱动**:复用 `sim_trader/intraday_monitor.py` 的 tick 事件,触发即检查

**复用**:`app/backtest/exit_rules.py` 的 8 条规则 + `build_context` + `adjust_for_gap`(除权跳空保护)。

**与 sim_trader 的差异**:
- sim_trader:规则触发→内存扣减(execute_sell)
- live_trader:规则触发→清仓锁 acquire→ack 轮询撤在途单→刷持仓→RiskGate(sell)→qmt_wrapper.order_stock→callback 更新

**行情**:用 QMT 实时价(`build_live_snapshot`),QMT 失败则该股票标记 `source=partial` 跳过决策(不退回腾讯,因为交易决策不容错,缺价就等下一轮)。

### 5.8 PnlEngine(buildSimpleCycles 移植)

移植 MQ `trade-logs-service.ts:48-221` 的交易闭环算法:

- 按 code 分组,按时间升序遍历 `live_deals`
- 用 `order_type`(23=买,24=卖)判断方向(**不用 direction**)
- 累积净仓 `net`,净仓归零=周期闭合
- 加权均价 = `sum(price*vol)/sum(vol)`
- 盈亏 = `sum(卖) - sum(买)`(仅闭合周期);未闭合周期保持 ongoing,用于实时成本

**与 sim_trader 简单减法的差异**:多次加仓后均价更准;支持部分卖出后的剩余成本重算。

### 5.9 Reconciler(对账引擎)

**4 时点**:09:35 / 11:30 / 14:55 / 15:05 触发三方比对:

```
A = QMT 实时持仓(query_stock_positions)
B = live_holdings_backup 最新归档
C = live_deals 还原(buildSimpleCycles)
比对 A vs B vs C:
  股数偏差 > 100 股 → CRITICAL 告警 + kill switch
  市值偏差 > 10%   → CRITICAL 告警 + kill switch
  小偏差 → INFO 记录
```

**双数据源**:主 `live_deals`(实时回调)+ 备 `live_deals_backup`(归档),基于 `trade_id` 去重(防 QMT 回报覆盖)。

## 6. 数据模型(`live_trader.duckdb`)

独立 DB 文件,与 `quant.duckdb` 物理隔离。对账用 DuckDB `ATTACH` 跨库查询。

| 表 | 主键 | 关键字段 | 说明 |
|----|------|----------|------|
| `live_orders` | order_id | code, direction, volume, price, price_type, status(int), status_msg, seq, **client_order_id(幂等键,唯一索引)**, **mode(live/dry-run,NOT NULL CHECK)**, strategy_name, order_remark, terminal, created_at, updated_at, finished_at | 委托主表。`client_order_id` 防 C3 跨机重单;`mode` v5.3 取代独立 dry-run 表 |
| `live_deals` | trade_id | order_id, code, direction, filled_volume, filled_price, filled_amount, commission, **mode**, traded_at | 成交流水 |
| `live_positions` | code | volume, can_use_volume, frozen_volume, **pending_buy_volume(在途买入预扣,C1)**, avg_cost, last_price, market_value, float_profit, profit_rate, peak_price, sell_count, entry_date, **managed(bool,C1.1 保留持仓标记)** | 持仓(本地缓存,QMT 为准;`pending_buy_volume` 防超买;`managed=false` 的保留持仓如 ETF 不参与策略/风控/对账偏差判定,见 §3.3.1) |
| `live_positions_audit` | id | timestamp, code, local_volume, qmt_volume, diff_volume, diff_value, source(callback/reconcile/manual), resolved | v5.3 Reconciler 偏差记录(不回写 live_positions) |
| `live_holdings_backup` | (date, code) | 快照字段同 positions + daily_high, daily_low | 每日 EOD 归档(双数据源备源) |
| `live_deals_backup` | (date, trade_id) | 同 live_deals | 成交归档(防 QMT 覆盖) |
| `live_assets_backup` | (date, time) | cash, frozen_cash, market_value, total_asset(time 分钟级,当日首条精确 09:30) | 资产归档(v5.3 字段精确) |
| `live_audit` | id(ts) | action, code, order_id, gate_result, reason, snapshot | 审计(每笔决策可回放) |
| `live_killswitch` | id | activated_at, reason, source, released_at | kill switch 历史 |
| `live_equity` | date | total_equity, cash, market_value, source(full/partial), **algo(simple/cycles,v5.3 渐进式)** | 净值曲线(复用 sim_trader 可信度保护) |
| `live_cycles` | (cycle_id, code) | status(ongoing/closed), buy_avg_price, sell_avg_price, pnl, pnl_pct | v5.3 buildSimpleCycles 输出(渐进式,与 live_equity 并行) |

**写约束**(v5.3 两层 buffer,取代 v5.2 含糊表述):
- **L1 in-process queue**:`collections.deque(maxlen=2000)`,callback 写入 < 100μs(put_nowait + return)
- **L2 单线程 flusher**:`ThreadPoolExecutor(max_workers=1)`,每 100ms 排空 queue 批量 INSERT
- **终态订单(53/54/56/57)同步落盘**(C2/H2 修复):不走 L1/L2,直接同步写 DB,防 `os._exit` 丢数据
- **强退前紧急 flush**:`os._exit(1)` 前尽力 flush deque(500ms 超时),或 L1 同时写 append-only WAL 文件(`data/live_trader/deals.wal`),重启从 WAL 补
- 独立 DB 避免与模拟盘写竞争;DuckDB 用事务

**存储介质差异**(v5.3):sim_trader 用 JSON(`output/sim_trader/state.json`),live_trader 用 DuckDB(`data/live_trader/live_trader.duckdb`),两套体系各自校验。`data/live_trader/*` 已被现有 `.gitignore` 的 `data/` 通配覆盖,无需额外配置。

## 7. 关键流程

### 7.1 下单流程(buy 为例)

> **C1/C3 修复**:买入侧加在途预扣 + 买入锁防超买;跨机下单带幂等键防漏/重单。

```
1. 信号源(screener TDX 选股 / 手动 Web / 定时 sell_phase)
   → 构造 OrderIntent(code, direction=buy, volume, price, strategy, terminal)
   → 生成 client_order_id = hash(strategy+code+date+seq)  [C3 幂等键]
2. 幂等检查(C3):查 live_orders.client_order_id 是否已存在
   存在 → 返回原结果,不重复下单(防跨机 HTTP 超时重试导致重单)
3. RiskGate.check(intent):9 闸门
   闸门 3/4 用 [实际持仓 + 在途买入预扣(pending_buy_volume)] 计算  [C1]
   失败 → audit(拒绝原因,带 rejection_reason_category) + 闸门7计数(5分钟窗,risk/broker 才计)
   通过 → 继续
4. ClearanceLock.acquire(env, account, code)  [买入侧也加锁,C1]
   已锁(有在途买单)→ 等待/串行,重算额度
5. execution.prepare:can_buy(涨停封板?) + calc_buy_cost + 代码格式化
6. qmt_wrapper.order_stock_async(...):子线程 + 3s 超时
   返回 seq ≤ 0 → audit(失败) + release lock
   返回 seq > 0 → INSERT live_orders(status=50, seq, client_order_id, mode)
                 + 冻结 pending_buy_volume += volume  [C1 在途预扣]
7. Callback on_order_stock_async_response:记录 order_id→seq 映射(终态后立即删,M3)
8. Callback on_stock_order:状态转换校验(非法转换拒绝) → UPDATE live_orders
9. Callback on_stock_trade(status=56):【终态同步落盘,H2】INSERT live_deals
   + pending_buy_volume -= filled_volume  [释放预扣换实际持仓]
   + buildSimpleCycles 重算盈亏 + release_by_order_id + WebSocket + 企业微信
10. Reconciler 在下个时点三方比对(只写 live_positions_audit,不回写,§18.2)
```

**跨机超时语义**(C3):Docker→Windows 下单 HTTP 超时 = 状态未知,Docker 端**不自动重试**,转为查询 `GET /live/orders/{client_order_id}` 确认状态后再决定。`client_order_id` 唯一索引保证即使重试也不会重复下单。

### 7.2 撤单流程(ack 轮询)

```
1. ClearanceLock.acquire(env, account, code)
2. qmt_wrapper.cancel_order_stock(account, order_id):3s 超时
   返回 0 → 进入 ack 轮询
   返回 -1/-3 → audit + release lock
3. ack 轮询:每 200ms 查 query_stock_orders(order_id),直到终态 {53,54,56,57}
   超时 5s 未终态 → 熔断器计数 + 告警
4. 终态后:刷持仓(query_stock_positions)→ release lock
```

**替代 sleep(1500)**:避免 stale can_use_volume 导致卖不全。

### 7.3 离场监控流程

> **时点约束**(详见 §16.3):实盘 sell_phase 提前到 **14:50** 触发;**14:55 后只撤不挂**(防进收盘集合竞价);**14:57 后强制清仓**(仅限仍需止损持仓)。时点参数化 `sell_phase_start`/`no_new_order_after`/`force_market_after`。
>
> **C2 修复(跌停不可成交性)**:A 股跌停时市价单**不保证成交**,只是排队。强平前必须先判断跌停/停牌/一字板,这类票市价清仓无意义,改为 audit + 告警"明日开盘优先处理",不盲目挂单制造废单。

```
1. 定时(60s)或 tick 触发;14:50 进入 sell_phase
2. query_stock_positions → 构建持仓快照(build_live_snapshot, QMT 实时价)
3. 对每只持仓:exit_rules.check(ctx) → ExitAction?
   命中 → ClearanceLock.acquire → 撤在途单(ack 轮询) → 刷持仓
        → calc_sell_target_shares_by_pct(板块取整:主板100/科创200/北交100)
        → RiskGate.check(sell intent)(闸门 1/6/7/8/9,闸门9校验 can_use_volume T+1)
        → 跌停/停牌/一字板判断(C2):
            已跌停(last_price ≤ 跌停价)或停牌或一字板 →
                不挂单,audit("跌停无法止损,明日开盘优先处理")+ 企业微信告警
        → 若 ≥ 14:55:只撤不挂(跳过新卖单)
        → 若 ≥ 14:57 且需止损 且 未跌停:
            强制市价单(最优五档即时成交剩余撤销,xtconstant.MARKET_PEER_PRICE_FIRST)
            [固化 price_type,见 §8;跌停票已在上面跳过]
        → 否则:qmt_wrapper.order_stock_async(sell, price_type=FIX_PRICE 限价) → 等回调
4. 全部处理完 → 归档(assets + positions + deals 串行)
```

**市价单类型固化**(C2,§8 补充):A 股实际可用市价类型有限,`price_type` 枚举固化为:
- `xtconstant.FIX_PRICE`(限价,price 字段填委托价)
- `xtconstant.MARKET_PEER_PRICE_FIRST`(对手方最优价格,常用于止损快成交)
- `xtconstant.MARKET_SH_CONVERT_5_CANCEL`(最优五档即时成交剩余撤销)
- **禁止**用"任意市价单"模糊表述;`qmt_proxy_server.py:272` 现用 `STOCK_BUY/SELL` 是 order_type 非 price_type,实盘必须显式传 price_type

### 7.4 kill switch 流程

```
触发(Web/API/文件/自动) → 三重状态置位(DB+文件+内存)
  → 所有 sell_phase/buy_phase/intraday_monitor 检测到标志 → 静默退出
  → 已挂单保留(用户可手动撤)
  → 企业微信告警
解除:Web 人工确认 → 清除三重状态 → audit
```

| 资源池耗尽 | WaitingFreeWriter → os._exit(1) → 指数退避拉起 |
| 进程崩溃 | NSSM 自动拉起,启动时从 live_orders 恢复在途订单状态 |
| 网络断 | 熔断器 3 次失败 → 30s 拒绝 → half-open 试恢复 |
| 数据不一致 | Reconciler 偏差告警 → kill switch → 人工核查 |
| 误下单 | kill switch 停新单 + 手动撤已挂单 + audit 回放 |
| 灾难恢复 | 每日 23:30 备份 live_trader.duckdb + 日志归档 Parquet,30 天清理 |

**回滚预案**:`git status` 评估改动,`live_trader` 是新模块不影响现有;`qmt_proxy_server.py` 演进保留旧路径;一旦破坏现有功能立即 `git checkout`。

## 16. v5.1 修订(自检逻辑漏洞迭代)

> 本节是规则2"出结果后自检并迭代"的产物。v5.0 初稿完成后,主动挑逻辑漏洞 12 项,其中 CRITICAL 1 项 / HIGH 4 项 / MEDIUM 3 项已修复,LOW 4 项记录备查。

### 16.1 [CRITICAL] 双进程 xtquant 资源池冲突 → 单进程独占(已改正文 §3.2)
**漏洞**:v5.0 初稿让 `live_trader` 和 `qmt_proxy_server.py` 两个进程都连 xtquant。xtquant 共享内存资源池有限,多进程高频调用必触发 `WaitingFreeWriter`(MQ 实证),且 `os._exit(1)` 后两进程互相不知道,导致循环崩溃。
**修复**:`live_trader` 单进程独占 xtquant(行情+下单+callback 全接管),`qmt_proxy_server.py` 标记 deprecated 不再启动,Docker 端 `qmt_gateway` 改调 `live_trader:8001`。启动互斥检查见 §16.8。

### 16.2 [HIGH] dry-run 数据隔离(统一为独立表)
**漏洞**:v5.0 §13 阶段1 说"写 `live_orders_dryrun`",但 §6 数据模型表清单未列 dry-run 表,验收清单只说"`live_orders` 行数=0",未明确 dry-run 数据落点。
**修复**:明确 dry-run 模式写入独立表 `live_orders_dryrun` / `live_deals_dryrun`(与 `live_orders`/`live_deals` 物理隔离,绝不混写)。验收:`SELECT COUNT(*) FROM live_orders` 在 dry-run 期间必须 = 0。dry-run 切 live 需手动 `--promote` 确认,系统不自动迁移 dry-run 数据。

### 16.3 [HIGH] sell_phase 时点提前 + 收盘竞价保护
**漏洞**:v5.0 沿用 sim_trader 的 14:53 sell_phase(`app/sim_trader/config.py:50` `SELL_TIME="14:53"`,engine.py 注释写的 14:52 是过期注释),但实盘需 ack 轮询(撤单+重挂),14:53→15:00 仅 7 分钟,撤单 ack 超时 5s + 重挂 + 成交确认可能来不及;且 14:57 后挂限价单可能进收盘集合竞价,成交价不可控。
**修复**:
- 实盘 sell_phase 提前到 **14:50** 触发,留足 10 分钟
- **14:55 后只撤不挂**:已挂单可撤,但不再挂新卖单(防进收盘竞价)
- **14:57 后强制市价清仓**:仅对仍需止损的持仓,用对手最优市价单确保成交
- 时点参数化(`sell_phase_start`/`no_new_order_after`/`force_market_after`),可配

### 16.4 [HIGH] 日亏损软熔断基准明确
**漏洞**:v5.0 §5.6 闸门5"日亏 3% 禁 buy"未明确"日亏"计算口径。若只算已实现盈亏,浮亏持仓不计入,则大跌时仍会开新仓。
**修复**:日亏 = 当日已实现盈亏(已平仓)+ 当日浮动盈亏(未平仓,基于 QMT 实时价 × buildSimpleCycles 均价)。基准 = 当日开盘总资产(`live_assets_backup` 当日首条)。日亏 3% 禁 buy 允许 sell,次日 09:30 自动恢复。

### 16.5 [HIGH] 持仓真相优先级 + 不一致修复
**漏洞**:v5.0 `live_positions` 是本地缓存,QMT 才是真相,但未说明对账发现不一致后如何修复本地缓存。callback 丢失会导致本地缓存与 QMT 偏差。
**修复**:持仓真相优先级 = **QMT 回报 > 本地 live_positions 缓存**。Reconciler 4 时点对账发现不一致时:以 QMT `query_stock_positions` 为准刷新 `live_positions` + 写 audit。若偏差 > 100 股或 > 10% 市值,刷新后仍激活 kill switch(防 QMT 自身有问题)。

### 16.6 [MEDIUM] 清仓锁 TTL 兜底后的状态检查
**漏洞**:v5.0 §5.4 清仓锁 TTL 300s 兜底,但若 ack 轮询超时(5s)后订单仍在途,TTL 到期自动释放,下一轮可能又挂新单,race 重现。
**修复**:TTL 触发释放前,先查订单状态(`query_stock_orders`):若仍非终态,则**不释放**,重新 acquire 并延长 TTL(最多延 2 次=900s);若已终态则正常释放。TTL 是"异常兜底"不是"正常释放路径",正常释放靠终态回调。

### 16.7 [MEDIUM] 盈亏重算数据源(不依赖归档)
**漏洞**:v5.0 §5.3 callback `on_stock_trade` 盈亏重算调 buildSimpleCycles,但若读 `live_deals_backup` 归档表(有延迟),成交回调瞬间算不准。
**修复**:盈亏重算数据源 = **内存 deals 缓存(近期 N 笔)+ DB `live_deals`(实时写入)**,不读归档表。归档表仅用于 Reconciler 事后对账和跨日盈亏。内存缓存用 `collections.deque(maxlen=500)` 按 code 分桶。

### 16.8 [MEDIUM] 启动互斥检查(防双进程)
**漏洞**:v5.0 §16.1 单进程独占,但若用户误启动 `qmt_proxy_server.py` + `live_trader` 两个进程,仍会资源池冲突。
**修复**:`live_trader` 启动时检测:(1) 端口 8081 是否在监听(`qmt_proxy_server` 标志);(2) `data/live_trader/live.lock` 文件锁是否存在。若发现 `qmt_proxy_server` 在跑,拒绝启动 + 企业微信告警"请先停止 qmt_proxy_server"。`live.lock` 用 `portalocker` 跨进程锁,NSSM 拉起时自动获取,异常退出时释放。

### 16.9 LOW 项(记录备查,不阻断)
- 闸门7"连续拒绝5次→kill switch":需排除 dry-run 模式的拒绝(否则 dry-run 调参时频繁误触发)
- `order_id_to_seq_map` LRU 上限 10000:长跑 1 年约 5000 单,够用,但仍需定期清理已终态
- 时区 `TZ=Asia/Shanghai`:已在 NSSM 环境变量设置,但 Python 内 `datetime.now()` 仍建议用 `pytz` 显式
- 企业微信频控 errcode=45009:重试 5 次后丢弃并写 audit(不阻塞主流程)

### 17.1 [P0] 订单状态恢复流程(响应 HIGH-3)

**专家指出**:§12 只说"从 live_orders 恢复在途订单状态",但没说怎么恢复。进程崩溃后,QMT 柜台的在途订单可能已成交/撤单/废单,只读 live_orders 拿到的是过时状态。

**修复**:新增"启动恢复流程"(ConnectionManager 连接成功后、进入主循环前执行):

```
启动恢复流程(reconcile_on_startup):
1. 读 live_orders 中 status NOT IN (53,54,56,57) 的在途订单(即崩溃前未终态的)
2. 调 query_stock_orders(account, cancelable_only=False) 从 QMT 拉最新状态
3. 逐单比对:
   a. 状态未变 → 继续监听
   b. 状态变为 56(已成)→ 补写:INSERT live_deals + buildSimpleCycles 重算盈亏
                              + release_by_order_id + WebSocket + 企业微信
   c. 状态变为 53/54(部撤/已撤)→ UPDATE live_orders + release_by_order_id
   d. 状态变为 57(废单)→ UPDATE live_orders + audit + release_by_order_id
   e. QMT 中已查不到该订单 → 标记 status=255(未知)+ 告警人工核查
4. 写"状态恢复报告"到 live_audit(action=startup_reconcile,列出状态变化的订单)
5. 若有订单进入 e 分支(查不到)→ 激活 kill switch,等人工确认
```

**关键约束**:恢复流程在 kill switch 检查之前完成,但恢复期间不下任何新单(启动锁)。恢复完成后才解除 kill switch(若启动时 kill switch 未激活)。

**写入位置**:正文 §5.2 ConnectionManager 补充"启动恢复"职责;§12 应急表"进程崩溃"行补充"→ 启动恢复流程(§17.1)"。

### 17.2 [P1] DuckDB 并发写策略(响应 HIGH-2)

**专家指出**:DuckDB 是单写者模型,7 个 callback 密集触发 + 定时写入会产生写锁竞争。专家自检后把严重度从 CRITICAL 降为 HIGH(DuckDB 内部有 WAL+MVCC,多线程短 INSERT 会排队而非直接失败)。

**采纳专家调整后的方案**。补充 §6:

```
DuckDB 并发写策略(§6 补充):
1. 所有 callback 写入经 db_executor(max_workers=4 有界线程池)串行化
   → 同一时刻最多 1 个线程在写 DuckDB(配合 threading.Lock 显式串行化写事务)
2. 写事务短小:单次 INSERT/UPDATE 不跨多表,不持有写锁做耗时操作
3. 高频路径(on_stock_order/on_stock_trade)双缓冲:
   - callback 先写内存 buffer(collections.deque,按 code 分桶,maxlen=500)
   - 专属 flusher 协程每 1s 批量 flush 到 DuckDB(单事务批量 INSERT)
   - 终态订单(53/54/56/57)立即 flush,不等 1s 周期
4. 对账/归档等定时写入避开 callback 高频时段(如 14:50-15:00 不归档)
5. 监控写锁等待时长,> 200ms 告警(可能是长事务阻塞)
```

**为什么不直接换 SQLite/Postgres**:DuckDB 与现有 sim_trader/backtest 一致(规则3 不破坏现有),且 OLAP 分析读性能好(对账跨日查询)。双缓冲方案能消化 callback 突发写入。

### 20.5 dry-run 残留清理逻辑(本轮新增,§18.3 严格保护落地)

Web 验证发现:dry-run mock 下单会留下虚拟持仓(QMT 实际没有),切 live 前必须清理。新增 `_cleanup_dryrun_residue`(main.py):

**清理规则**:
- 拉本地 live_positions + QMT 实际持仓
- 本地 `managed=true` 但 QMT 没有的 → 删除(dry-run 残留)
- 保留持仓(`managed=false` ETF)不动,即使 QMT 没有也不删(可能临时查不到)
- dry-run 模式:额外清理 `live_orders`/`live_deals` 中 mode='dry-run' 的记录(每次启动清)
- live 模式:发现 managed=true 残留 → 清理 + 告警(不应出现,需人工核查)

**验证结果**(本轮):
- 启动前:600000.SH 残留(local=200, qmt=0, WARN 偏差)
- 启动后:日志 `清理 dry-run 残留持仓: 600000.SH` + `清理 dry-run 残留委托和成交`
- 启动后 positions 只剩 2 只 ETF,orders 空,reconcile 0 偏差(全 INFO)
