## 1. MQ 实盘架构全景

MQ 的实盘交易系统由三个独立服务组成,**职责分明**:

```
┌─────────────────────────────────────────────────────────────┐
│  x-tdxqmt (Python FastAPI, :8002)  通达信选股 + 回测引擎      │
│  走通达信 TQ 通道(tqcenter/TPythClient.dll),不调 xtquant    │
│  含 exit_rule_engine(5条规则)+ VBT 撮合 + Numba 加速        │
└─────────────────────────────────────────────────────────────┘
                          ↓ 生成买入信号
┌─────────────────────────────────────────────────────────────┐
│  x-server (TypeScript Midway, :8001)  业务中台 / 实盘大脑    │
│  BFF 模式,HTTP 调 x-miniqmt                                  │
│  含 离场监控 + 清仓锁 + 盈亏闭环 + 双数据源 + 通知 + WebSocket│
└─────────────────────────────────────────────────────────────┘
          ↓ HTTP REST                ↑ HTTP POST 回调
┌─────────────────────────────────────────────────────────────┐
│  x-miniqmt (Python FastAPI, :8000)  QMT SDK 接入层 / 代理     │
│  封装 xtquant,NSSM 守护,单进程单连接                        │
│  含 ConnectionManager(熔断)+ 6 service + Callback 推送      │
└─────────────────────────────────────────────────────────────┘
                          ↓ 共享内存
                   XtMiniQmt.exe → 券商柜台
```

**核心认知**:MQ 的实盘"大脑"是 `x-server`(TS),不是 `x-miniqmt`。`x-miniqmt` 只是把 xtquant 包了一层 HTTP。真正的高价值设计(离场规则引擎、清仓锁、buildSimpleCycles 盈亏闭环、双数据源合并、TEST/RUN 双模式)全在 `x-server`。本项目是 Python,需把这些设计"翻译"过来。

## 3. x-tdxqmt 策略交易层分析

### 3.1 定位:回测引擎,非实盘

**关键发现**:x-tdxqmt 走通达信 TQ 通道(`tqcenter/TPythClient.dll`),**不直接调 xtquant**。它是一个回测引擎 + 选股服务,实盘下单交给 x-server。`tqcenter.py:2290` 的 `order_stock()` 标注"暂无实际功能"。

### 3.2 exit_rule_engine 5 条规则(重点)

**双实现**:Python 纯函数(`strategies/exit_rule_engine.py`,可读参考)+ Numba JIT(`vbt_runner/decision/exit_rules_nb.py`,高性能),严格 1:1 对齐。

规则按优先级从高到低,**首个命中即返回**(短路评估):

| 优先级 | 规则 | 触发条件 | 动作 | 源码 |
|--------|------|----------|------|------|
| 100 | 强制平仓 | 持仓天数 ≥ `LONG_HOLD_DAYS` | 100% 清仓 | `exit_rule_engine.py:80-88` |
| 80 | 强卖 | 持仓 ≥ `FORCE_SELL_DAYS` 且盈亏在 `[trigger, take_profit)` (正触发) 或 ≤ `trigger`(负触发) | 卖 `FORCE_SELL`% | `:91-121` |
| 60 | 止损 | 回撤 ≥ `STOP_LOSS_DRAWDOWN`(基准可选"最高价"或"成本价") | 卖 `STOP_LOSS_SELL`% | `:124-142` |
| 40 | 止盈 | 峰值盈利 ≥ `TAKE_PROFIT_TRIGGER` 且回撤 ≥ `TAKE_PROFIT_DRAWDOWN`;回撤 ≥ `BOTTOM_DRAWDOWN` 则兜底 100% 清仓;否则阶梯一卖/二卖/三卖(30%/50%/100%) | 阶梯或清仓 | `:145-191` |
| 20 | 固卖 | 盈利 ≥ `FIXED_FIRST/SECOND_SELL_RATIO`,最多 2 次 | 卖固定数量 | `:194-219` |

**`sell_count` 跨规则共享**:止盈和固卖都依赖 `sell_count`,在卖出成交后递增。

**17 个参数**全部来自 MySQL 数据字典(`dict_client.py:23-42`)。

### 3.3 与本项目 p9 的 8 条规则对比

p9 已有 `app/backtest/exit_rules.py` 的 8 条规则(优先级 100/95/90/80/60/40/20/10):

| 优先级 | p9 规则 | MQ 有无 | p9 优势 |
|--------|---------|---------|---------|
| 100 | HS 硬止损 | ✅(MQ 止损) | — |
| 95 | BE 保本止损 | ❌ | **p9 独有**:峰值盈利后回落到保本线 |
| 90 | FD 首日弱势 | ❌ | **p9 独有**:前 N 天最高价未达目标 |
| 80 | TF 时间强制 | ✅(MQ 强制平仓) | — |
| 60 | TP 阶梯止盈 | ✅(MQ 止盈) | — |
| 40 | TR 移动止盈 | 部分(MQ 止损回撤) | — |
| 20 | TC 时间条件 | ❌ | **p9 独有**:持仓>N天且盈利达标 |
| 10 | VC 成交量高潮 | ❌ | **p9 独有**:3倍均量+弱势收盘 |

**结论**:p9 的 8 条规则比 MQ 的 5 条**更丰富**(多了保本/首日弱势/时间条件/成交量高潮),且已归一(backtest + sim_trader 共用 `exit_rules.py`)。**实盘应沿用 p9 的 8 条,不采纳 MQ 的 5 条**。这与 v4.0 决策一致,本次研究进一步坐实。

### 3.4 x-tdxqmt 缺陷

| 缺陷 | 严重度 |
|------|--------|
| **无 T+1 限制**:回测买入后同 bar 可卖,A 股不符 | HIGH(回测失真) |

## 4. x-server 业务中台分析(实盘大脑)

### 4.1 完整性:高(生产跑通,设计成熟)

**技术栈**:Midway.js + TypeORM + MySQL + Redis(三库分离)+ Socket.IO + axios。

**模块命名**:`x_c_` 连接层 / `x_m_` 业务层 / `x_b_` 归档层。

### 4.2 离场监控 exit_monitor(核心)

- **定时任务驱动**(默认 60s,可前端配置),非事件驱动
- **5 条规则**(与 x-tdxqmt 同逻辑,独立实现),规则**只判定是否命中,不计算数量**,数量在执行层统一算
- **优先级合并**:高优先级覆盖低优先级,同优先级取更大 targetVolume
- **腾讯行情替换 QMT 行情**:用于交易决策时,腾讯行情失败**直接抛异常终止 + 企业微信告警**(不容错,避免错误行情下单)
- **固卖限价单智能切换**:最新价 ≥ 限价→市价单(快速成交);最新价 < 限价→限价单(按目标价挂单)

### 4.3 清仓锁 ClearanceLockService(防 race,高价值)

**解决的问题**:"第 N 轮撤掉固卖单 → 第 N+1 轮固卖规则又把单挂回去"的 race condition。

- **Key**:`(envName, accountId, stockCode)` 三元组
- **实现**:内存 Map + 双索引(主 Map + orderId→key 反查表),TTL 300s 兜底
- **acquire**:5 类清仓动作执行前(撤单/挂新单/强平)
- **release**:成交回调 / 错误回调 / 异常路径,均 `releaseByOrderId` 幂等
- **固卖规则 evaluate 阶段检查 isLocked**,被锁则跳过

**缺陷**:内存实现,多进程部署失效(注释提到"多进程改 Redis")。

### 4.4 buildSimpleCycles 交易闭环(盈亏计算,高价值)

**源码**:`x_m_trade_logs/service/trade-logs-service.ts:48-221`。

**算法**:以买入为基准,净仓归零闭合周期。

```
对每只股票,按时间升序遍历成交:
  net = 0
  买入(orderType=23): net==0 则开启新周期; net += vol
  卖出(orderType=24): net -= vol
  net == 0 → 周期闭合
加权均价 = sum(price*vol) / sum(vol)
盈亏 = sum(卖出金额) - sum(买入金额)  (仅闭合周期)
```

**关键约束**:**用 `orderType`(23=买,24=卖)判断方向,不用 `direction`**(direction 在股票场景是多空方向 LONG/SHORT)。

### 4.5 双数据源合并(防 QMT 回报覆盖)

**源码**:`trade-data-query-service.ts:29-107`。

- 主数据源:`x_stock_trade_log`(实时回调日志表,新鲜但可能被 QMT 覆盖)
- 备数据源:`x_qmt_deals_backup`(归档表,历史完整)
- 合并:基于 `tradeId` 去重,主数据源优先

### 4.6 撤单 ack 轮询替代 sleep(高价值)

**原方案**:`sleep(1500)` 盲等 → stale `can_use_volume` → 卖不全。
**新方案**:`tdx-service.ts:563-629` 轮询订单状态直到终态,超时熔断。

### 4.7 orderRemark 协议(贯穿全程)

```
"WEB"                          → 手工下单
"TDX"                          → 通达信公式触发
"SYS:::止盈|回撤3.50%，档位一卖，卖出50%"  → 系统离场(终端:::策略详情)
```

一个字段承载终端来源 + 策略详情,贯穿 WebSocket 推送 / 企业微信通知 / 盈亏重算。

### 4.8 TEST/RUN 双模式

- **TEST**:`testEvaluateExitCandidates` 仅评估不下单,支持自定义配置覆盖
- **RUN**:`executeExitSellWithTiering` 完整流程(评估→归档→下单)
- 共用 `evaluateExitCandidatesCore` 内核,`mode` 参数区分
- 测试单标记 `isMockTrade`(envName 含"测试/模拟/demo"),企业微信消息追加"(测试单)"

### 4.9 WebSocket + 企业微信

- **WebSocket**:Socket.IO 命名空间 `/x/message`,6 种事件(下单前预览/同步下单成功/委托更新/成交/错误/废单),Redis Adapter 支持多实例
- **企业微信**:成交通知 + 行情异常告警(高优先级),Markdown 格式,频控处理(errcode=45009 时 1 分钟后重试,最多 5 次)

### 4.11 x-server 缺陷

| 缺陷 | 严重度 |
|------|--------|
| **清仓锁内存实现**,多进程失效 | HIGH |
| **ExitSellService 2263 行**,超 800 行上限,职责过多 | MEDIUM |

## 5. 基于 MQ 生产实践提炼的最佳实践

> 说明:本次 WebSearch/WebFetch 受环境网络策略限制不可用,本节基于 MQ 生产源码 + p9 现有 `qmt_proxy_server.py` 实战代码 + v4.0 自检修订提炼,均为第一手资料。来源单一(仅 MQ 一个生产项目),故标题为"基于 MQ 生产实践提炼"而非"全球最佳实践";建议后续网络可用时补充 vnpy/qlib 等开源框架对比。

### 5.1 xtquant SDK 硬约束(高危,必须遵守)

| # | 实践 | 依据 |
|---|------|------|
| 1 | **Callback 方法体只做 `getattr` 数据提取 + 派发到独立 `db_executor` 线程池** | 实测 `xttrader.py` `start()` 中 `ThreadPoolExecutor(max_workers=1)`,所有 callback 串行;慢回调会阻塞后续所有回报 |
| 2 | **`XtQuantTrader` 必须在子线程实例化** | `__init__` 执行 `asyncio.set_event_loop(self.loop)`,主线程实例化会劫持 uvicorn 主 loop 死锁 |
| 3 | **`register_callback` 必须在 `start()`+`connect()` 之前** | 否则回调丢失 |
| 4 | **所有 xtquant 同步调用包 3 秒超时** | 底层 C++ 通信可能永久阻塞,用 `ThreadPoolExecutor`+`Future.result(timeout=3)` |
| 5 | **`WaitingFreeWriter` 即 `os._exit(1)` + NSSM 指数退避拉起** | 资源池耗尽唯一恢复方式是重启;指数退避(30s→60s→...→1800s)防死循环拉起磁盘满 |
| 6 | **`on_disconnected` 触发 kill switch** | 断连后所有 callback 停止,不能只打日志;停新单 + NSSM 重启恢复 |
| 7 | **Callback 幂等 + 状态转换校验** | `on_stock_order` 与 `on_stock_trade` 顺序不保证;基于 order_id 做 UPDATE,终态后不再处理,UPDATE 前 SELECT 校验(如 57 废单不能变回 50) |

### 5.2 业务规则

| 规则 | 实践 |
|------|------|
| **方向判断** | 用 `orderType`(23=买,24=卖),**不用 `direction`**(股票场景是多空方向) |
| **字段提取** | 全用 `getattr(obj,'field',default)`,QMT 版本差异会导致 `obj.field` 崩 |
| **代码格式化** | 6 开头→.SH,0/3 开头→.SZ,8/4/920→.BJ;带点的不处理 |
| **T+1** | A 股当日买入不可卖,`can_sell_today` 校验 |
| **涨跌停** | 涨停封板不买(0.5% 容差),`can_buy` 校验 |
| **状态码** | 整数(48-57+255),非字符串;终态 `{53,54,56,57}` |

### 5.3 风控最佳实践

| 层级 | 实践 |
|------|------|
| **事前 8 闸门** | 单笔金额/现金保留/单只集中度/总仓位/日亏损/启动自检/连续拒绝/kill switch;**闸门 2/3/4 只对 buy,sell 不查**(止损卖出不应被"现金不足"误拒) |
| **kill switch** | 4 触发方式(Web/API/文件 `touch .kill_switch`/自动);三重状态(DB+文件+内存);人工解除不自动 |
| **熔断器** | 连续 3 次失败→30s 拒绝→half-open 试恢复;WaitingFreeWriter 直接退出 |
| **清仓锁** | (env,account,code)三元组,TTL 300s,绑 order_id 释放 |
| **日亏损软熔断** | 日亏 3% 禁 buy 允许 sell,次日 09:30 恢复 |

### 5.4 部署最佳实践

| 实践 | 依据 |
|------|------|
| **QMT 必须 Windows**,实盘模块 NSSM 服务化 | xtquant 通过共享内存与 XtMiniQmt.exe 通信,Windows 独占 |
| **Docker 跑非实盘业务**(回测/选股/模拟盘) | Linux 容器无 xtquant |
| **实盘独立 DB 文件** | DuckDB 单写多读,模拟盘 14:53 写入与实盘高频 callback 写竞争 |
| **行情同步隔离子进程** | QMT C++ 底层多线程死锁(`qmt_sync_job.py` 实证),subprocess 运行完销毁 |
| **时区显式 Asia/Shanghai** | 避免云服务器 UTC 导致 14:53 错位 |
| **DRY_RUN 数据隔离** | dry-run 写 `live_orders_dryrun` 表,不污染 `live_orders`;验收检查 `live_orders` 行数=0 |

## 6. 对本项目实盘模块的优化思考

### 6.1 MQ 做法采纳/不采纳决策表

| MQ 设计 | 采纳? | 理由 |
|---------|-------|------|
| x-miniqmt 独立进程 | **不采纳** | p9 单语言 Python,现有 `qmt_proxy_server.py` 已是 Windows 端进程,演进即可,无需再拆 |
| 6 个 service 模块化 | **采纳** | 同进程但解耦,代码清晰 |
| ConnectionManager 熔断器 + WaitingFreeWriter 强退 | **完整照搬 + 加强** | 加指数退避防死循环 |
| Callback 守护线程 HTTP 推送 | **不采纳**(改同进程回调) | p9 单进程,callback 直接写 DB + 派发 db_executor,无需 HTTP |
| Callback max_workers=1 硬约束 | **采纳**(关键) | 只做 getattr + 派发,禁止同步 IO |
| seq 映射表 | **采纳** | 关联异步下单与回报 |
| 浮点清洗 + getattr 取值 | **采纳** | 防脏数据 + 版本兼容 |
| 清仓锁 ClearanceLock | **完整照搬 + 改 Redis** | p9 实盘单进程可用内存,但预留 Redis 接口防未来多进程 |
| buildSimpleCycles 交易闭环 | **采纳**(移植 Python) | 替代 p9 简单减法,多次加仓后均价更准 |
| 双数据源合并(实时日志+归档) | **采纳** | 防 QMT 回报覆盖 |
| 撤单 ack 轮询替代 sleep | **采纳** | 防 stale can_use_volume |
| 腾讯行情失败终止操作 | **采纳,但主数据源用 QMT** | p9 的 CLAUDE.md 硬约束是 QMT 优先,腾讯是回退;交易决策用 QMT,QMT 失败才告警 |
| 固卖限价/市价智能切换 | **采纳** | 提高成交率 |
| orderRemark 协议 | **采纳** | 终端:::策略详情,贯穿通知 |
| TEST/RUN 双模式 | **采纳**(对应 dry-run/live) | 同一规则引擎,模式切换 |
| WebSocket 推送 | **采纳**(复用 p9 现有 `sync_broadcast`) | p9 已有 `/ws` 端点 |
| 企业微信通知 | **采纳** | 成交 + 告警 |
| 离场 5 条规则 | **不采纳**(沿用 p9 8 条) | p9 规则更丰富且已归一 |
| 数据字典 MySQL 配置 | **不采纳**(用 p9 config 体系) | p9 是 app_setting.json + config.py,不引入 MySQL 依赖 |
| x-server BFF 聚合 | **不采纳**(单语言无需 BFF) | p9 直接在 FastAPI 路由聚合 |

### 6.2 在 MQ 基础上的加强点(修复 MQ 缺陷)

| # | MQ 缺陷 | p9 加强 |
|---|---------|---------|
| 1 | x-miniqmt `get_qmt_trader_by_session_id` 不存在 | 单连接架构,不暴露 session_id 接口,从根上避免 |
| 2 | `on_disconnected` 仅日志 | 触发 kill switch + DB audit + NSSM 重启 |
| 3 | `on_account_status` 空实现 | 监听异常状态码自动激活 kill switch |
| 4 | `order_id_to_seq_map` 内存泄漏 | 加 LRU 上限(如 10000)+ 定期清理已终态订单 |
| 5 | Callback 同步 requests.post 累积线程 | 同进程回调,派发到有界 `db_executor`(如 max_workers=4) |
| 6 | 清仓锁内存实现多进程失效 | 默认内存实现 + 预留 Redis `IClearanceLock` 接口 |
| 7 | 腾讯行情部分失败仍继续 | QMT 行情按股票粒度校验,缺价股票标记 `source=partial` 并跳过决策(复用 p9 `equity_price_coverage`) |
| 8 | 持仓天数依赖归档完整性 | 每日 EOD 强制归档 + 缺失日用 costPrice 兜底并告警 |
| 9 | 交易次数校验不区分终端 | 校验时排除 SYS 终端的撤单 |
| 10 | ExitSellService 2263 行过大 | 拆分为 Evaluator / Executor / ConfigManager / TaskManager,每个 < 300 行 |
| 11 | x-tdxqmt 无 T+1 | 复用 p9 `execution.can_sell_today`,实盘必须 T+1 |
| 12 | x-tdxqmt 数据字典失败静默 | 启动时校验风控参数非零,缺失则拒绝启动(fail-fast) |
