## 🏛️ 架构分析师发现

### [CRITICAL-1] `first_day_exit_min_profit` 量纲错误 —— RiskParams 漏除 100

**文件：** `app/config/risk_params.py:57`

`load_risk_params()` 中所有百分比字段都做了 `/100.0` 转小数，**唯独** `first_day_exit_min_profit` 漏了：

```python
# 第50行: hard_stop 正确转小数
hard_stop=_g("hard_stop_loss_pct", -6.0) / 100.0,    # -6.0 → -0.06 ✅

# 第57行: first_day_exit_min_profit 漏了 /100.0 !
first_day_exit_min_profit=_g("first_day_exit_min_profit", 0.0),  # 3.0 → 3.0 ❌ 本应是 0.03
```

**影响范围（两条路径同时受影响）：**

1. `engine.py:451` — `dataclasses.asdict(_load_risk_params())` → `first_day_exit_min_profit=3.0`（100倍偏大），传给 `build_context` → `rule_first_day_exit` 中 `day_high_pct < 3.0` 永远为 True → **首日弱势离场必定触发**。

2. `simulate_one_trade.py:99` — 更严重：`getattr(_risk, "first_day_exit_min_profit", 0.0) * 100`，3.0 × 100 = 300.0 → 传给 `build_context` → 与 `day_high_pct`（约 0.02 级别）比较 → 10000 倍偏大。

3. `sim_trader/config.py:35` — `FIRST_DAY_EXIT_MIN_PROFIT = _RP.first_day_exit_min_profit` 也受影响，回测配置面板读到 3.0 而非 0.03。

**当前幸免原因：** 默认值 `0.0`，`rule_first_day_exit` 中 `if fd <= 0: return None` 直接禁用，bug 被掩藏。**一旦用户启用首日离场（设置值 > 0），行为立即异常。**

**修复：** `risk_params.py:57` 加 `/ 100.0`：
```python
first_day_exit_min_profit=_g("first_day_exit_min_profit", 0.0) / 100.0,
```

### [CRITICAL-2] 保本止损（Breakeven Stop）功能完全失效 —— 用户配置值被静默忽略

**根因链：**

1. **配置入口缺失** — `app/config/risk_params.py:47-61` 的 `RiskParams` dataclass 定义了 11 个字段，但**不包含** `breakeven_threshold_pct` 和 `breakeven_stop_pnl_pct`。

2. **用户已配置非零值** — `app_setting.json` 中实际存储了 AI 优化器产出的保本止损参数（约 2.23% / 0.98%），但没有任何代码路径读取它们。

3. **四个执行路径全部受影响**：

| 执行路径 | 文件:行号 | 如何失效 |
|----------|-----------|----------|
| 模拟盘卖出阶段 | `engine.py:451` | `dataclasses.asdict(_load_risk_params())` → 无 breakeven key |
| 模拟盘盘中监控 | `intraday_monitor.py:157` | 同上 |
| **实盘风控** | `exit_monitor.py:223` | 同上 |
| 回测仿真 | `simulate_one_trade.py:99` | `getattr(_risk, 'breakeven_threshold', 0.0)` → 恒为 0.0 |

4. **退出规则层静默兜底** — `exit_rules.py:431-432`：
```python
breakeven_threshold=_pct(params.get("breakeven_threshold_pct", 0.0)),
breakeven_stop=_pct(params.get("breakeven_stop_pnl_pct", 0.0)),
```
`.get()` 的默认值 `0.0` 让缺失参数不报错、不告警、静默禁用。

5. **规则引擎短路** — `exit_rules.py:256`：
```python
if ctx.breakeven_threshold <= 0:
    return None  # 永远走到这里
```

**修复方案：**
```python
# risk_params.py 的 RiskParams 增加两个字段：
breakeven_threshold_pct: float = 0.0
breakeven_stop_pnl_pct: float = 0.0

# load_risk_params() 增加两行：
breakeven_threshold_pct=_g("breakeven_threshold_pct", 0.0),
breakeven_stop_pnl_pct=_g("breakeven_stop_pnl_pct", 0.0),
```

### [HIGH] `_g()` 函数 fallback 路径实质断裂 —— 7/10 个 key 的 `key.upper()` 与 config.py 常量名不匹配

**文件：** `app/config/risk_params.py:38-44`

```python
def _g(key: str, default):
    val = _settings.get("risk", key)
    if val is not None:
        return val
    import app.sim_trader.config as _sc
    return getattr(_sc, key.upper(), default)  # ← 这里
```

**实测验证：**

| settings key | `key.upper()` | config.py 实际常量 | 匹配？ |
|---|---|---|---|
| `hard_stop_loss_pct` | `HARD_STOP_LOSS_PCT` | `HARD_STOP` | ❌ |
| `trailing_stop_activate_pct` | `TRAILING_STOP_ACTIVATE_PCT` | `TRAIL_ACTIVATE` | ❌ |
| `trailing_drawdown_pct` | `TRAILING_DRAWDOWN_PCT` | `TRAIL_DD` | ❌ |
| `time_exit_min_pnl_pct` | `TIME_EXIT_MIN_PNL_PCT` | `TIME_EXIT_PROFIT` | ❌ |
| `time_exit_force_days` | `TIME_EXIT_FORCE_DAYS` | `TIME_FORCE_DAYS` | ❌ |
| `use_atr_stop` | `USE_ATR_STOP` | `USE_ATR_TRAIL` | ❌ |
| `atr_stop_multiplier` | `ATR_STOP_MULTIPLIER` | `ATR_TRAIL_MULTIPLIER` | ❌ |
| `time_exit_days` | `TIME_EXIT_DAYS` | `TIME_EXIT_DAYS` | ✅ |
| `first_day_exit_min_profit` | `FIRST_DAY_EXIT_MIN_PROFIT` | `FIRST_DAY_EXIT_MIN_PROFIT` | ✅ |
| `first_day_exit_days` | `FIRST_DAY_EXIT_DAYS` | `FIRST_DAY_EXIT_DAYS` | ✅ |

**影响：** 当 `app_setting.json` 没有 `[risk]` 段对应 key 时（如首次启动、配置被清空），7 个核心参数的 fallback 路径静默返回 `_g()` 的硬编码 `default` 值，而不是 config.py 中实际配置的值。

**当前实际不触发的原因：** 因为 `config.py` 本身的常量也是从 `load_risk_params()` 派生的（`config.py:22-23`），所以存在循环依赖——config.py 的常量本身就是从 risk_params 来的，fallback 回去读它是死循环。**结论：这个 fallback 路径是死代码，应该移除或将常量名对齐。**

## 🤔 我额外想到的隐患

### 1. 配置源循环依赖在极端条件下可能触发

`risk_params.py._g()` → `import config.py` → `config.py` 调用 `load_risk_params()` → 再次进入 `_g()`。当前不触发是因为 `_settings.get("risk", key)` 通常能命中，但如果在 config.py 导入时 settings 尚未初始化完毕，可能触发。这是一个低概率但高影响的隐患。

### 2. `_cycle_locked` 的 RLock 不能跨进程

当前 `RLock` 只保护单进程内的并发（cron + 手动 API）。如果未来有多进程场景（如 uvicorn workers > 1），锁会失效。当前 `workers=1` 所以安全，但应在文档中注明这个假设。

### 3. `check_stops` 和 `simulate_one_trade` 的 breakeven 行为不一致

`simulate_one_trade.py` 能从 settings/override 读到 breakeven 值并通过 `_p()` 传给 `build_context`。但 `check_stops`（模拟盘 + 实盘）的 breakeven 永远为 0。这意味着**回测结果中保本止损生效、实盘/模拟盘中不生效**——如果用户基于回测优化了 breakeven 参数但实盘不生效，会导致回测收益高估。
