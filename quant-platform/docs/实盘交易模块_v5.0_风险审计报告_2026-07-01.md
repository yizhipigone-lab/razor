# 实盘交易模块 v5.0 风险审计报告

> **审计身份**：实盘风险审计师
> **审计对象**：`docs/实盘交易模块实施开发书_v5.0.md`（含 v5.1/v5.2/v5.3 修订）
> **审计日期**：2026-07-01
> **审计方式**：通读开发书 + 核实全部代码引用（`intraday_monitor.py` / `exit_rules.py` / `qmt.py` / `sim_trader/config.py` / `app_setting.json`），确认文档引用事实全部属实。
> **报告立场**：只列缺陷与整改方案，不评价优点。

---

## 审计核心判断

这份文档在**"防误下单"**（kill switch、dry-run、清仓锁、六重防线）上做得过度充分，但在实盘最要命的三个物理现实场景上反而薄弱：

- **防超买**（异步撮合下的仓位失控）
- **防漏单/重单**（跨机 HTTP 链路的幂等性）
- **极端行情能否真卖掉**（跌停的不可成交性）

大量精力花在了防御框架的完备性上，却对 A 股撮合的异步性、跨机链路的幂等性、跌停不可成交性这些实盘物理现实估计不足。

---

## 一、CRITICAL（会直接导致资金损失或失控，必须开工前解决）

### C1. 买入下单只有"事前"闸门，没有"成交后"仓位再校验 → 会超买

**问题**：RiskGate 8 闸门全是**事前**检查（§5.6 明确"事前检查，不是事后"）。但 A 股是异步撮合：

- 闸门 3/4 检查"单只 ≤30%、总仓 ≤90%"用的是**下单那一刻**的持仓快照。
- `on_stock_trade` 成交回调是**几百毫秒到几秒后**才回来。
- 若同一轮信号对**同一只或多只股票连续下多笔单**（信号叠加/分批建仓），第 2、3 笔下单时第 1 笔成交还没回调进 `live_positions`，闸门 3/4 读到"旧的低仓位"→全部放行→最终成交后实际仓位远超 30%/90%。

**文档自身矛盾**：清仓锁（ClearanceLock）只锁"撤单/挂新单/强平"等**卖出侧**动作防 race，**买入侧并发下单完全没有锁**，闸门读到脏数据。

**整改方案**：
1. 引入**"在途买入额度"预扣机制**：下单成功（seq>0）即在内存冻结 `volume × price` 名义敞口，闸门 3/4 用 `实际持仓 + 在途未成交买入` 计算，成交回调后释放预扣换实际持仓。
2. 买入侧也走 ClearanceLock（或独立 `pending_buy_lock`），同一 code 有在途买单时后续买单串行、重算额度。
3. §14.1 验收增加："同一轮 3 笔并发买入，最终总仓位不超过 max_total_position_pct"。

---

### C2. 强制市价清仓（14:57）没有涨跌停/流动性防护 → 砸死自己或根本卖不掉

**问题**：§7.3 / §16.3 规定"14:57 后强制市价单（对手最优）清仓仍需止损的持仓"。两个致命场景：

- **跌停**：需止损的股票大概率在跌停附近，14:57 挂对手最优市价，对手盘就是跌停封单，**要么排队几万手根本不成交**，要么流动性差的票市价单击穿多价位（北交所 30% 幅度，滑点巨大）。
- **文档"对手最优市价单确保成交"是错的**：A 股跌停时对手最优市价单**不保证成交**，只是排队。文档把"市价单"等同"一定能卖出"，是对 A 股微观结构的误解。

**整改方案**：
1. 14:57 强平前先判断：若已跌停（`last_price ≤ 跌停价`），市价清仓无意义，改为**记录 audit + 告警"跌停无法止损，明日开盘优先处理"**，不盲目挂单制造废单。
2. 明确市价单类型：A 股实际可用为"最优五档即时成交剩余撤销"或"对手方最优价格"，在 §8 xtquant 接口清单**固化具体 price_type 枚举值**。
3. 强平只对**流动性足够**的持仓生效，对停牌/跌停/一字板明确跳过并告警。

---

### C3. Docker（Linux）↔ Windows 纯 HTTP 传递交易状态，无幂等确认 → 漏单/重复下单

**问题**：§3.1 信号可能来自 Docker 端 screener，最终到 Windows 端 live_trader 下单。这条跨机链路：

- 文档只说 Docker "只读"拉状态，**没说买入信号如何从 Docker 传到 Windows 下单**。§7.1 步骤 1 写"信号源（screener TDX 选股 / 手动 Web / 定时 sell_phase）"，但 screener 在 Docker、下单在 Windows，**这条 HTTP 调用的幂等性、超时重试、断连补偿完全空白**。
- Docker→Windows 下单请求超时（网络抖动）时，Docker 端不知道单下没下。**重试则重复下单，不重试则漏单**——直接违反核心原则"宁可漏买漏卖，绝不误下单"。

**整改方案**：
1. 跨机下单必须带**客户端幂等键** `client_order_id`（如 `strategy+code+date+seq` 的 hash）。Windows 端收到后先查 `live_orders` 是否已存在，存在则返回原结果不重复下单。
2. `live_orders` 表增加 `client_order_id` 唯一索引（§6 表结构缺此字段，必须补）。
3. 超时语义明确："下单接口超时 = 状态未知"，Docker 端**不自动重试**，转为查询确认状态后再决定。

## 二、HIGH（严重逻辑/风控漏洞，上线前必须修）

### H1. 日亏软熔断（闸门5）浮亏依赖 QMT 实时价，QMT 挂了就失效
§16.4 定义日亏 = 已实现 + 浮动盈亏，浮动依赖"QMT 实时价 × 均价"。§5.7 又说"QMT 失败则该股票 `source=partial` 跳过决策"。**矛盾**：QMT 行情部分失败时浮亏算不准，日亏 3% 熔断可能因"取不到价"而**永远触发不了**，大跌日照样开新仓。
**整改**：QMT 行情缺失时闸门5 应**保守禁买**（fail-safe），不能因"算不出亏损"就放行。

### H2. `os._exit(1)` 强退与 DuckDB 双缓冲（L1 deque）冲突 → 丢成交数据
§5.2 遇 WaitingFreeWriter 用 `os._exit(1)` 硬杀；§18.6 又把成交先写 L1 内存 deque，L2 每 100ms 才 flush。**`os._exit()` 不执行清理、不 flush**，100ms 窗口内未落盘成交**全丢**。§18.6 还说"queue 数据可选落盘或丢弃"——**实盘不可接受丢弃**。
**整改**：终态订单/成交必须**同步落盘**；强退前尽力 flush deque（500ms 紧急落盘），或 L1 直接落 append-only 文件（WAL），重启从文件补。

### H3. NSSM 指数退避计数器递增/清零时机不明 → 退避可能失效
§4.1 退避序列存 `restart_counter.json`，但**何时 +1、何时清零没说清**。若进程在写 counter 前就 `os._exit`，退避失效，回到"疯狂拉起打满磁盘"的原始故障。
**整改**：计数器递增必须在**进程启动最早期**（拉起即 +1，正常运行 N 分钟后才清零），而非退出时写。

### H4. "连续 5 单被拒→kill switch"（闸门7）早盘可能误杀
§18.11 已排除 dry-run 并按 risk/broker/market/code 分类。但**早盘 9:30 集合竞价刚结束、QMT 柜台未完全 ready** 时，连续几单因 broker 类原因（柜台未就绪）被拒，直接停掉一整天。
**整改**：连续拒绝计数带**时间窗口**（如"5 分钟内连续 5 单"），区分"柜台未就绪"（可重试瞬态）与"资金不足"（真风控）。

### H5. Reconciler 对账阈值"100 股 / 10% 市值"对大资金失真
§5.9 用绝对值"100 股"做 CRITICAL 阈值。但 §1.1 资金放大到 10 万+。对 5 元股票 100 股才 500 元，对 10 万本金是 0.5%——**对高价股太松、对低价股太严**。且"连续 2 时点同方向偏差→kill switch"缺少**时点间成交量归一**（两时点间本有正常成交，直接比总数会误报）。
**整改**：偏差判定用**市值比例 + 最小绝对值**双门限（如 `max(1 手, 市值×0.5%)`）；对账比对需扣除时点间正常成交量。

### H6. T+1 校验只在验收项，没有设计实现
§14.4 验收"T+1 校验（当日买入不可卖）"，但正文 §5.6 的 8 闸门、§7.3 离场流程**完全没有 T+1 闸门设计**。exit_rules 里也无 T+1 概念（回测中 T+1 在成交层处理）。实盘若 `can_use_volume` 用错，当天买的票被止损触发卖出→废单/错误。
**整改**：把 T+1 作为**独立第 9 闸门**明确写进 RiskGate，卖出量必须 ≤ `can_use_volume`（QMT 返回可用数量，已剔除当日买入冻结）。

## 三、MEDIUM（性能瓶颈与可维护性）

### M1. 3 秒超时 × 单连接独占 = 串行阻塞瓶颈
§5.1 所有 xtquant 同步调用走 `ThreadPoolExecutor + Future.result(timeout=3)`，§3.2 单进程单连接独占。离场监控 60s 扫描全部持仓，每只都要 `query_stock_positions` + `query_stock_orders`（ack 轮询每 200ms、最多 5s）。持仓一多，**撤单 ack 轮询串行排队**，一只卡满 5s 后面全延迟。14:50-15:00 仅 10 分钟，若 20+ 只都要止损**根本处理不完**。
**整改**：ack 轮询改**批量查询**（一次 `query_stock_orders` 拉全部在途单本地匹配）；离场扫描按"最急止损"优先级排序。

### M2. 清仓锁 TTL 续期上限 900s，但收盘只剩 10 分钟
§16.6 清仓锁 TTL 300s，最多续 2 次到 900s。但 §7.3 尾盘窗口 14:50-15:00 仅 600s。若一只票 acquire 后 ack 持续超时续到 900s，**已过收盘**，锁还在，当天再没机会处理。
**整改**：尾盘时段 TTL 缩短并与收盘时点挂钩。

### M3. `order_id_to_seq_map` LRU 10000 上限清理时机模糊
§16.9 承认"需定期清理已终态"但无触发条件。长跑中若映射表被非终态单占满，新单映射被 LRU 挤掉，回调找不到订单。
**整改**：终态回调时**立即从 map 删除**，不依赖 LRU 淘汰。

### M4. 企业微信是唯一告警通道，它挂了就静默
§10/§11 所有告警走企业微信，频控 45009 重试 5 次后**丢弃**（§16.9）。kill switch 这种 CRITICAL 事件若告警丢了，人不知道。
**整改**：CRITICAL 级告警**多通道**（企业微信 + 本地声音/桌面弹窗 + 日志标红）；kill switch 触发必须落 DB 且前端红条常驻，不依赖推送。

## 四、文档层面的系统性问题

### D1. 三次自检把文档越改越长，缺"最终一致版本"
§16/§17/§18 三轮修订中，§18.2 推翻 §17.5，§18.3 推翻 §16.2。正文 §5.4/§5.6/§7.3 部分仍是旧描述，**读者要交叉比对 4 个版本才知最终结论**，开发时极易实现到被推翻的旧方案。
**整改**：出一份**扁平化最终规格**（推翻/修订合并进正文，历史修订移附录）。

### D2. "26 文件 / 7400 行" vs "复用度 92%"自相矛盾
§13 说新写 7400 行，§18.7 又说 ExitMonitor 复用度 92%。真正新逻辑规模没说清，工期不可控。
**整改**：区分"新写 / 移植 / 复用"三类行数。

### D3. 阶段2 验收"对账 0 偏差"不现实
§13 阶段2 要求"对账 0 偏差"，但 §18.2 自己承认 callback 与 QMT 有正常时序差异（100 股内属正常）。矛盾。
**整改**：验收改为"无 CRITICAL 偏差"。

## 六、审计结论

**建议 C1 / C2 / C3 必须在阶段0 POC 里就用真实小资金验证，而不是留到阶段2。**

文档对"防误下单"的防御堆砌足够，但对以下实盘物理现实估计不足：
1. A 股撮合的**异步性**（下单与成交回调之间的时间差 → 超买）
2. 跨机链路的**幂等性**（HTTP 超时的状态不确定 → 漏/重单）
3. 跌停的**不可成交性**（市价单不等于一定卖出 → 止损失效）

这三点是实盘与模拟盘的本质区别，也是本方案当前最大的风险敞口。
