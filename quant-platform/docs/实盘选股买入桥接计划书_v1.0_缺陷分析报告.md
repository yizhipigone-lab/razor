## 🔴 P0 事实性错误

### 缺陷 1：BUY_TIME 改时间是个伪需求

**计划书原文**（§4.1）：

> 改 TDX 选股时点 14:54 → 14:52
> `app/sim_trader/config.py` 的 `BUY_TIME = "14:54"` → `"14:52"`

**代码真相**：

- [cron_jobs.py:84-93](app/scheduler/cron_jobs.py#L84-L93) 硬编码 `minute=52`，**根本不读 config.BUY_TIME**
- [config.py:53](app/sim_trader/config.py#L53) 的 `BUY_TIME = "14:54"` 只是个注释性常量，没有任何代码引用它来控制调度

```
# cron_jobs.py 第 84-93 行 — 硬编码 14:52
self._scheduler.add_job(
    self.run_sim_trader_daily,
    'cron',
    day_of_week='mon-fri',
    hour=14,
    minute=52,          # <-- 硬编码，不读 config
    id="sim_trader_daily",
)
```

**风险**：改 config 不改 cron（或反过来），两边就对不上。当前 cron 已经在 14:52 触发，§4.1 整条改动是多余的。

**建议**：

1. 让 cron 从 config 读时间（彻底消除硬编码），或
2. 直接删掉 §4.1，承认现状已满足

### 缺陷 2：信号格式描述错误

**计划书原文**（§2、§4.2）：

```
signals [(code, price)]
POST /live/buy-signal { signals: [{code, price}], strategy: "QUANTQQ" }
```

**代码真相**：

TdxBridge.execute_screen() 返回的是：

```python
{"status": "ok", "matched": ["300806.SZ", "000001.SZ", ...]}  # 只有代码，没有价格
```

价格是 [cron_jobs.py:430](app/scheduler/cron_jobs.py#L430) 从 snapshot 二次查找的：

```python
px = snapshot.get(code_num, {}).get('close', 0)
```

**风险**：如果 Docker 端直接把 TdxBridge 原始结果转发给 Windows，Windows 端拿到的只有代码没有价格。计划书完全没提这个衔接。

**建议**：明确价格来源，二选一：

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| A. Docker 附带价格 | 转发时带上 snapshot 价格 | 快，但价格可能过时（Docker QMT 行情有延迟） |
| B. Windows 自己查价 | Windows 端从 QMT 查实时价 | 准，但多一次查询 + 代码量更大 |

推荐方案 B：尾盘价格波动大，用最新价更安全。

### 缺陷 3：买入量计算"跟随系统设置"是一笔糊涂账

**计划书原文**（§5）：

> 1. `trading.max_buy_amount`（app_setting.json，当前 =1万）— 单只买入上限
> 2. 若未设置，回退 `backtest.position_size`（当前 =5万）
> 3. 板块取整

**代码真相**：这是**三个不同系统**的参数，互相独立、互不影响：

| 来源 | 参数 | 当前值 | 用在哪 |
|------|------|--------|--------|
| `app_setting.json` trading 段 | `max_buy_amount` | 1万 | `core/settings.py` 通用交易 API |
| `sim_trader/config.py` | `POSITION_SIZE` | 5万 | 模拟盘 engine.execute_buy() |
| `live_trader/config.py` | **无此参数** | — | 不存在 |

实盘 live_trader **根本没有仓位计算逻辑** — [main.py:428](app/live_trader/main.py#L428) 的 `place_order` 要求调用方传入 `volume`，自己不算。

**风险**：计划书说"改系统设置时实盘自动跟随"，但三个系统的参数互不相干，改哪个都不影响其他。实盘端的 volume 计算是空白，必须从零实现。

**建议**：在 live_trader/config.py 新增 `buy_position_size` 参数，或在 BuySignalRequest 里让 Docker 端传 volume。明确谁算、怎么算、取哪个值。

## 🔴 P0 架构设计缺陷

### 缺陷 4：place_order 不是可复用的内部函数

**计划书原文**（§4.2）：

> 端点逻辑（复用现有 place_order 全链路）

**代码真相**：[main.py:428-608](app/live_trader/main.py#L428-L608) 的 `place_order` 是一个 **80 行的 FastAPI 路由函数**，直接从 `_state` 字典拿组件、构造 OrderIntent、写 DB、返回 HTTP 响应。它不是 service 函数，不能被别的端点调用。

```python
@app.post("/live/order")
async def place_order(req: dict):       # <-- 路由函数，不是 service
    # 80 行逻辑，直接操作 _state 字典
    config = _state.get("config")
    store = _state.get("store")
    ...
```

**风险**：如果 /live/buy-signal 抄 place_order 的代码 → 大面积复制粘贴，后续改一处漏一处。如果不抄 → 先重构出 `place_order_service()` → 工作量不在计划书里。

**建议**：先提取内部 service 函数：

```python
def place_order_service(intent: OrderIntent) -> OrderResult:
    """下单核心逻辑（幂等→风控→清仓锁→下单→写DB），供路由和 buy-signal 共用"""
    ...
```

然后 place_order 和 buy-signal 都调用它。额外工作量约 +50 行。

### 缺陷 5：信号价格时效性问题

**计划书假设**：Docker 端选完股后立即转发信号，实盘端拿到价格就下单。

**代码真相**：

1. 14:52 选股时拿到的 snapshot 价格来自 `augment_bars_with_realtime()`
2. 该函数在 Docker 容器内通过 `host.docker.internal:8001/live/quotes` 拉行情
3. 信号从 Docker 发到 Windows 有网络延迟
4. Windows 端逐个走 RiskGate → ClearanceLock → 下单，**单只耗时约 3-5 秒**
5. 如果有 5 只信号股，**整个过程可能 15-25 秒**

14:52-14:57 是尾盘阶段，价格波动可能很大。用 Docker 端 14:52:00 的价格作为 Windows 端 14:52:20 的限价单 → **很可能成交不了**。

**风险**：限价单挂上去不成交 → 废单。尾盘没有时间撤单重挂。

**建议**：

1. 买入时用**五档即成即撤**（price_type=42/47），而不是限价单
2. 或 Windows 端自己从 QMT 查最新价（见缺陷 2 方案 B）
3. 计划书应明确 `price_type` 参数（当前完全没提）

---

### 缺陷 6：实盘端缺少同股冷却期

**计划书 §4.2 端点逻辑**：只有幂等检查和 9 闸门，**没有同股冷却期**。

**代码真相**：

- 模拟盘在 [cron_jobs.py:471](app/scheduler/cron_jobs.py#L471) 有 `SAME_STOCK_COOLDOWN = 20`（同股 20 天不重复买入）
- live_trader 的 RiskGate 9 闸门里**没有这个检查**

**风险**：模拟盘某只股票刚卖，实盘又收到同只股票的买入信号 → 直接真买。模拟盘的"20 天冷却"保护在实盘端完全不存在。

**建议**：在 /live/buy-signal 端点或 RiskGate 新增冷却期检查。至少查 `live_positions` 的 `entry_date` 或 `live_deals` 的最近卖出日期。

## 🟡 P1 安全与可靠性缺口

### 缺陷 7：/live/buy-signal 无鉴权

计划书没提任何鉴权机制。现有 `/live/order` 也没有 auth，但那是人工手动下单。`/live/buy-signal` 是**程序自动触发真金白银下单**，且跨网络（Docker→Windows），风险等级完全不同。

**风险**：任何能访问 8001 端口的进程都能发 `POST /live/buy-signal` 下单。虽然 8001 绑了 127.0.0.1，但 Docker 内网所有容器都能访问 `host.docker.internal`。

**建议**：至少加一个共享密钥（环境变量或 app_setting.json），Docker 端请求时带 `Authorization: Bearer <token>`。工作量约 10 行。

---

### 缺陷 8：HTTP 请求失败无重试

**计划书 §2**：

```
POST http://host.docker.internal:8001/live/buy-signal
```

没有说网络断了怎么办。

**实际情况**：

- Windows 端 live_trader 可能 NSSM 重启中（几秒不可用）
- Docker 端发请求，HTTP 超时或连接拒绝 → **信号丢失**
- 没有重试逻辑，没有持久化待发信号
- 计划书 §4.4 的看门狗只能"没收到就告警"，不能补发

**风险**：Docker 端选出了信号但转发失败，实盘端完全不知道今天该买什么。

**建议**：

1. Docker 端转发失败时把信号暂存本地（文件或 Redis），后续重试
2. 或 Windows 端提供 `GET /live/buy-signal/pending` 让 Windows 端主动拉取

---

### 缺陷 9：幂等键设计不安全

**计划书**：说"生成 client_order_id(幂等)"，没说格式。

**代码真相**：[main.py:461-464](app/live_trader/main.py#L461-L464) 的幂等键是：

```python
client_order_id = hashlib.md5(
    f"{strategy_name}|{code}|{date.today()}|{direction}|{int(time.time() * 1000)}".encode()
).hexdigest()[:16]
```

因为包含**毫秒时间戳**，同一只股票同一天重试会产生不同 ID → 幂等形同虚设。

**风险**：Docker 端重发信号（网络抖动重试），Windows 端两次请求生成不同 client_order_id → 同一只股票重复下单。

**建议**：buy-signal 的幂等键应该是 `MD5("buy_signal"|code|date)` — 不带时间戳，确保同一天同一只股票只下一次单。

---

### 缺陷 10：卖出在买入之前？时序竞争

**计划书 §2 信号流**：

```
cron(14:52) → TdxBridge.execute_screen() → signals → engine.execute_buy() → 转发给实盘
```

**代码真相**：[cron_jobs.py:448-475](app/scheduler/cron_jobs.py#L448-L475) 实际是**先卖出再买入**：

```python
# ── 卖出 ── (第 448 行)
if engine.auto_sell:
    engine.sell_phase(today, snapshot, trading_dates)

# ── 买入 ── (第 466 行)
if engine.auto_buy and signals:
    ...
```

Windows 端的 exit_monitor 每 60 秒扫描一次卖出。14:52 收到买入信号时，可能同一只股票的卖出委托还没成交（在途）。ClearanceLock 会阻止买入（同 code 有锁），但买入信号会被**永久拒绝**而不是等待。

**风险**：正在卖出的股票，同一天又收到买入信号 → 清仓锁冲突 → 买入被拒 → 信号丢失。

**建议**：buy-signal 端点遇到清仓锁时，不应立即拒绝，而应排队等待或延迟重试（比如等 30 秒后再试一次）。

## 🟡 P1 缺失的关键环节

### 缺陷 11：没说 price_type

计划书从头到尾没提 price_type。实盘下单必须指定：

| 值 | 含义 | 适用场景 |
|----|------|----------|
| 11 | 限价 | 需指定价格，可能挂不上 |
| 44 | 对手最优价 | 即时成交 |
| 42/47 | 五档即成即撤 | 尾盘最安全的选择 |

14:52 尾盘用限价单很可能挂不上，用市价单又可能成交在较差价格。

**建议**：明确 price_type 策略 — 建议尾盘用五档即成即撤（42/47），确保成交。

---

### 缺陷 12：买入侧板块取整未实现且规则有误

**计划书原文**（§5）：

> 板块取整：主板100股整数倍，科创/北交可1股

**代码真相**：

1. 卖出侧有 `_calc_sell_volume()`（[exit_monitor.py:279-289](app/live_trader/exit_monitor.py#L279-L289)）
2. **买入侧没有对应函数**。`core/settings.py` 的 `calc_buy_volume()` 统一按 100 股取整，不区分板块
3. sim_trader 的 `execute_buy()` 第 415 行也是 `int(max_amt / price / 100) * 100`，硬编码 100

**计划书的取整规则本身也是错的**：

| 板块 | 实际最小单位 | 计划书说的 |
|------|-------------|-----------|
| 主板/创业板 | 100 股 | 100 股 ✅ |
| 科创板（688） | **200 股** | 1 股 ❌ |
| 北交所（8/4开头） | **100 股** | 1 股 ❌ |

**建议**：

1. 买入侧也需要 `_calc_buy_volume(code, amount, price)` 函数
2. 正确的取整规则：主板/创业板 100 股、科创板 200 股、北交所 100 股

### 缺陷 13：看门狗设计过于粗糙

**计划书原文**（§4.4）：

> 14:55 加信号看门狗：若当日开了 BUY_ENABLED 但没收到任何信号 → 告警

**问题**：

1. 14:52 选股 → 14:53 信号到 Windows → 14:55 看门狗检查。**窗口只有 2 分钟**，如果选股慢了（TDX worker 超时 600 秒），看门狗就误报了
2. 非交易日怎么办？BUY_ENABLED 开着但当天是周末，看门狗会误报
3. 收到 0 个信号（当天没有符合条件的股票）不是异常，但看门狗会告警

**建议**：看门狗应区分"没收到信号"和"Docker 端选股失败"。可以让 Docker 端无论有没有信号都发一个心跳（含选股结果状态），Windows 端检查心跳而非信号数量。

### 缺陷 14：手动触发端点转发会重复下单

**计划书原文**（§4.3）：

> 手动触发买入的端点也加转发（保持手动/自动一致）

**代码真相**：`POST /api/sim-trader/execute` 是手动触发完整流程。如果用户在 14:50 手动触发一次，14:52 cron 又自动触发一次，**同一个信号会被转发两次**给实盘。

虽然有幂等检查，但如缺陷 9 所说，现有幂等键带毫秒时间戳，两次请求的 ID 不同 → 重复下单。

**建议**：

1. Docker 端记录"今日已转发信号"集合，同一天同一只股票只转发一次
2. 或 buy-signal 端点的幂等键不带时间戳（见缺陷 9）

---

### 缺陷 15：没有回滚预案

计划书 §7 说"不破坏现有"，但 §6 验证步骤里，如果小额 live 测试出了问题（比如闸门配置错误导致多买），**没有任何撤销机制**。

现有系统有 kill switch 可以停止后续下单，但**已经下的单撤不回来**。也没有"一键撤单所有今日 buy-signal 来源的委托"功能。

**建议**：

1. buy-signal 端点在下单时标记 `terminal="TDX"` 和 `strategy_name="QUANTQQ"`，便于事后筛选
2. 新增 `POST /live/cancel-by-source?terminal=TDX&date=今天` 批量撤单端点
3. 验证步骤增加"确认撤单路径可用"这一步

## 修订建议汇总

按优先级排列，建议在实施前先修正以下内容：

### 必须修正（P0）

1. **删掉 §4.1 或改为"让 cron 从 config 读时间"** — 当前已是 14:52，不需要改
2. **明确价格来源** — 推荐 Windows 端自己从 QMT 查实时价（缺陷 2 方案 B）
3. **新增 live_trader 仓位计算逻辑** — 在 config.py 新增 `buy_position_size`，BuySignalRequest 端点自己算 volume
4. **先提取 `place_order_service()` 内部函数** — 否则 buy-signal 端点只能复制粘贴
5. **明确 price_type** — 尾盘建议用五档即成即撤（42/47）
6. **实盘端增加同股冷却期** — 参照模拟盘 SAME_STOCK_COOLDOWN

### 应该修正（P1）

7. **buy-signal 端点加鉴权** — 共享密钥即可
8. **Docker 端转发失败时暂存信号 + 重试** — 防止信号丢失
9. **幂等键去掉时间戳** — `MD5("buy_signal"|code|date)` 确保同天同股不重复
10. **清仓锁冲突时排队等待** — 而非立即拒绝
11. **买入侧板块取整函数** — 科创板 200 股，不是 1 股
12. **看门狗改为心跳检查** — 而非检查信号数量
13. **手动触发防重复转发** — Docker 端记录已转发集合
14. **新增批量撤单端点** — 按来源/日期撤单

### 可选修正（P2）

15. 合并 BUY_ENABLED 和 AUTO_BUY 为三档开关
16. 转发前探活
17. 修订工作量估计（375 → ~530 行）
18. app_setting.json 新增 live_trader 段
