## 1.5 P0 前置 bug（评审新发现，必须在主任务前处理）

> 来源：`综合反馈_实施计划书评审与新发现_2026-06-28.md`。两项均经本会话独立 grep+Read 核实为真，且都与用户长期反馈的"参数/配置"痛点同源。**因涉及跨多点协调 + UI 字段盘点，不在立即项里草率改，列为主任务前的 P0 正式条目。**

### P0-1：止盈百分比参数的「单位约定冲突」（真 bug，比反馈描述更微妙）

- **两套冲突的约定（本会话逐行核实，修正了反馈 §3.1 path-C 的不准确结论）**：
  | 位置 | 约定 | 证据 |
  |---|---|---|
  | config `risk.take_profit_tiers` / `_build_tp_plan` 输出 | **小数**（0.027=2.7%） | `app_setting.json:26` `0.027`；`ai_optimizer.py:175` `tp1_profit/100.0` |
  | `engine.py` daily_fallback 消费 | **百分比**（`tp_price=entry*(1+tp_pct/100)`） | `engine.py:761/931` 都 `/100` |
  | `ai/apply` 写入 config | **不转换**（透传 search_space 的百分比值） | `api/backtest.py:251` `profit_pct: params["tp1_profit"]` |
- **真正的雷（与反馈方向相反）**：
  - daily_fallback 走 `settings.staged_take_profit`（`engine.py:858` 非 override 分支）时，读到 config 的**小数** 0.027，又执行 `*(1+0.027/100)` → 止盈目标 **+0.027%**，几乎一开盘就触发全卖 ❌（反馈说的"3.0→永不触发"不准确；实际是小数被当百分比→极小目标）。
  - `ai/apply`（`api/backtest.py:251`）把 search_space 的百分比值（如 0.83）直接写进 config 的小数字段 → 下游若按小数读则 0.83=83%，若按百分比读则 0.83%。**取决于走哪条读取路径，两种都可能错。**
- **影响路径精确区分**：
  - Python 策略寻优走 `_fast_simulate`（`ai_optimizer.py:431→557`），**不走 engine.daily_fallback**——其 tp_pct 单位需单独核实（见 §2.2.4）。
  - `engine.run()`（含 params_override 时）走 daily_fallback 的 percent 约定。
- **修复（统一收口）**：
  1. **定一个唯一约定**（建议：config 与所有内部传递一律小数），写进 schema 文档。
  2. `engine.py:761/931` 消费端若改吃小数，则去掉 `/100`；`ai/apply` 写入端 `api/backtest.py:251` 按约定归一化。
  3. `_fast_simulate`、`_build_tp_plan`、daily_fallback 三处 tp_pct 口径对齐到同一约定。
  4. `trailing_activate_pct`/`trailing_drawdown_pct`/`breakeven_*` 逐一核实是否同病。
- **验收**：构造 tp1=3% 的参数，分别走 ai/apply→config→engine.run、Python 寻优 `_fast_simulate` 两条路径，确认止盈都在 +3% 触发（而非 +0.03% 或 +300%）。
- **归档**：改前记录 `app_setting.json` risk/backtest 段当前值。

### P0-2：`saveSettings()` 系统设置页总保存按钮是空 stub

- **核实**：`main.js:877` `function saveSettings() { /* stub */ }`，绑定 index.html:945「保存全局设置」按钮。**附带发现**：`saveGatewaySettings()`（`main.js:992`）同为空 stub（反馈未提）。
- **影响修正（比反馈更精确）**：系统设置页**每张卡片有独立"保存此卡"按钮**（saveRiskSettings/saveSearchSpace/saveDataSettings 都有实体且正常）。所以"保存全局设置"总按钮失效**不等于完全无法保存**——用户用"保存此卡"是能落盘的。但总按钮点了无反应是真缺陷，且 `saveGatewaySettings` 失效会导致网关配置无法保存。
- **与"重启回默认值"的关系**：这是诱因之一，但回测面板的 `/api/settings/risk-params`、`/api/backtest/apply-to-system` 链路正常（已在前序会话确认）。需区分"哪条保存路径用户在用"。
- **修复**：实现 `saveSettings()`——盘点系统设置 tab 全部字段（风控/搜索空间/cron/数据/网关），可复用各卡 `save*` 函数顺序调用，或统一 POST `/api/settings`；同时实现 `saveGatewaySettings()`。**需先盘点字段+确认 API 契约，属有设计量的功能项。**
- **验收**：系统设置页改参数 → 点"保存全局设置" → 重启服务 → 值保留。

## 2. 主任务一：全路径成本一致化（最高优先）

### 2.1 目标
让所有"零成本"仿真路径接入 `execution.py` 的 `calc_buy_cost/calc_sell_revenue`，并修复"名义档位收益"（止盈按真实价差算）。**与 EOD 成交价格假设正交**。

### 2.2 改造点（函数级）

#### 2.2.1 `BacktestEngine._simulate_trade_daily_fallback`（`engine.py:797`）
- **现状**：`engine.py:931` `realized_pnl += tp_pct * actual_sell`（名义档位收益）；全路径零成本；函数签名无 `apply_costs`。
- **改**：
  1. 函数签名加 `apply_costs: bool = True`。
  2. 止盈卖出：`sell_price = entry_price*(1+tp_pct/100)`，`realized_pnl += _cost_pnl(entry_price, sell_price, actual_sell, apply_costs)`（参照 `_simulate_trade_v2` 的 `_cost_pnl`）。
  3. 止损/时间退出卖出同理按 `signal.sell_price` 真实价 + 扣成本。
- **调用方下传**（关键，否则开关死）：`engine.py:277` 调用处加 `apply_costs=params.get('apply_costs', True)`。
- **受影响**：`engine.run()` 路径（AI 优化器对 Python 策略的回测）。

#### 2.2.2 `simple_runner._run_intraday_backtest`（`simple_runner.py:287`）
- **现状**：`:448` `cost = sh*px`、`:598` `cash += sell_shares*sig.sell_price`（裸成交价）。
- **改**：买入 `calc_buy_cost(px, sh)`、卖出 `calc_sell_revenue(px, ss)`，与同文件 FastEngine 日线分支（`:99/:152`）一致。
- **受影响**：`intraday_freq ∈ {5m,1m}` 的 simple 回测。

#### 2.2.3 `tdx_runner._run_intraday_backtest`（`tdx_runner.py:223`）
- **现状**：`:441` `cost=sh*px`、`:500/:543` `cash += sell_shares*sell_px`。
- **改**：同 2.2.2，走 execution。
- **受影响**：TDX 5m/1m 回测（默认 5m）。

#### 2.2.4 `ai_optimizer._fast_simulate`（`ai_optimizer.py:596`）— 双重 bug
- **现状**：①整函数无成本调用；②`:641` `realized += tp_pct * actual`（名义档位收益，与 engine:931 同根）。
- **改**：
  1. 引入 `calc_buy_cost/calc_sell_revenue`。**口径选金额（与 `_simulate_trade_v2._cost_pnl` 一致），避免 % 折算的小数精度问题**；同步确认 `_calmar_score`（`:72-87`，`np.mean(pnls)` 期望百分比）的输入契约——若改金额口径，`_calmar_score` 输入格式需一并调整，否则寻优目标函数算错。
  2. `:641` 改为按真实价差算 pnl（与 `:657 close_pnl`/`:668`/`:676` 口径统一）。
  3. **核实 `_fast_simulate` 里 tp_pct 的单位**（`:557` `params.get('tp1_profit')`）——与 P0-1 的单位约定冲突同源，须对齐到统一约定。
- **受影响**：AI 寻优 Python 策略的 1m 仿真目标函数。**这是任务二的前置——目标函数 pnl 必须先正确。**

#### 2.2.5 `sim_trader/SimTraderEngine`（`engine.py:337/446-454`）
- **现状**：买 `cost=shares*price`、卖 `cash += ss*exit_price`、`profit=ss*(exit_price-entry_price)`，全无成本。
- **改**：加可配置成本层——买入 `cost=shares*price+commission`（佣金万2.5最低5元）；卖出 `cash += ss*exit_price - commission - stamp_tax(千1) - transfer_fee(万0.1)`；`profit/return_pct` 基于含费净额。成本率从 config 读。
- **受影响**：模拟盘账户净值、单笔盈亏、累计盈亏。

#### 2.2.6 成本参数入 config（先迁移既有硬编码，再建新段）
- **现状（评审核实）**：`execution.py:56-61` 已有 `DEFAULT_COST_CFG`（commission_rate 万2.5 / min_commission 5 / stamp_tax_rate 千0.5 / slippage_rate 万10），但是**硬编码**；`calc_buy_cost/calc_sell_revenue` 接受可选 `cfg` 参数但调用方都没传。
- **改（顺序很重要）**：
  1. **先**把 `DEFAULT_COST_CFG` 的值迁到 `config/app_setting.json` 的 `backtest.cost` 段，`execution.py` 从 settings 读（保留硬编码作为 settings 缺失时的 fallback）。
  2. **再**让 2.2.1~2.2.5 各路径调用 `calc_buy_cost/calc_sell_revenue` 时统一走这套 config 成本率。
  - 否则：config 建了新段但 execution 仍走硬编码，新段形同虚设。
- **受影响**：所有扣成本路径的成本率来源。
- **注**：sim_trader（2.2.5）此前完全无成本逻辑，新增时直接读同一 config 段，与 execution 口径一致。

## 3. 主任务二：AI 寻优反过拟合（次高优先，依赖任务一）

### 3.1 目标
消除"valid_score 防护被 score 抵消"，让 Optuna 真正在样本外验证集上选优。**前置：任务一已让 pnl 含成本（否则在错误 pnl 上反过拟合无意义）。**

### 3.2 改造点（函数级，三处一起改）

#### 3.2.1 objective 返回 valid_score（`ai_optimizer.py:844`）
- **现状**：`return summary["score"]`（全样本 IS score）。
- **改**：`return summary["valid_score"]`，让 Optuna 在验证集爬山。需确认 `_summarize_result` 已算出 valid_score（WFO 训练窗口内）。

#### 3.2.2 最终选优口径统一（`ai_optimizer.py:1130-1138` `_sort_key`）
- **现状**：`return (score, wfe_val)`（用 IS score 重排），抵消了 Top-10 的 `(valid_score, wfe)` 防护。
- **改**：`return (valid_score, wfe_val)`，与 Top-10 排序（`:1100-1107`）一致。

#### 3.2.3 样本切分按自然交易日（`ai_optimizer.py:1060-1069`）
- **现状**：按信号序号 70/20/10 切（信号时间分布不均时 valid/test 区间畸短）。
- **改**：按自然交易日切；**test 集严格隔离，只在最终展示，绝不参与任何选优/优化**。

### 3.3 结构性增强（中期，可分阶段）
- LHS 种子参数化 + `np.random.default_rng(seed)` 局部生成器（消除 `:193 np.random.seed(42)` 全局污染 + 每次探索点相同）。
- 参数维度 10~12 vs trial 62 自由度不足：先固定 ratio 只搜 pct（**先跑关联分析确认 ratio/pct 哪个方差大再决定固定谁**），或 trial 提到 ≥200。
- 目标函数加回撤惩罚 + 最小交易数门槛；profit_factor 的 `inf`（`:135`）改大常数或 None。
- step 量化（寻优-H1）：LHS/Optuna 支持 `step=`；`apply` 端点对 `_ratio` 用 step=0.05 且 clip≤1.0。

### 3.4 验收口径
- 同一策略对比"旧 IS 选优 vs 新 valid 选优"的 **test 集**表现：新方案 test 集更稳、IS-test gap 更小 → 过拟合被抑制。
- 改前归档旧寻优推荐（`output/optimizer_v1_<tag>/`）。

### 3.5 回滚
寻优跑崩或 valid_score 缺失 → 回退 `_sort_key`/objective 到 score；切分逻辑独立可单独回退。
