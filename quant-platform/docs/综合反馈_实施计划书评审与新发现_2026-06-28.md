## 2. 计划书精度增强（5 处，不影响路线图）

### 2.1 §2.2.4 `_fast_simulate` pnl 格式设计选择

计划书已标注"把成本折算成%扣减或重构为金额口径"——建议**选金额口径**（与 v2 的 `_cost_pnl` 一致），避免%折算引入小数精度问题。且需同步检查 `_calmar_score`（`:72-87`）的输入格式兼容性。

### 2.2 §2.2.6 成本参数「双源」问题

计划书要在 config 新增 `backtest.cost` 段。但 `execution.py:55-61` 当前**硬编码**成本率：

```python
DEFAULT_COST_CFG = {
    'commission_rate': 0.00025,   # 万2.5
    'min_commission': 5.0,
    'stamp_tax_rate': 0.0005,
    'slippage_rate': 0.001,
}
```

计划书应先**把成本率从硬编码迁出到 config**，再在 `backtest.cost` 新增段。否则 config 建了新段但 execution 不读，仍走硬编码。

### 2.3 §6 最小起点「78 公式」→ 应改为「Python 策略」

`_fast_simulate` 是 Python 策略的 1m 寻优路径，78 公式走 TDX 路径（`_run_trial_tdx`→`tdx_runner`）。若 78 公式中均为 TDX 策略，`_fast_simulate` 改动对基线 diff 影响为零。

**建议**：§6 的"78 公式中抽 1 个"明确为"Python 策略（非 TDX）"。

### 2.4 §1 措辞修正

"不给卖出→买入资金回笼加 T+1 拦截"→ 建议改为"不给卖出→买入资金回笼加拦截"。A 股 T+1 限制的是买入→卖出方向，资金回笼不受 T+1 约束——当前措辞可能让后人混淆。

### 2.5 §1.1 K 线图 B 点已修复确认 + 一处无效 fallback

`main.js:3272-3289` 的 B 点逻辑已修复（`if (signalBuyDate)` 不再要求 `isSignal &&`）——计划书标记 ✅ 正确。

但 `main.js:3282` 的 fallback 链 `trade.close` 在回测交易对象中不存在（trade 有 `entry_price`/`exit_price`/`pnl_pct`/`ret_pct`，无 `close`），建议去掉避免误导。

## 3. 评估过程中发现的新问题（3 项，计划书未覆盖）

### 3.1 ⚠️【重要】AI 参数写入系统配置时单位不一致

这是用户在讨论中提出的关键问题，经完整代码链追踪后确认存在。

**问题链路**：

```
AI 寻优 → tp1_profit = 3.0（百分比格式，表示 3%）

  ↓ 路径 A（ai_optimizer.py:175 _build_tp_plan）：
  tp1_profit / 100.0 → profit_pct = 0.03 ✅ 正确

  ↓ 路径 B（ai_optimizer.py:557 _fast_simulate）：
  profit_pct = params.get('tp1_profit', 10.0)  ← 直接用百分比值
  → profit_pct = 3.0 → exit_rules 算 entry*(1+3.0) = 400% ❌ 错误

  ↓ 路径 C（engine.py:610 daily_fallback）：
  profit_pct = params_override.get('tp1_profit', 10.0)  ← 不做 /100
  → profit_pct = 3.0 → 止盈永远不会触发 ❌ 错误

  ↓ 路径 D（api/backtest.py:251 写入 config）：
  {"profit_pct": params["tp1_profit"]}  ← 不做 /100
  → config 的 take_profit_tiers[0].profit_pct = 3.0（300%） ❌ 错误
```

**当前 config 中实际值**（`app_setting.json:26`）：

```json
"profit_pct": 0.027000000000000003   // 0.027 = 2.7%（小数格式，正确）
```

说明某次 AI 写入时恰好给了小数值（~0.027）所以没出事。但如果给了百分比格式（2.7），config 就变成了 270%。

**影响**：
- `api/backtest.py:250-252` 写入 `profit_pct` 不做单位转换
- `engine.py:610/845` 读取不做单位转换（默认值 10.0 当作小数→ 1000% 目标价，止盈永不触发）
- `ai_optimizer.py:557` `_fast_simulate` 中 tp1_profit 不做转换
- 同样的问题可能存在于 `trailing_activate_pct` / `trailing_drawdown_pct` / `breakeven_*` 等百分比参数

**修复建议**：在 `api/backtest.py:250` 写入时增加单位归一化（若 `profit_pct > 1` 则 `/100`），并同步修正 `engine.py:608-614` 的读取路径。建议统一在 `_build_tp_plan` 函数处做归一化，所有调用方都经过它。

### 3.2 ⚠️【重要】系统设置页「保存全局设置」按钮是空 stub

**现状**：`main.js:877` `function saveSettings() { /* stub */ }` —— 函数体为空。

**UI 表现**：用户在系统设置 tab 修改参数后点击"保存全局设置"，按钮看起来正常，但实际上**什么都没有保存**。

**影响**：
- 系统设置页的参数修改不会落盘
- 重启服务后回到默认值 —— **这正是用户反馈的"每次重启回到默认值"问题的根因**
- 但 `/api/settings/risk-params` 和 `/api/backtest/apply-to-system` 两条路径是正常保存的（回测面板→写入 sim_trader config → settings.save()），说明从回测面板写入系统配置的链路是正常的
- 真正有问题的只是**系统设置 tab 的保存按钮**（`saveSettings()` 是 stub）

**修复建议**：实现 `saveSettings()` 函数，收集系统设置 tab 中的所有参数值（包括风控参数、搜索空间、cron 设置等），调用 `/api/settings` POST 写入。

### 3.3 `_fast_simulate` pnl 格式与 `_calmar_score` 契约

`_fast_simulate` 返回百分比 pnl_pct（`realized` 是百分比累加），`_calmar_score`（`:72-87`）做 `np.mean(pnls)` 期望百分比。重构为金额口径时需同步改 `_calmar_score` 的输入格式，否则寻优目标函数计算错误。

## 4. 用户反馈的既有问题（2 项）

### 4.1 「系统配置」按钮对回测面板的读取链路

用户问：回测面板点"系统配置"，系统配置参数没有被读过来填到前端。

**当前链路分析**：

```
点击"系统配置"按钮
  → loadBtConfigFromSystem() (main.js:3966)
  → GET /api/backtest/simple-config (backtest.py:592)
  → _load_bt_config() + _default_bt_config()
  → 返回 config 和 system_config
  → _populateBtConfigUI(sys) (main.js:3980)
```

`_default_bt_config()` 的逻辑（`backtest.py:508-571`）：
1. 先以 `sim_trader/config.py` 硬编码常量为底
2. 再尝试从 `app_setting.json` 的 `backtest` 段覆盖

**这个链路是正常的**——问题在于 `app_setting.json` 的 `backtest` 段是否包含了用户期望的值。如果之前没有人通过 `/api/settings/risk-params` 或 `/api/backtest/apply-to-system` 写入过 `backtest` 段，那读取到的就是 `sim_trader/config.py` 的硬编码默认值。

**需确认的状态**：
- `app_setting.json` 中 `backtest` 段的 `take_profit_tiers` 已存在（`:170-184`），说明 apply-to-system 链路至少跑过一次
- 但如果 `backtest` 段缺某个 key（如 `hard_stop`），该 key 就回退到 `sim_trader/config.py` 的硬编码值

### 4.2 `tp1_profit` / `profit_pct` 的单位不一致

用户问：AI 寻优后写入系统配置，0.2 写 0.2，是 20% 还是 0.2%？

**结论**：这是一个确认存在的**单位解释混乱**。

- `_build_tp_plan`（`:175`）做 `tp1_profit / 100.0` → 语义正确
- `engine.py:610` 和 `_fast_simulate:557` **不做** `/100` → 语义不一致
- `api/backtest.py:251` 写入 config **不做** `/100` → 潜在污染

但在 EOD 设计前提澄清后，当前 **search_space 中的 tp1_profit 值区间（0.83~5.52）是否与 stop 路径的单位一致**需要逐一确认。建议作为实施前的一次独立审查。

## 6. 用户问题的直接回答

### Q1：回测交易有 K 线图展示吗？

**有。** 选股信号表和回测交易表都有"查看图表"/"图表"按钮，调用 `showChart()`（`main.js:3184`），打开 ECharts K 线图。B 点标记已修复。计划书标记正确。

### Q2：优化后 config 的 `optimizer.search_space` 还会对 AI 回测生效吗？

**会。** 计划书 §3 只改了 objective、`_sort_key`、样本切分，没有动搜索空间的读取链路（`ai_optimizer.py:1032 search_space = settings.optimizer_search_space`）。search_space 仍然来自 config，仍然是 LHS + Optuna 的搜索范围来源。**但 step 字段仍然是死字段**（计划书放中期）。

### Q3：系统配置参数没有被读过来填到前端 / 保存后重启回默认值？

**两个独立问题**：
1. **系统设置 tab 的"保存全局设置"按钮是空 stub**（`main.js:877`），导致系统设置页的修改不落盘，重启回到默认值
2. **回测面板"系统配置"按钮的读取链路**（`/api/backtest/simple-config`→`_default_bt_config()`→`sim_trader/config.py`+`app_setting.json`）**本身是正常的**，但受限于 `app_setting.json` 中 `backtest` 段是否被正确写入

### Q4：AI 寻优后 tp1_profit=0.2 写入 config 是 20% 还是 0.2%？

**存在真实的单位混乱**。`_build_tp_plan` 做 `/100`（3.0→0.03=3%），但 `api/backtest.py:251` 写入 config 和 `engine.py:610` 读取都不做转换。当前 config 中的值碰巧是小数值（0.027=2.7%）所以没炸，但如果 AI 输出了百分比格式值（如 5.0），config 就变成 500%。
