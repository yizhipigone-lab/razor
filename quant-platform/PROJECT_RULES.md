# 项目基本要求与开发规则

## 1. 核心原则
*   **严禁使用易封锁或抓包接口**：出于稳定性考虑，本项目所有数据抓取、实时行情、指数拉取等功能**严禁使用**东方财富 (EastMoney)、新浪 (Sina)、腾讯 (Tencent) 的非官方抓包 API 和 AKShare 库。
*   **优先数据源**：
    *   **实时行情与交易主链路**：**全盘使用 QMT**（通过 HTTP 代理模式）。
    *   **历史数据备份与收割**：**使用 Tushare** 作为离线数据池的补充来源。

## 2. 交易网关与环境依赖
*   **废弃 Windows 绑定依赖**：为确保系统能在 Headless 的 Linux Docker 容器中长期运行，系统**已全面剔除** `easytrader`、`pywinauto`、`PySide6`、`vnpy` 等只跑在 Windows 下的包。
*   **实盘代理模式**：系统内的 `QMTGateway` 运行在隔离沙盒内，通过向宿主机的 `http://host.docker.internal:8081/api` 发送 HTTP 指令完成下单，不在容器内生硬绑定 QMT 客户端。

## 3. 分布式架构与 Docker 部署
*   **三服务职能分离**：
    *   `api-server`: 专职对外提供 FastAPI Web 服务，不允许在主循环中运行阻塞任务。
    *   `task-worker`: 通过 `cron_jobs.py` 独立起盘，专职在后台收割 Tushare 数据和跑 VectorBT 回测，崩溃不影响前端。
    *   `redis`: 作为进程间高速消息总线与临时状态缓存。
*   **DuckDB 读写自律**：盘中高频时段，API Server 应尽量对 DuckDB 保持只读模式（`read_only=True`）规避写锁；重度数据灌入（盘后收割）全权交由 Task Worker 独占写锁完成。

## 4. 预览与测试原则 (全局控制)
*   **自检服务状态**：以后每次邀请用户去前端体验或预览时，必须**自行在后台启动对应服务 (如 FastAPI)**，并利用诸如 `curl` 或 `browser_subagent` 工具自行确认后端是否启动成功、前端页面是否能正常加载。
*   **拒绝白内障式交接**：坚决避免让用户跑到前端去体验后，发现服务根本没起或者页面报错，再跑回这里反馈。把“自测跑通再交付验收”作为此项目全过程的必须实施原则。

## 5. 股票代码规范
*   **后缀强制性**：所有传递给交易网关的股票代码**必须强制携带后缀**。
    *   **6开头**股票/ETF -> `.SH` (如 `600519.SH`)
    *   **0或3开头**股票 -> `.SZ` (如 `000001.SZ`, `300120.SZ`)
    *   **指数处理**：上证指数强制为 `000001.SH`，深证成指为 `399001.SZ`。
    *   **5开头**基金/ETF -> `.SH`。

## 6. 部署环境与安全边界声明（审计豁免范围）

*   **单机本地部署前提**：本项目为**个人本地单机使用**，运行在受信的本地环境，**不对公网开放**、无多用户、无外部不可信访问者。所有 API / WebSocket / QMT Proxy 仅供本机或受信内网调用。
*   **安全维度审计豁免**：基于上述前提，以下"网络/应用安全"类问题在本项目语境下**判定为已知可接受风险，不作为缺陷处理，后续审计无需再报告**：
    *   API / WebSocket **无鉴权 / 无 Rate Limiting**（单机无外部访问者）。
    *   **CORS `allow_origins=["*"]`**（无跨站攻击面）。
    *   **QMT Proxy 监听 `0.0.0.0:8081` 无 token**（本机/受信内网）。
    *   `/api/settings/env-keys` **返回明文密钥**、`/api/factory/save_physical_strategy` **exec 用户策略代码无沙箱**（操作者即本人，等同本地执行任意脚本）。
    *   `.env` / `_deprecated/` 中的 **token 入库 / 硬编码**（本地私有仓库，操作者即所有者）。
*   **不豁免的范围（仍须严格对待）**：上述豁免**仅限"外部攻击面"安全**。以下与安全无关、影响**数据正确性 / 计算口径 / 资金核算 / 回测真实性**的问题**不在豁免内**，必须照常审计修复：
    *   成本 / T+1 / 涨停 / 复权口径一致性。
    *   AI 寻优过拟合、单位约定、配置真相源唯一性。
    *   数据同步正确性、静默吞异常导致的**用错数据**（区别于"无鉴权"——吞异常用错数据仍是缺陷）。
    *   性能、测试覆盖、架构债等工程质量。
*   **说明**：若未来本项目改为多用户 / 公网部署，本节豁免**立即失效**，须重新对全部安全项做整改。

## 7. 数据层专项审计结论（2026-06-29 归档）

> 本节点是对审计报告(76项) + P0/P1整改后三条数据层主线的最终确认。经代码修复+验证+本次全量重同步实地调查后，结论如下。

### 7.1 min5 列名统一（数据-C1）
- **修复**：`download_min5_bars` 两路径(Tushare+TDX兜底)输出 `datetime`；增量 worker 按 freq 选列；`batch_save_bars` 旧 `date` 列文件自动归一 `datetime`。
- **验证**：旧文件与新列正确合并，无双列/NaN。
- **状态**：✅ 已闭环。

### 7.2 日线前复权口径（数据-C3）
- **修复**：读取层 `_apply_qfq_by_code`（qfq = raw × adj_factor / 文件内最新因子）；写入层 pipeline 拉 `pro.adj_factor`、engine 三路径标记 `adj_factor=1.0`；存量 5550 文件补 `adj_factor=1.0`。
- **2026-06-29 专项核实**：实地拉取万科(000002) Tushare `pro.adj_factor` 返回绝对因子(最新 181.7)——存量 parquet 的 close(最新~3元)已经是"以最新因子为基准的前复权价"，即前复权工作**在数据拉取时由 Tushare `pro.daily` 接口已自动完成**。因此 `adj_factor=1.0` 是正确的"不要二次复权"标记，写入任何非 1.0 的真实因子都会导致读取层二次变化、全库价格污染。
- **唯一标记**：`adj_factor=1.0` 意指"已是前复权基准价，读取层不要再动"。这是唯一安全的标记，不需要也不应该升级为真实因子。
- **状态**：✅ 已闭环（存量 1.0 是正确终态，不需要全量重同步）。
- **规范**：未来任何同一写入路径在落盘前必须先确认：价格是否已前复权？若是则设 `adj_factor=1.0`；若否则必须同时写入对应的 `adj_factor`。

### 7.3 双时段幂等（数据-C4）
- **修复**：`run_daily_pipeline(force=False)` 按 `(日期, 时段 am/pm)` 幂等键防止同天重复消耗 Tushare 配额；手动触发 `trigger_manual_run` 用 `force=True` 绕过。
- **状态**：✅ 已闭环。

### 7.4 结论
数据层三条主线经代码修复 + 运行验证 + 实地调查，**全部已闭环，不需要额外再跑全量重同步**。存量 1.0 标记是正确的稳态终点。
